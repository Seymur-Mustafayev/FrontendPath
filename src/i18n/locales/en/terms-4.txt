@@ term.engine.tr
JavaScript engine

@@ term.engine.def
The program that processes and executes your code: V8 (Chrome, Node.js), SpiderMonkey (Firefox), JavaScriptCore (Safari).

The engine doesn't just read code line by line — it first parses it, turns it into an internal representation (bytecode), then executes it, and while running it re-optimizes the hot (frequently executed) parts.

The book's main claim: without knowing this processing model it is impossible to explain the rules of [[scope]].

@@ term.engine.ex
V8 → parse → AST → bytecode (Ignition) → optimized code (TurboFan)

@@ term.compilation.tr
Compilation

@@ term.compilation.def
Turning the whole source code into a list of instructions the machine understands. The result is usually saved as a file and executed later.

In JavaScript this process doesn't happen in a build step, but a few microseconds before the code runs. Even so, the order is the same: first the whole program is parsed/compiled, then execution begins.

See the [[two-phases]] topic — the book shows the proof through three behaviors.

@@ term.interpretation.tr
Interpretation

@@ term.interpretation.def
Processing source code line by line: each line is converted and executed immediately, then the next line follows.

JS was long considered an “interpreted scripting language”, but the behavior of modern engines doesn't fit that — even if a syntax error sits at the end of the program, the first line never runs.

@@ term.tokenizing.tr
Tokenizing / lexical analysis

@@ term.tokenizing.def
The first stage of compilation: the stream of characters is split into meaningful pieces the language understands — tokens.

```
var a = 2;   →   [var] [a] [=] [2] [;]
```

The difference between tokenizing and lexing is subtle: if a token is recognized statelessly, it is tokenizing; if stateful parsing rules kick in during recognition, it is lexing.

The term “lexical scope” comes precisely from the name of this stage ([[lexical-scope]]).

@@ term.ast.tr
Parsing and the Abstract Syntax Tree

@@ term.ast.def
The second stage: the token stream is turned into a nested tree that describes the grammatical structure of the program. This tree is called the Abstract Syntax Tree (AST).

```
var a = 2;

VariableDeclaration
 ├─ Identifier (a)
 └─ AssignmentExpression
     └─ NumericLiteral (2)
```

Practical benefit: ESLint, Prettier, Babel, TypeScript and Vite all read and change code at the AST level. The answer to “why did my code get changed like this?” usually lives in the AST.

@@ term.code-generation.tr
Code generation

@@ term.code-generation.def
The third stage: the AST is turned into executable instructions. For `var a = 2;` the engine builds instructions that create the variable `a` (allocating memory) and write a value into it.

The details of this stage vary sharply by language and platform; the book deliberately doesn't go into them and focuses on observable behavior.

@@ term.jit.tr
Just-in-time compilation

@@ term.jit.def
A JS engine has no time to spare: compilation doesn't happen in a build step but a few microseconds before execution. To stay fast, the engine uses tricks — it compiles functions lazily and recompiles and optimizes frequently running “hot” code.

This is why the same function in your code can run at different speeds at different moments of the program.

@@ term.two-phases.tr
Two phases: parse first, then execute

@@ term.two-phases.def
The book's central claim: a JS program is processed in at least two phases — first a complete parse/compilation, then execution.

The specification doesn't require the word “compilation”, but the behaviors it requires are only possible with this model. The proof is three observations: [[syntax-error]], [[early-error]] and [[hoisting]].

Practical consequence: the [[scope]] structure is determined BEFORE execution and doesn't depend on runtime conditions.
