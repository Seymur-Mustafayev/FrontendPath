@@ exam.ydkjs-scope.ch1.0.q
According to the book, how is a JS program processed?

@@ exam.ydkjs-scope.ch1.0.o0
It is interpreted top-down, line by line

@@ exam.ydkjs-scope.ch1.0.o1
In at least two phases: parsing/compilation first, then execution

@@ exam.ydkjs-scope.ch1.0.o2
It is compiled only ahead of time, in a build step

@@ exam.ydkjs-scope.ch1.0.o3
Each line is compiled separately right before it runs

@@ exam.ydkjs-scope.ch1.0.why
The chapter's central claim: processing happens in (at least) two phases — parsing/compilation first, then execution. This is observable fact, not theory: syntax errors, early errors and hoisting prove it.

@@ exam.ydkjs-scope.ch1.1.q
What is the correct order of the three stages of classic compiler theory?

@@ exam.ydkjs-scope.ch1.1.o0
Parsing → Tokenizing/Lexing → Code Generation

@@ exam.ydkjs-scope.ch1.1.o1
Code Generation → Parsing → Tokenizing/Lexing

@@ exam.ydkjs-scope.ch1.1.o2
Tokenizing/Lexing → Parsing → Code Generation

@@ exam.ydkjs-scope.ch1.1.o3
Tokenizing/Lexing → Code Generation → Parsing

@@ exam.ydkjs-scope.ch1.1.why
First the characters are broken into tokens (tokenizing/lexing), then an AST is built from the tokens (parsing), and finally the AST is turned into executable code (code generation).

@@ exam.ydkjs-scope.ch1.2.q
What is the difference between tokenizing and lexing?

@@ exam.ydkjs-scope.ch1.2.o0
Lexing identifies tokens with stateful rules, tokenizing does it in a stateless way

@@ exam.ydkjs-scope.ch1.2.o1
Lexing builds the AST, tokenizing doesn't

@@ exam.ydkjs-scope.ch1.2.o2
Tokenizing only removes whitespace

@@ exam.ydkjs-scope.ch1.2.o3
There is no difference, they are just two names

@@ exam.ydkjs-scope.ch1.2.why
The difference is subtle and academic: if the tokenizer invokes stateful parsing rules to figure out whether `a` is a distinct token, that is **lexing**.

@@ exam.ydkjs-scope.ch1.5.q
Where does the `ReferenceError` occur, and why?

@@ exam.ydkjs-scope.ch1.5.o0
On the `var greeting = 'Hello'` line, because `var` isn't allowed in a block

@@ exam.ydkjs-scope.ch1.5.o1
On the `console.log` line, because `greeting` is declared twice

@@ exam.ydkjs-scope.ch1.5.o2
There is no error, `'Hi'` is printed

@@ exam.ydkjs-scope.ch1.5.o3

@@ exam.ydkjs-scope.ch1.5.why

@@ exam.ydkjs-scope.ch1.10.q
Which statement about `eval(..)` and `with` is true?

@@ exam.ydkjs-scope.ch1.10.o0
In non-strict mode they can modify scope at runtime; in strict mode that isn't possible

@@ exam.ydkjs-scope.ch1.10.o1
Both improve performance

@@ exam.ydkjs-scope.ch1.10.o2
They only work in strict mode

@@ exam.ydkjs-scope.ch1.10.o3

@@ exam.ydkjs-scope.ch1.10.why
`eval` can add `var`/`function` declarations at runtime, and `with` turns an object into a scope. Both hurt performance and readability, and in strict mode these "cheats" are not available.

@@ exam.ydkjs-scope.ch2.0.why

@@ exam.ydkjs-scope.ch2.1.q

Only GREEN(3)

@@ exam.ydkjs-scope.ch2.1.o3

@@ exam.ydkjs-scope.ch2.1.why
A reference is allowed for declarations in the current scope and in any scope above/outside it. GREEN(3) is the innermost, so it sees all three.

@@ exam.ydkjs-scope.ch2.2.q
Can an expression in the BLUE(2) scope (the `getStudentName` function) reference the `student` (GREEN) variable?

@@ exam.ydkjs-scope.ch2.2.o1

@@ exam.ydkjs-scope.ch2.2.why

@@ exam.ydkjs-scope.ch2.3.q
When are scope bubbles determined?

@@ exam.ydkjs-scope.ch2.3.o0
During compilation — based on where functions and blocks are written

@@ exam.ydkjs-scope.ch2.3.o1
On every function call, based on the call site

@@ exam.ydkjs-scope.ch2.3.o2
When the program finishes

@@ exam.ydkjs-scope.ch2.3.o3
When the browser loads the page, based on the DOM

@@ exam.ydkjs-scope.ch2.3.why
Bubbles are determined during compilation from the structure of the code. Each bubble is entirely inside its parent — a scope is never partially in two outer scopes.

@@ exam.ydkjs-scope.ch2.4.q
How does JS see the statement `var students = [ .. ]`?

@@ exam.ydkjs-scope.ch2.4.o0
As a single operation — everything happens at once during execution

@@ exam.ydkjs-scope.ch2.4.o1

@@ exam.ydkjs-scope.ch2.4.o2

@@ exam.ydkjs-scope.ch2.4.o3
As three operations: lexing, parsing and assignment

@@ exam.ydkjs-scope.ch2.4.why

@@ exam.ydkjs-scope.ch2.5.q
What is Scope Manager's job?

@@ exam.ydkjs-scope.ch2.5.o0
Breaking the code into tokens

@@ exam.ydkjs-scope.ch2.5.o1
Executing the program from start to finish

@@ exam.ydkjs-scope.ch2.5.o2
Maintaining a lookup list of declared identifiers and enforcing the rules for accessing them

@@ exam.ydkjs-scope.ch2.5.o3
Producing machine code

@@ exam.ydkjs-scope.ch2.5.why
Engine is responsible for compilation and execution, Compiler for parsing and code generation, and Scope Manager for the list of variables and the rules for accessing them.

@@ exam.ydkjs-scope.ch2.6.q

@@ exam.ydkjs-scope.ch2.6.o0
Throws a SyntaxError

@@ exam.ydkjs-scope.ch2.6.o1
Deletes the old variable and creates a new one

@@ exam.ydkjs-scope.ch2.6.o2

Once, during compilation

@@ exam.ydkjs-scope.ch2.7.o1
Three times — each execution gets its own Scope Manager instance

@@ exam.ydkjs-scope.ch2.8.q
How are variables initialized when a scope starts executing?

@@ exam.ydkjs-scope.ch2.8.o0
`function` → the function reference, `var` → `undefined`, `let`/`const` → not initialized (TDZ)

@@ exam.ydkjs-scope.ch2.8.o1

@@ exam.ydkjs-scope.ch2.8.o2
`var` → not initialized, `let`/`const` → `undefined`

@@ exam.ydkjs-scope.ch2.8.o3

@@ exam.ydkjs-scope.ch2.8.why
At the start of a scope all identifiers are registered (variable hoisting). Function declarations are bound to their function right away, `var` gets `undefined`, and `let`/`const` stay in the TDZ until their declaration.
