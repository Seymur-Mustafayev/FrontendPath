@@ exam.ydkjs-scope.ch6.0.q

@@ exam.ydkjs-scope.ch6.0.o0
Keep all variables in the global scope so everyone can reach them

@@ exam.ydkjs-scope.ch6.0.o1
Expose the bare minimum by default: declare variables in as small and deeply nested scopes as possible

@@ exam.ydkjs-scope.ch6.0.o3

@@ exam.ydkjs-scope.ch6.6.q

@@ exam.ydkjs-scope.ch6.6.o0
An immediately invoked function expression — it creates a scope to hide variables

@@ exam.ydkjs-scope.ch6.6.o1
An imported function expression

@@ exam.ydkjs-scope.ch6.6.o2

@@ exam.ydkjs-scope.ch6.7.q
Why are the `( .. )` around the function required in a standalone IIFE?

@@ exam.ydkjs-scope.ch6.7.o0
For readability

@@ exam.ydkjs-scope.ch6.7.o1
They mark the function as an expression, not a declaration

@@ exam.ydkjs-scope.ch6.7.o2
They create the scope

@@ exam.ydkjs-scope.ch6.7.o3
They aren't required

@@ exam.ydkjs-scope.ch6.7.why
In the middle of an expression (e.g. `var x = function(){}()`) the parentheses are optional. In a standalone IIFE, without them the parser would read `function` as a declaration. For consistency, always writing them is recommended.

@@ exam.ydkjs-scope.ch6.8.q
Which statements change meaning when code is wrapped in an IIFE?

@@ exam.ydkjs-scope.ch6.8.o0
`let` and `const`

@@ exam.ydkjs-scope.ch6.8.o1

@@ exam.ydkjs-scope.ch6.8.o2
`if` and `else`

@@ exam.ydkjs-scope.ch6.8.o3

@@ exam.ydkjs-scope.ch6.8.why
An IIFE is a full function: `return` refers to the IIFE, a non-arrow IIFE changes `this`, and `break`/`continue` can't cross the function boundary. In such cases it's better to create the scope with a block.

@@ exam.ydkjs-scope.ch6.10.q

The `{ }` of an object literal, a `class` body, and around a `switch`'s `case` clauses are not blocks. A function body is technically not a block either, but it is a function scope.
