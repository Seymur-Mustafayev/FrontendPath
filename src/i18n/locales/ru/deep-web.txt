@@ deep.web.0
То, как браузер получает адрес и показывает пиксели на экране, — не одна операция, а конвейер из нескольких последовательных этапов. Этот конвейер называется [[critical-rendering-path]], и почти всё, что говорят о производительности фронтенда, касается какой-то точки этой последовательности.

## Этапы по порядку

1. Parse HTML — браузер читает байты, делит их на токены и строит дерево [[dom]]. Процесс инкрементальный: дерево растёт по мере того, как HTML приходит частями.

2. Parse CSS — все источники стилей (внешние файлы, тег style, inline-стили) читаются и превращаются в дерево [[cssom]]. CSS блокирует рендеринг: браузер ничего не рисует, пока CSSOM не будет полностью готов, потому что не знает, как должны выглядеть элементы.

3. Render tree — DOM и CSSOM объединяются. Попадают только видимые элементы: элемента с `display:none` в render tree нет, а элемент с `visibility:hidden` есть (занимает место, но не виден). Эта разница — классический вопрос на собеседовании junior.

4. Layout (reflow) — вычисляются точные размеры и координаты каждого элемента. Этот этап зависит от размера документа и стоит дорого.

5. Paint — пиксели рисуются по слоям. 6. Composite — слои объединяются и выводятся на экран.

## Что происходит, когда меняешь то или иное

Практическая польза от знания этой последовательности: изменяемое CSS-свойство определяет, с какого этапа работа будет повторяться.

```
width, height, top, margin, font-size  →  Layout + Paint + Composite  (самое дорогое)
color, background, box-shadow          →  Paint + Composite
transform, opacity                     →  только Composite  (самое дешёвое)
```

Поэтому в анимации вместо `left` используют `transform: translateX()`, а вместо `display` — `opacity`. При 60 FPS на каждый кадр есть 16.6 ms; анимация, вызывающая layout, легко превышает этот бюджет, и пользователь видит «дёрганье».

## Блокирующие скрипты

Когда парсер при чтении HTML встречает `<script>`, он останавливается: скрипт загружается, выполняется, и только потом парсинг продолжается. Причина в том, что скрипт может изменить документ через `document.write`. Решение — два атрибута:

```html
<script src='app.js' defer></script>  <!-- грузится параллельно, выполняется по порядку после готовности DOM -->
<script src='analytics.js' async></script> <!-- грузится параллельно, выполняется сразу по готовности, порядок не гарантирован -->
```

Для кода приложения правильный выбор — `defer`, для независимых скриптов без зависимостей (аналитика) — `async`.

## Частые ошибки

Читать размер элемента (`offsetHeight`) в обработчике прокрутки и сразу же записывать стиль — это называется layout thrashing: при каждом чтении браузер выполняет принудительный [[reflow]], чтобы применить предыдущие записи. Решение: сначала выполнить все чтения, потом все записи, или использовать `requestAnimationFrame`.

> Запомни: React или любой другой фреймворк не отменяет этот конвейер — он лишь управляет тем, когда трогать DOM. Проблемы производительности всё равно возникают на этих шести этапах.

[[http]] — текстовый протокол без состояния (stateless). Без состояния означает, что сервер не помнит тебя между двумя запросами: каждый запрос должен нести информацию, доказывающую, кто ты (cookie, токен). Большая часть ежедневной работы фронтенд-разработчика — правильно строить эти запросы и правильно читать ответы.

## Анатомия запроса

```
POST /api/v1/orders HTTP/1.1          ← метод, путь, версия
Host: api.example.com                  ← заголовки
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...
                                       ← пустая строка
{ 'customerId': 42, 'total': 19.90 }   ← тело
```

Методы несут смысловую нагрузку: GET читает и ничего не меняет (поэтому его можно кэшировать), POST создаёт новый ресурс, PUT полностью заменяет, PATCH частично обновляет, DELETE удаляет. Класть тело в GET-запрос или менять данные через GET — нарушение протокола, которое ломает механизмы кэша, прокси и повторных попыток.

## Коды состояния — практическое прочтение

Группы [[status-code]] нужно не заучивать, а превращать в поведение UI:

```
200 OK          → показать данные
201 Created     → создано, обычно приходит id нового ресурса
204 No Content  → успех, но тела нет (типично после DELETE)
400 Bad Request → показать пользователю ошибки формы
401 Unauthorized→ личности нет / истекла → на страницу входа или в процесс обновления
403 Forbidden   → личность есть, прав нет → сообщение «у вас нет доступа»
404 Not Found   → UI пустого состояния
409 Conflict    → например, одновременное редактирование; попроси пользователя решить
422             → ошибки валидации (некоторые API отдают его вместо 400)
429 Too Many    → смотри заголовок retry-after, жди
500 / 502 / 503 → «техническая проблема», кнопка повтора, лог в Sentry
```

Путать 401 и 403 — самая частая ошибка: если при 403 отправить пользователя на страницу входа, получится бесконечный цикл, ведь он уже вошёл.

## Заголовки

Набор [[http-header]] определяет поведение запроса. Самые используемые: `Content-Type` (формат, который ты отправляешь), `Accept` (формат, который ты хочешь получить), `Authorization` (токен), `Cache-Control` (поведение кэша), `ETag` и `If-None-Match` (условный запрос — если данные не изменились, сервер вернёт 304, и трафик не тратится).

## HTTP/2 и разница версий

В HTTP/1.1 к одному домену одновременно открывалось ограниченное число соединений, поэтому объединение файлов (конкатенация, спрайты) считалось оптимизацией. HTTP/2 принёс мультиплексирование — параллельные запросы по одному соединению. В результате часть старых советов устарела: сегодня собирать весь JS в один огромный файл часто вредно, потому что маленькое изменение инвалидирует кэш всего файла.

## Замечание о безопасности

[[https]] — это не просто «зелёный замок»: без [[tls]] современные API браузера вроде Service Worker, Geolocation, Clipboard вообще не работают. То есть HTTPS сегодня — функциональное требование.

## Разрешение DNS

[[dns]] превращает доменное имя в IP-адрес. Цепочка такая: кэш браузера → кэш операционной системы → DNS-сервер провайдера → корневые серверы → авторитетный сервер домена. На каждом шаге есть значение TTL (time to live), поэтому изменение DNS не видно по всему миру сразу — распространение может занять часы.

Практический вывод: при переносе домена на новый хостинг старый сервер нельзя сразу выключать, иначе у части пользователей сайт не откроется.

## Хостинг и разница между статикой и динамикой

Среда [[hosting]] бывает двух видов: сервер статических файлов (отдаёт HTML/JS/CSS, код не выполняет) и среда выполнения (Node.js-сервер, serverless-функции). Обычное React SPA на Vite ложится на статический хостинг; режим SSR в Next.js требует среды выполнения. В Azure это выбор между Static Web Apps и App Service.

Классическая проблема при размещении SPA на статическом хостинге: если открыть `/orders/12` напрямую, приходит 404, потому что такого файла на сервере нет. Решение — правило fallback: перенаправлять все неизвестные пути на `index.html`, а маршрутизацию решает роутер в браузере.

## CDN и кэш

[[cdn]] хранит твои файлы в точках, распределённых по миру (edge). Польза двойная: сокращается физическое расстояние и не нагружается исходный сервер.

Стандартная формула кэширования:

```
index.html          → Cache-Control: no-cache  (всегда перепроверять, файл маленький)
app.9f3a2b.js       → Cache-Control: max-age=31536000, immutable
style.71c0de.css    → то же: в имени есть хэш, при изменении содержимого меняется имя
```

Этот приём называется «cache busting»: хэш в имени файла вычисляется из содержимого при создании [[build-artifact]]. Никогда не проси пользователей вручную чистить кэш — это признак ошибки в конфигурации.

## Привычка диагностики

Если деплой прошёл, а видна старая версия, порядок такой: (1) в панели Network посмотри статус ответа `index.html` и заголовок `age`, (2) если это «200 from disk cache», правило кэширования неверное, (3) сделай purge в панели CDN, (4) если есть имена файлов без хэша, исправь конфигурацию сборки.

## Главная идея REST

[[rest]] — ресурсно-ориентированный стиль. URL указывает на ресурс (существительное), а метод — на операцию (глагол):

```
GET    /orders?status=paid&page=2   → список заказов с фильтром
GET    /orders/12                   → один заказ
POST   /orders                      → создать новый заказ
PATCH  /orders/12                   → изменить статус
DELETE /orders/12                   → удалить
GET    /orders/12/items             → вложенный ресурс
```

Адреса вроде `/getOrders`, `/createOrder` — это стиль RPC: не ошибка, но и не REST. Понимание того, в каком стиле сделан проект, экономит время при чтении документации.

## Форма ответа и модель UI

Ответ API часто приходит не в той форме, которая нужна UI. Чтобы это исправить, полезно держать слой-адаптер: модель API → доменная модель → props для UI. Тогда, если бэкенд переименует поле, изменится одна функция, а не все компоненты.

```js
// api/orders.ts
const toOrder = (dto) => ({
  id: dto.order_id,
  total: Number(dto.total_amount),
  createdAt: new Date(dto.created_at),
  isPaid: dto.status === 'PAID'
});
```

## Пагинация, фильтры и сортировка

[[pagination]] бывает двух видов: на основе offset (`?page=2&size=20` — просто, но при изменении данных строки могут сдвигаться) и на основе курсора (`?after=eyJpZCI6MTJ9` — устойчиво для больших и живых списков). Знать, какой вариант у тебя, важно для правильной реализации «бесконечной прокрутки».

## Идемпотентность и повторный клик

[[idempotent]] операция при повторе не меняет результат. GET, PUT и DELETE идемпотентны, POST — нет. Значит, если пользователь дважды нажмёт «Создать», могут создаться два заказа. Решение на фронтенде: блокировать кнопку во время отправки. Полное решение — согласованный с сервером ключ идемпотентности: для каждой формы отправляется один UUID, и, увидев повторный ключ, сервер возвращает прежний результат.

## Умение читать документацию

Пять вещей, на которые стоит смотреть на странице Swagger/OpenAPI: (1) тип аутентификации, (2) обязательные заголовки, (3) схемы запроса и ответа, (4) формат ошибок, (5) формат дат и чисел. С датами особенно важны ISO 8601 и часовой пояс — значение `2026-03-15T21:00:00Z` в Баку должно отображаться как дата следующего дня.

## Network — здесь 80 процентов проблем с данными

Во вкладке [[network-tab]] есть статус, заголовки, payload и разбивка по времени каждого запроса. Порядок диагностики:

```
Запрос вообще не виден          → код не запускается, условие неверное
Статус (failed) / ошибка CORS   → заголовки сервера, preflight
401 / 403                        → токена нет, истёк или нет прав
200, но UI пустой                → форма ответа отличается от ожидаемой
Запрос повторяется много раз     → зависимости useEffect или query key нестабильны
```

Последний случай в React встречается очень часто: если в зависимости передаётся объект, создаваемый заново на каждом рендере, эффект уходит в бесконечный цикл. Десятки повторов одного и того же запроса в панели Network — первый признак этого.

## Sources — культура точек останова
