@@ topic.next.0.t
CSR, SSR, SSG, ISR и hydration

@@ topic.next.0.body
При [[csr]] HTML приходит пустым, и всё загружает JS — нормально для внутренних панелей, слабо для публичного сайта. [[ssr]] готовит HTML на сервере: первый экран быстрый, данные свежие. [[ssg]] готовит его во время сборки — самый быстрый вариант. [[isr]] обновляет статическую страницу в фоне с заданным интервалом.

[[hydration]] — это подключение JS к HTML, пришедшему с сервера. Если сервер и клиент отрендерили разный результат (например, из-за new Date() или localStorage), получаешь ошибку гидратации — одну из самых частых ошибок в Next.js.

@@ topic.next.1.t
App Router, Server Components и Server Actions

@@ topic.next.1.body
В [[app-router]] компоненты по умолчанию являются [[rsc]]: работают на сервере, не попадают в бандл и могут напрямую обращаться к БД/API. 'use client' пишется только там, где нужна интерактивность.

С помощью [[server-action]] форма обрабатывается на сервере без написания API-маршрута. [[streaming]] отправляет страницу частями и сразу показывает то, что уже готово. Практическое правило: опускай клиентскую границу как можно ниже, к листовым компонентам.

@@ topic.next.2.t
Маршрутизация, layout и UI состояний

@@ topic.next.2.body
В [[file-based-routing]] структура папок определяет URL. [[layout]] сохраняется между маршрутами и не перерендеривается при навигации — туда выносятся сайдбар и шапка.

Через loading.tsx и error.tsx для каждого маршрута декларативно задаётся UI ожидания и ошибки. Когда нужен серверный endpoint, пишется [[route-handler]].

@@ topic.next.3.t
Загрузка данных и стратегии кэширования

@@ topic.next.3.body
Слои кэширования Next.js (request memoization, data cache, full route cache) полезны, но при неправильном понимании вызывают проблему «данные не обновляются». Выбирай [[revalidate]] и параметры кэша осознанно для каждого fetch.

При выборе [[cache-strategy]] вопрос простой: одинаковы ли эти данные для всех пользователей или они личные? Насколько старыми они могут быть? Пустить личные данные в статический кэш — проблема безопасности.

@@ topic.next.4.t
Деплой, переменные окружения и сборка

@@ topic.next.4.body
[[env-variable]] меняется в зависимости от окружения; префикс NEXT_PUBLIC_ выводит значение в браузер — класть туда ключи и секреты является реальной ошибкой безопасности.

[[build-artifact]] должен собираться один раз и распространяться во все окружения. [[vercel]] требует минимум настройки для Next.js; Azure App Service / Static Web Apps — стандарт в корпоративной среде и интегрируются с pipeline.

@@ topic.test.0.t
Что тестировать — пирамида тестов и ценность

@@ topic.test.0.body
[[test-pyramid]]: много [[unit-test]], меньше [[integration-test]], меньше всего [[e2e]]. Во фронтенде же центр тяжести — интеграционные тесты: компонент + его хуки + замоканный API вместе.

При написании теста вопрос должен звучать не «работает ли эта функция?», а «может ли пользователь пройти этот сценарий?». Не гонись за цифрой [[coverage]]; критические сценарии (вход, создание заказа, оплата) должны быть покрыты.

@@ topic.test.0.note
Практическое правило для начала: на каждый исправленный баг пиши тест, который его воспроизводит. Через месяц у тебя будет настоящий набор тестов.

@@ topic.test.1.t
Основы Vitest и структура теста

@@ topic.test.1.body
[[vitest]] основан на Vite, совместим с API Jest и быстр. Файл теста строится из блоков describe/it, а проверка выполняется через [[assertion]].

Хороший тест проверяет одно поведение, его название говорит, что именно проверяется (should show error when API fails), и он сохраняет структуру Arrange-Act-Assert. [[test-runner]] запускают в режиме watch — результат виден сразу во время написания.

@@ topic.test.2.t
Тестирование поведения с React Testing Library

@@ topic.test.2.body
Философия [[rtl]]: тестируй не реализацию, а то, что видит пользователь. Поэтому смотрят не на state, а на текст и роли на экране.

[[query-by-role]] — самый устойчивый способ выбора, потому что работает через дерево доступности и заодно косвенно проверяет a11y. Для действий пользователя используй [[user-event]] (а не fireEvent), асинхронный результат жди через findBy.... Если видишь предупреждение [[act]], значит, обновление состояния происходит там, где его не ждали.

@@ topic.test.3.t
Моки, MSW и изоляция тестов

@@ topic.test.3.body
[[mock]] заменяет реальную зависимость, [[spy]] отслеживает вызовы. Для сети лучший подход — не мокать fetch, а подделывать API на сетевом уровне с помощью [[msw]]: код выполняет настоящий fetch, а ответ остаётся под контролем.

Так одни и те же моки можно использовать и в тестах, и в dev-среде, а UI можно писать, пока бэкенд ещё не готов.

@@ topic.test.4.t
Тестирование хуков и мемоизации (useMemo/useCallback)

@@ topic.test.4.body
Для изолированного тестирования хука есть [[renderhook]]; результат читается через result.current, а изменение props имитируется через [[rerender]].

Золотое правило для [[memoization-test]]: не тестируй сам useMemo — тестируй его результат. Есть два способа: (1) заменить дорогую функцию на vi.fn() и проверить, что она не вызывается повторно, когда props не меняются; (2) убедиться, что ссылка осталась той же, что и в предыдущем рендере (toBe). А то, что дочерний компонент не рендерится лишний раз, измеряется счётчиком рендеров.

@@ topic.test.4.note
Эта тема — пересечение двух твоих слабых областей (тестирование + производительность React): пусть один из первых 3 тестов, которые ты напишешь, будет здесь.

@@ topic.test.5.t
E2E с Playwright и стабильные тесты

@@ topic.test.5.body
[[playwright]] проверяет весь сценарий в настоящем браузере, а механизм auto-wait избавляет от большого количества кода ожидания.

[[selector-strategy]] критически важна: тест, привязанный к CSS-классу, падает при первом рефакторинге — используй role, label или data-testid. [[flaky-test]] — главный враг; причина обычно в фиксированных sleep и состоянии гонки, а решение — явные условия ожидания и независимость тестов друг от друга.

@@ topic.git.0.t
Ядро Git: commit, branch, HEAD

@@ topic.git.0.body
[[commit]] — это снимок; [[branch]] — просто указатель на коммит, и понимание этого — половина Git. [[head]] показывает, где ты находишься сейчас.

Хороший коммит атомарен: одно логическое изменение и понятное сообщение (что сделал и зачем). Сообщения вроде «fix» или «update» через неделю никому ничего не скажут. Формат Conventional Commits (feat:, fix:) создаёт основу для автоматического changelog и [[semantic-versioning]].

@@ topic.git.1.t
Merge, rebase и разрешение конфликтов

@@ topic.git.1.body
[[merge]] объединяет историю как есть, а [[rebase]] переносит твои коммиты поверх новой базы и создаёт прямую линию. Золотое правило: не делай rebase общей ветки — это ломает историю других.

[[merge-conflict]] — не ошибка, а нормальная ситуация: прочитай обе стороны, запиши правильный результат, удали маркеры, протестируй и продолжай. С помощью [[interactive-rebase]] можно сделать [[squash]] коммитов и навести порядок, а через [[cherry-pick]] — перенести отдельное исправление в другую ветку.

@@ topic.git.1.note
Способ потренироваться: создай тестовый репозиторий, намеренно устрой конфликт и разреши его. Страх перед конфликтами проходит только с повторением.

@@ topic.git.2.t
Стратегии ветвления и культура PR

@@ topic.git.2.body
При подходе [[trunk-based]] ветки живут недолго и часто сливаются в main — это современный стандарт вместе с CI/CD. [[git-flow]] всё ещё встречается в продуктах с графиком релизов.

[[pull-request]] — ворота для просмотра кода. Хороший PR небольшой, у него есть описание, и он объясняет, что и почему изменилось. На [[code-review]] смотри на код, а не на человека; пиши своё предложение вместе с причиной. Если отзыв получаешь ты: не защищайся, спроси о причине.

@@ topic.git.3.t
Azure DevOps: Boards, Repos, Pipelines

@@ topic.git.3.body
[[azure-devops]] состоит из трёх частей: Boards (рабочие элементы), Repos (Git) и [[pipeline]]. Если указать в сообщении коммита номер рабочего элемента (#1234), изменение связывается с задачей и его можно отследить.

На практике важны branch policy: запрет прямого push в main, минимум один ревьюер, обязательная успешная сборка. Это и есть ответ на вопрос «как работают в команде».

@@ topic.git.4.t
CI/CD: автоматизация сборки, тестов и деплоя

@@ topic.git.4.body
[[ci]] при каждом push автоматически запускает сборку, линтинг и тесты; [[cd]] выкатывает прошедшее проверку изменение в окружение. Типичные шаги [[yaml-pipeline]]: install → lint → type-check → test → build → публикация [[artifact]] → deploy.

Локально [[pre-commit-hook]] (Husky + lint-staged) ловит ошибку ещё до того, как она дойдёт до CI. Если pipeline упал, не паникуй: прочитай лог сверху вниз, найди упавший шаг и выполни ту же команду локально.

@@ topic.perf.0.t
Core Web Vitals: LCP, INP, CLS

@@ topic.perf.0.body
[[lcp]] — время появления самого большого видимого элемента (цель < 2.5s), [[inp]] — задержка реакции на действие пользователя (< 200ms), [[cls]] — неожиданный сдвиг раскладки (< 0.1).

[[lighthouse]] — лабораторное измерение, оно не совпадает с данными реальных пользователей (RUM). Самое дешёвое решение для CLS: заранее задать размеры для изображений и рекламных блоков и использовать swap для шрифтов.

@@ topic.perf.1.t
Размер бандла и разделение кода

@@ topic.perf.1.body
[[bundle-size]] — самый большой рычаг скорости фронтенда. Сначала измерь: посмотри самые тяжёлые пакеты через bundle analyzer (библиотеки дат, графики, наборы иконок и файлы локализации — классические виновники).

Затем сделай [[code-splitting]]: [[dynamic-import]] на уровне маршрутов и для тяжёлых компонентов. Чтобы работал [[tree-shaking]], используй именованные импорты — default-импорт всей библиотеки его отключает.

@@ topic.perf.2.t
Оптимизация изображений, шрифтов и ресурсов

@@ topic.perf.2.body
[[image-optimization]] — самый быстрый выигрыш: правильный формат, подходящий размер, srcset и атрибуты размеров. [[font-display]]: swap не даёт тексту оставаться невидимым.

Для критических ресурсов — [[preload]], для вероятных — prefetch. Сторонние скрипты (аналитика, чат-виджеты) часто самая тяжёлая часть — если их отложить, INP заметно улучшится.

@@ topic.perf.3.t
Большие списки, виртуализация и частота ввода

@@ topic.perf.3.body
Если сложить в DOM тысячи строк, браузер задохнётся. Решение — [[virtualization]]/[[windowing]]: рендерятся только видимые строки. В DevExtreme DataGrid это даётся режимами virtual scrolling и paging.

Для часто срабатывающих событий вроде поля поиска и прокрутки применяй [[debounce]]/throttle — уменьшается и количество запросов, и количество рендеров.

@@ topic.perf.4.t
Инструменты измерения: Profiler, Performance, память

@@ topic.perf.4.body
С помощью [[profiler]] видно, какой компонент, сколько и почему рендерится — этот шаг обязателен перед оптимизацией. В панели Performance браузера [[flame-chart]] показывает длинные задачи (long task).

[[memory-leak]] в SPA ощущается как утяжеление по мере перехода по страницам; причина обычно в неочищенном слушателе, таймере или подписке. Находится сравнением снимков памяти.

@@ topic.tool.0.t
Vite, бандлер и dev-сервер

@@ topic.tool.0.body
[[vite]] во время разработки использует ESM и мгновенно показывает изменения через [[hmr]]; production-сборку выполняет [[bundler]] (Rollup).

Знай, что поведение в dev и production различается — некоторые вещи, работающие в dev, ломаются при сборке. Поэтому запускать сборку локально хотя бы раз должно войти в привычку.

@@ topic.tool.1.t
ESLint, Prettier и соглашения о коде

@@ topic.tool.1.body
[[eslint]] находит ошибки и плохие шаблоны, [[prettier]] автоматизирует форматирование — это две разные зоны ответственности. Для TypeScript добавляются правила typescript-eslint.

Если [[lint-rule]] мешает, прежде чем его отключать, прочитай, зачем оно существует, — особенно react-hooks/exhaustive-deps. Правила — это договорённость команды; они хранятся в репозитории, а не в редакторе.

@@ topic.tool.2.t
npm/pnpm, package.json и lock-файл

@@ topic.tool.2.body
[[npm]] или [[pnpm]] управляет зависимостями. [[lock-file]] фиксирует точные версии и обязательно коммитится в репозиторий — большая часть проблем «у меня работает» заканчивается на этом.

Разберись в обозначениях [[semver]]: ^ разрешает минорные обновления. В CI используй npm ci — он устанавливает зависимости строго по lock-файлу. Правильно разделяй dependencies и devDependencies.

@@ topic.tool.3.t
Монорепозиторий, workspace и конфигурация окружений

@@ topic.tool.3.body
[[monorepo]] хранит несколько приложений и общие пакеты (UI-kit, типы, утилиты) в одном репозитории; [[workspace]] связывает их между собой. Turborepo/Nx экономят время за счёт кэша сборки.

Правило для управления [[env-variable]]: в репозитории должен быть .env.example, но не реальные значения. Различия между окружениями (dev/test/prod) решай конфигурацией, а не условиями в коде.

@@ topic.tool.4.t
Отладка, source map и настройка редактора

@@ topic.tool.4.body
[[source-map]] связывает минифицированный production-код с исходными строками — это обязательно для мониторинга ошибок.

Ставить [[breakpoint]] через отладчик VS Code, использовать условные точки останова в [[devtools]] и смотреть дерево компонентов в React DevTools — эта тройка серьёзно ускоряет ежедневную работу.

@@ topic.sec.0.t
XSS и безопасный вывод пользовательского контента

@@ topic.sec.0.body
[[xss]] — выполнение вредоносного скрипта на твоей странице. React по умолчанию экранирует содержимое как текст — основной риск в использовании [[dangerously-set-html]] или innerHTML.

Если нужно показать форматированный текст (rich text), применяй [[sanitization]] (DOMPurify). Проверяй и URL: ссылка со схемой javascript: опасна. Самый сильный дополнительный слой — заголовок [[csp]], который ограничивает разрешённые источники скриптов.

@@ topic.sec.1.t
CSRF, параметры cookie и CSP

@@ topic.sec.1.body
При атаке [[csrf]] запрос отправляется от имени пользователя с его cookie. Защита: параметр [[same-site-cookie]] (Lax/Strict) и CSRF-токен.

Политика [[csp]] блокирует инлайн-скрипты и неизвестные источники; при правильной настройке она резко снижает последствия XSS. Эти заголовки задаются на сервере или в конфигурации хостинга — как фронтенд-разработчик ты должен уметь сказать, что именно нужно.

@@ topic.sec.2.t
Хранение токенов и процесс аутентификации

@@ topic.sec.2.body
Хранить токен в localStorage удобно, но при [[xss]] его можно украсть. Более безопасный вариант — [[http-only-cookie]], потому что JS не может его прочитать.

Содержимое [[jwt]] читается открыто — нельзя принимать решения о правах на фронтенде, полагаясь только на него; скрыть UI — не безопасность, сервер должен проверять каждый запрос. Процесс [[refresh-token]] настрой один раз в центральном interceptor.

@@ topic.sec.3.t
Зависимости и риск цепочки поставок

@@ topic.sec.3.body
Атаки на [[supply-chain]] приходят через пакеты. Прежде чем добавить новый пакет, посмотри: насколько он популярен, поддерживается ли, какой у него размер, действительно ли он нужен.

[[npm-audit]] показывает известные уязвимости, а [[dependabot]]/Renovate автоматически открывают PR с обновлениями. Lock-файл и npm ci в CI предотвращают неожиданную смену версий.
