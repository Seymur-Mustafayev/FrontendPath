@@ deep.async.0
Асинхронный код — повседневная реальность фронтенда: каждый экран ждёт хотя бы один запрос. [[promise]] и [[async-await]] — стандартный способ управлять этим ожиданием, но настоящий навык — правильно обрабатывать ошибки и параллельность.

## Три состояния Promise

pending → fulfilled или rejected. Состояние меняется один раз и не возвращается назад. Используется через цепочку `.then/.catch/.finally` или синтаксис `async/await` — второй вариант выигрывает в читаемости.

```js
async function loadOrder(id){
  try{
    const res = await fetch(`/api/orders/${id}`);
    if(!res.ok) throw new ApiError(res.status, 'Не удалось загрузить заказ');
    return await res.json();
  } catch(err){
    report(err);          // лог / мониторинг
    throw err;            // передать наверх — пусть решает UI
  } finally{
    setLoading(false);    // срабатывает в обоих случаях
  }
}
```

## Проблема проглатывания ошибок

Самый вредный шаблон — пустой блок `catch`: ошибка скрыта, пользователь смотрит на пустой экран, в логах ничего нет. Правило: либо обработай ошибку (покажи пользователю сообщение), либо передай её выше. Держи блок [[try-catch]] настолько узким, чтобы он охватывал одну вещь: try, обёрнутый вокруг всей функции, скрывает, какой шаг сломался.

## Параллельность

Самая частая ошибка производительности — последовательно ждать независимые запросы:

```js
// НЕПРАВИЛЬНО — 300ms + 250ms = 550ms
const user = await getUser();
const settings = await getSettings();

// ПРАВИЛЬНО — около 300ms
const [user, settings] = await Promise.all([getUser(), getSettings()]);
```

[[promise-all]] отклоняется сразу при первой ошибке. Если частичный результат тоже полезен, используется `Promise.allSettled`:

```js
const results = await Promise.allSettled([getStock(), getPrices(), getPromos()]);
const ok = results.filter(r => r.status === 'fulfilled').map(r => r.value);
```

`Promise.race` берёт первый завершившийся — классический способ сделать таймаут. `Promise.any` ждёт первый УСПЕШНЫЙ результат.

## await внутри цикла

`await` внутри `for...of` означает последовательное выполнение — иногда намеренно (чтобы не нагружать сервер), иногда по ошибке. Если нужно параллельное выполнение, используют `map` + `Promise.all`. Если запросов сотни, выпускать их все одновременно тоже неправильно — применяют ограниченную параллельность (батчи).

## Забытый Promise

Async-функция, вызванная без `await`, работает молча, а её ошибка попадает в `unhandledrejection`. Полезно ловить это на глобальном уровне:

```js
window.addEventListener('unhandledrejection', e => report(e.reason));
```

@@ deep.async.1
[[fetch]] — стандартный сетевой API браузера, и выглядит он просто, но для кода продакшен-уровня вокруг него нужно несколько слоёв: проверка статуса, отмена, таймаут, повторные попытки и единый формат ошибок.

## Первая ловушка: fetch не выбрасывает ошибку

Ответ 404 или 500 для fetch — успешный запрос: сеть сработала. Ошибка выбрасывается только при проблеме на уровне сети (нет соединения, блокировка CORS).

```js
const res = await fetch(url);
if (!res.ok) {            // БЕЗ ЭТОЙ СТРОКИ ошибки проходят молча
  const body = await res.json().catch(() => null);
  throw new ApiError(res.status, body?.message ?? res.statusText);
}
```

## Отмена

[[abort-controller]] останавливает выполняющийся запрос. Два основных сценария: размонтирование компонента и обновление поискового запроса. Без второго возникает состояние гонки — поздно пришедший старый ответ перезаписывает новый результат.

```js
useEffect(() => {
  const ac = new AbortController();
  fetch(`/api/search?q=${q}`, { signal: ac.signal })
    .then(r => r.json())
    .then(setResults)
    .catch(err => { if (err.name !== 'AbortError') setError(err); });
  return () => ac.abort();
}, [q]);
```

## Таймаут

У fetch нет таймаута по умолчанию — запрос может висеть минутами. Современное решение:

```js
const res = await fetch(url, { signal: AbortSignal.timeout(10000) });
// чтобы объединить несколько сигналов: AbortSignal.any([ac.signal, AbortSignal.timeout(10000)])
```

## Повторные попытки

[[retry]] имеет смысл только в определённых случаях: сетевая ошибка, 502/503/504 и 429. 400 и 401 повторять не нужно — результат не изменится. Нарастающая задержка (exponential backoff) снижает нагрузку на сервер:

```js
async function withRetry(fn, tries = 3){
  for (let i = 0; i < tries; i++){
    try { return await fn(); }
    catch (e){
      if (i === tries - 1 || !isRetriable(e)) throw e;
      await new Promise(r => setTimeout(r, 2 ** i * 300));
    }
  }
}
```

## Единый слой API

Вместо того чтобы писать fetch в каждом компоненте, держат одну обёртку: базовый URL, заголовки, токен, преобразование ошибок и обработка JSON находятся в одном месте. Когда этот слой меняется (например, способ аутентификации), меняется один файл.

```js
export async function api(path, options = {}){
  const res = await fetch(BASE + path, {
    ...options,
    headers: { 'Content-Type': 'application/json', ...options.headers },
    credentials: 'include'
  });
  if (!res.ok) throw await toApiError(res);
  return res.status === 204 ? null : res.json();
}
```

> В реальном проекте поверх этого слоя ставят [[tanstack-query]]: кэширование, повторы, фоновое обновление и отмена идут из коробки, и кода, который пишешь ты, становится заметно меньше.

## Разница между формой ответа и моделью UI

Передавать модель бэкенда прямо в компонент — короткий путь, но каждое переименование поля заставляет трогать десятки файлов. Функция-адаптер разрывает эту связь и заодно держит в одном месте преобразования дат, чисел и enum.

```js
const toOrder = (d) => ({
  id: d.order_id,
  createdAt: new Date(d.created_at),   // строка ISO → Date
  total: Number(d.total_amount),
  status: STATUS_MAP[d.status] ?? 'unknown'
});
```

## Виды пагинации

У [[pagination]] две модели, и поведение UI у них разное:

```
offset:  GET /orders?page=3&size=20     → общее количество известно, показываются номера страниц
cursor:  GET /orders?after=abc&limit=20 → устойчиво для бесконечной прокрутки, общего количества часто нет
```

В модели offset при добавлении нового элемента строки сдвигаются, и пользователь может увидеть одну и ту же строку дважды — для живых списков предпочтителен cursor.

## Фильтры, сортировка и URL

Хранить фильтры в состоянии компонента кажется простым, но при перезагрузке страницы они теряются, а ссылкой нельзя поделиться. Правильная модель: фильтры в URL ([[url-state]]), и ключ запроса строится из тех же значений.

## Формат ошибок

Хороший API возвращает единую структуру ошибки. На фронтенде её нужно обработать в одном месте и превратить в форму, понятную UI:

```js
{ 'code': 'VALIDATION_FAILED',
  'message': 'В форме есть ошибки',
  'fields': { 'email': 'Этот адрес уже зарегистрирован' } }
```

Передача ошибок полей в библиотеку форм ([[react-hook-form]] `setError`) серьёзно улучшает пользовательский опыт.

## Граничные случаи — часть дизайна экрана

Для каждого экрана со списком нужно спланировать пять состояний: загрузка, пусто (данных никогда не было), пустой результат фильтра, ошибка, частичная ошибка. Добавлять их потом всегда дороже.

## Отличие GraphQL

Если в проекте вместо [[rest]] используется GraphQL, принципы меняются: один endpoint, запрос определяет клиент, проблема over-fetching решена, но кэширование и обработка ошибок строятся иначе (Apollo, urql). Знания REST всё равно нужны, потому что слой HTTP остаётся тем же.

## Что такое токен и чем он не является

[[jwt]] состоит из трёх частей: header, payload, подпись. Payload закодирован в base64 — но не зашифрован. То есть кто угодно может прочитать значения `userId`, `role`, `exp` внутри токена. Отсюда два вывода: (1) чувствительные данные в токен не кладут, (2) решение о правах нельзя принимать на фронтенде, глядя на токен: спрятать кнопку в UI — не мера безопасности, а просто удобство. Сервер проверяет заново при каждом запросе.

## Где хранить

```
localStorage   → JS может прочитать → при XSS токен будет украден
sessionStorage → тот же риск, просто очищается при закрытии вкладки
в памяти (RAM) → теряется при перезагрузке страницы, нужен процесс обновления
HttpOnly cookie→ JS не может прочитать → самый устойчивый к XSS вариант
```

При выборе [[http-only-cookie]] появляется риск CSRF — решение: `SameSite=Lax/Strict` и при необходимости CSRF-токен ([[same-site-cookie]]).

## Процесс обновления

Access token живёт недолго (5–15 минут), а [[refresh-token]] — долго и защищён лучше. Процесс:

```
1. Запрос возвращает 401
2. Interceptor отправляет запрос на обновление
3. Получается новый access token
4. Исходный запрос повторяется
```

Здесь есть классический баг: если пять запросов одновременно получат 401, уйдут пять запросов на обновление, и некоторые серверы сочтут второе обновление недействительным. Решение — хранить единственный «летящий» промис обновления:

```js
let refreshing = null;
function refresh(){
  refreshing ??= api('/auth/refresh').finally(() => { refreshing = null; });
  return refreshing;
}
```

## OAuth и корпоративная среда

Вход через [[oauth]] 2.0 / OpenID Connect (Microsoft Entra ID, Google) — стандарт корпоративных систем. Современный правильный процесс — Authorization Code с PKCE; implicit flow устарел и использоваться не должен. Фронтенд обычно использует библиотеку вроде MSAL или oidc-client — писать этот процесс вручную не рекомендуется.

## Выход и очистка состояния

При выходе удалить токен недостаточно: закэшированные серверные данные тоже нужно очистить, иначе следующий пользователь может увидеть данные предыдущего.

```js
await api('/auth/logout', { method: 'POST' });
queryClient.clear();          // кэш TanStack Query
navigate('/login', { replace: true });
```

## Защита маршрутов

Для защищённых маршрутов используют компонент-обёртку, но помни: это лишь слой UI. Каждый API-запрос заново проверяется на сервере — защита на фронтенде нужна для удобства пользователя.

@@ deep.async.4
[[cors]] — механизм, с которым фронтенд-разработчики сталкиваются чаще всего и который чаще всего понимают неправильно. Ключ к его пониманию: CORS — не ограничение, а контролируемое исключение из политики [[same-origin]].

## Что такое same-origin

Origin состоит из трёх частей: протокол + хост + порт. Если хотя бы одна отличается, origin другой:

```
https://app.example.com        ← база
http://app.example.com         ← другой (протокол)
https://api.example.com        ← другой (хост)
https://app.example.com:8443   ← другой (порт)
```

Этой политикой браузер защищает пользователя: вредоносный сайт не должен иметь возможности отправить запрос с твоей банковской сессией и прочитать ответ.

## Важный нюанс

Запрос на самом деле ДОХОДИТ до сервера, и сервер его обрабатывает. Браузер просто не отдаёт ответ JavaScript. Поэтому мысль «получил ошибку CORS, значит, запрос не ушёл» неверна — статус запроса виден в панели Network.

## Простые запросы и preflight

Простые запросы (GET, POST + ограниченный Content-Type) уходят сразу. Когда выходишь за эти рамки, браузер сначала отправляет [[preflight]]-запрос OPTIONS:

```
OPTIONS /api/orders
Origin: https://app.example.com
Access-Control-Request-Method: PATCH
Access-Control-Request-Headers: authorization, content-type

--- ответ сервера ---
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PATCH, DELETE
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Max-Age: 600          ← результат preflight кэшируется
```

Preflight означает дополнительный круг «туда-обратно» для каждого запроса; через `Max-Age` его частоту уменьшают.

## Запросы с cookie

Чтобы отправлять cookie, одновременно должны выполняться два условия:

```js
fetch(url, { credentials: 'include' });
// и на стороне сервера:
// Access-Control-Allow-Credentials: true
// Access-Control-Allow-Origin: https://app.example.com   ← НЕ МОЖЕТ быть *
```

## Где решается проблема

Проблема CORS не решается в коде фронтенда. Варианты: (1) правильные заголовки на сервере, (2) обратный прокси, чтобы API оказался под тем же origin (путь `/api`), (3) прокси Vite в dev-среде — только для разработки:

```js
// vite.config.ts
server: { proxy: { '/api': { target: 'https://api.example.com', changeOrigin: true } } }
```

Главная причина конфигураций, которые работают в dev и ломаются в продакшене, — забытый прокси.

@@ deep.async.5
Интерфейсы с живым обновлением — статус заказа, остатки, уведомления, чат — строятся тремя разными техниками. Выбор делается по требованию; брать самый мощный вариант не всегда правильно, потому что каждый приносит свою сложность.

## Сравнение трёх вариантов

```
Polling    : просто, работает с любым бэкендом, задержка равна интервалу, создаёт лишний трафик
SSE        : одно направление от сервера к клиенту, поверх HTTP, есть автоматическое переподключение
WebSocket  : двусторонний, минимальная задержка, требует отдельной инфраструктуры и управления состоянием
```

## Polling

Для [[polling]] в TanStack Query есть готовая поддержка:

```js
useQuery({
  queryKey: ['order', id],
  queryFn: () => api(`/orders/${id}`),
  refetchInterval: (query) => query.state.data?.status === 'DONE' ? false : 5000
});
```

Внимание: когда вкладка в фоне, интервал нужно останавливать (`refetchIntervalInBackground: false`), иначе батарея пользователя и ресурсы сервера тратятся впустую.

## Server-Sent Events

[[sse]] — идеальный выбор для потока уведомлений и статусов: просто и совместимо с HTTP-инфраструктурой:

```js
useEffect(() => {
  const es = new EventSource('/api/stream', { withCredentials: true });
  es.addEventListener('order-updated', (e) => {
    const data = JSON.parse(e.data);
    queryClient.setQueryData(['order', data.id], data);
  });
  es.onerror = () => { /* браузер переподключится сам */ };
  return () => es.close();
}, []);
```

## WebSocket

[[websocket]] нужен для двусторонних сценариев: чат, совместная работа, живое редактирование. В реальном проекте три вещи нужно спланировать заранее: переподключение (с нарастающим интервалом), механизм heartbeat/ping и восстановление сообщений, потерянных, пока соединение было разорвано.

```js
useEffect(() => {
  const ws = new WebSocket(url);
  ws.onmessage = (e) => applyEvent(JSON.parse(e.data));
  ws.onclose = () => { reconnectTimer = setTimeout(connect, backoff()); };
  return () => { ws.close(); clearTimeout(reconnectTimer); };
}, [url]);
```

## Объединение данных реального времени с кэшем

Самая чистая архитектура такова: канал реального времени не отдаёт данные прямо в компонент, а обновляет кэш ([[cache-invalidation]] или `setQueryData`). Тогда компоненты не меняются, а источник данных остаётся единственным.

## Когда не использовать

Если данные меняются реже раза в минуту, поднимать WebSocket — неоправданная сложность; достаточно простого polling или кнопки «Обновить» у пользователя. Цена real-time — не код, а работа над устойчивостью и мониторингом.
