@@ deep.tool.0
Инструмент сборки превращает твой код в форму, понятную браузеру, и определяет ежедневную скорость разработки. [[vite]] сегодня — выбор по умолчанию в новых проектах.

## Почему Vite быстрый

В режиме разработки Vite не собирает бандл: он использует встроенную поддержку ESM в браузере и мгновенно преобразует только запрошенный модуль. А зависимости заранее подготавливает через esbuild. В результате dev-сервер стартует мгновенно и не замедляется по мере роста проекта.

Production-сборка выполняется через Rollup — там происходят полная оптимизация, [[tree-shaking]] и разбиение на чанки.

## Разница между dev и production

Эта разница важна: код, работающий в dev, может сломаться при сборке. Причины обычно — имена файлов, различающиеся только регистром букв (важно на Linux-сервере), переменные окружения, существующие только в dev, и то, что при сборке не выполняется проверка типов. Поэтому регулярно запускать `npm run build` локально — полезная привычка.

## Пример конфигурации

```ts
export default defineConfig({
  plugins: [react()],
  resolve: { alias: { '@': path.resolve(__dirname, './src') } },
  server: {
    port: 3000,
    proxy: { '/api': { target: 'https://api.local', changeOrigin: true } }
  },
  build: {
    sourcemap: true,                 // делает ошибки продакшена читаемыми
    rollupOptions: {
      output: { manualChunks: { vendor: ['react', 'react-dom'] } }
    }
  }
});
```

## HMR

[[hmr]] заменяет изменённый модуль без перезагрузки страницы, и состояние компонента сохраняется. Иногда HMR ломается (например, если файл экспортирует и компонент, и константу) — тогда Vite делает полную перезагрузку и пишет причину в консоли.

## Альтернативы

webpack всё ещё присутствует в больших корпоративных проектах и силён широкой экосистемой плагинов, но его конфигурация тяжёлая. Next.js приносит собственную систему сборки (Turbopack), так что там этот выбор не в твоих руках. Если публикуешь библиотеку, используют `tsup` или library-режим Vite.

## Практический совет

Трогай конфигурацию сборки только по необходимости. Самый вредный шаблон — скопированные из интернета плагины и параметры оптимизации, о которых неизвестно, что они делают: они создают скрытые проблемы, которые потом усложняют диагностику.

## Роли

[[eslint]] смотрит на СМЫСЛ кода: потенциальные ошибки, опасные шаблоны, нарушения правил. [[prettier]] смотрит только на ФОРМАТ: длину строк, отступы, кавычки. Их используют вместе; правила форматирования убираются из ESLint, чтобы не было противоречий.

## Конфигурация

```js
// eslint.config.js (flat config)
export default [
  js.configs.recommended,
  ...tseslint.configs.recommendedTypeChecked,
  reactHooks.configs['recommended-latest'],
  {
    rules: {
      'react-hooks/exhaustive-deps': 'warn',
      '@typescript-eslint/no-floating-promises': 'error',
      '@typescript-eslint/no-unnecessary-condition': 'warn',
      'no-console': ['warn', { allow: ['warn', 'error'] }]
    }
  }
];
```

`no-floating-promises` особенно ценно: ловит async-вызовы без `await` — главный источник тихих ошибок.

## Отключение правила

Если [[lint-rule]] мешает, сначала прочитай, зачем оно существует. Отключить предупреждение `react-hooks/exhaustive-deps` — значит спрятать баг, а не решить его. Если исключение действительно обосновано, пиши его вместе с причиной:

```ts
// eslint-disable-next-line react-hooks/exhaustive-deps -- должен работать только при монтировании, не пересоздаваться даже при смене id
```

## Prettier и команда

Споры о форматировании — потеря времени. `.prettierrc` кладут в репозиторий, в редакторе включают «format on save», и тема закрыта. Добавляя Prettier в существующий проект, отформатируй все файлы одним коммитом и добавь этот коммит в файл `.git-blame-ignore-revs`, чтобы не испортить результаты `git blame`.

## Связь с CI

Проверки, работающей в редакторе, недостаточно — у каждого редактор может быть настроен по-своему. Правила должны быть обязательным шагом в конвейере [[ci]]:

```json
{ 'scripts': { 'lint': 'eslint .', 'format:check': 'prettier --check .' } }
```

## Другие полезные инструменты

`eslint-plugin-jsx-a11y` ловит ошибки доступности прямо во время написания. `knip` или `ts-prune` находят неиспользуемые экспорты и файлы — незаменимо для уборки в больших проектах. Biome — новая альтернатива, объединяющая функциональность ESLint + Prettier в одном, значительно более быстром инструменте.

## Основные поля package.json

```json
{
  'scripts': {
    'dev': 'vite',
    'build': 'tsc --noEmit && vite build',
    'test': 'vitest run',
    'lint': 'eslint .'
  },
  'dependencies':    { 'react': '^18.3.1' },
  'devDependencies': { 'vite': '^5.4.0', 'vitest': '^2.0.0' },
  'engines': { 'node': '>=20' }
}
```

Скрипты [[npm]] — договор команды: новый разработчик должен иметь возможность набрать `npm i && npm run dev` и начать работать. А поле `engines` уменьшает проблемы из-за разницы версий Node.

## Диапазоны версий

```
^1.4.2  → последняя внутри 1.x.x (обновляются minor и patch)
~1.4.2  → обновляется только patch
1.4.2   → точная версия
```

Обозначения [[semver]] означают, что один и тот же `package.json` в разное время может установить разные версии. Именно поэтому существует [[lock-file]], и он обязательно коммитится в репозиторий.

## Разница между install и ci

```bash
npm install   # МОЖЕТ ОБНОВИТЬ lock-файл
npm ci        # строго следует lock-файлу, собирает node_modules с нуля
```

В конвейере всегда используется `npm ci` — это условие воспроизводимой сборки.

## dependencies и devDependencies

Код, уходящий в браузер, — `dependencies`, а то, что нужно только для разработки и сборки, — `devDependencies`. Во фронтенд-приложениях эта разница не влияет напрямую на бандл (бандлер берёт только импортированное), но важна для аудита, проверки лицензий и размера Docker-образа.

## pnpm

[[pnpm]] хранит пакеты в глобальном хранилище и даёт проекту жёсткие ссылки: экономия диска, более быстрая установка и строгая изоляция зависимостей. Особенно ощутимо его преимущество в монорепозиториях. Команде нужно выбрать один менеджер пакетов — репозиторий с двумя разными lock-файлами — источник проблем.

## Выбор пакета

Четыре вопроса перед добавлением новой зависимости: смогу ли я сам написать эту функцию в 20 строк, активно ли поддерживается пакет, какой у него размер (bundlephobia) и какие транзитивные зависимости он тянет? Каждый пакет — обязательство, которое в будущем нужно будет обновлять, проверять и мигрировать.

## Что такое монорепозиторий

[[monorepo]] — хранение нескольких пакетов в одном репозитории. Преимущества: общий код легко разделять, изменение тестируется вместе со всеми потребителями, сквозное изменение можно сделать одним PR.

```
apps/
  web/            → клиентское приложение
  admin/          → внутренняя панель
packages/
  ui/             → общие компоненты
  api-client/     → слой API и типы
  config/         → базовые конфигурации eslint и tsconfig
```

Механизм [[workspace]] (npm workspaces, pnpm workspaces) связывает пакеты друг с другом — пакет `@acme/ui` используется прямо из исходников, публиковать его не нужно.

## Инструменты

Turborepo и Nx выполняют задачи в виде графа и кэшируют их: результат build/test неизменённого пакета берётся из кэша. В большом репозитории это сокращает время конвейера в разы.

## Когда не нужен

Для одного приложения и команды из двух человек монорепозиторий — лишняя сложность. Для его внедрения нужна реальная причина: общий код, несколько приложений или релизы, требующие координации.

## Конфигурация окружений

```
.env.example   → в репозитории, образец без значений
.env.local     → локально, в gitignore
CI/CD secrets  → хранит платформа
```

Правила: секреты никогда не попадают в репозиторий; разница между окружениями не пишется в коде как `if (isProd)`, а решается конфигурацией; переменные проверяются при старте, чтобы неправильная конфигурация всплыла рано, а не поздно.

```ts
const env = z.object({
  VITE_API_URL: z.string().url(),
  VITE_SENTRY_DSN: z.string().optional()
}).parse(import.meta.env);
```

## Документ для онбординга

README хорошего репозитория отвечает на три вопроса: как запустить, как протестировать, как деплоится. Эта одна страница экономит новому члену команды часы в первый же день — и её пишут реже всего.

@@ deep.tool.4
Навык отладки — один из факторов, которые сильнее всего влияют на продуктивность разработчика. Главный принцип здесь — систематичность: не делать случайных изменений, а проверять гипотезу.

## Систематический подход

```
1. Воспроизведи         → научись стабильно вызывать проблему
2. Локализуй            → на каком она уровне: сеть? state? рендер? CSS?
3. Сформулируй гипотезу → 'думаю, причина в этом, потому что...'
4. Проверь              → breakpoint, лог, упрощённый пример
5. Исправь и подтверди  → напиши тест, чтобы не повторилось
```

Баг, который нельзя воспроизвести, — самый тяжёлый: в этом случае единственный источник — логи и инструменты мониторинга вроде [[sentry]]. Поэтому мониторинг ошибок не должен оставаться в списке «настроим потом».

## Приёмы с точками останова

Виды [[breakpoint]] экономят много времени в повседневной работе: условная точка останова (`order.id === 1042`), logpoint (запись значения без остановки), DOM breakpoint (остановка при изменении элемента — чтобы найти сторонний код, вмешивающийся в DOM), XHR breakpoint (когда уходит запрос на конкретный URL).

Написать в коде `debugger;` тоже работает, но нужно следить, чтобы это не попало в коммит, — правило линтера это ловит.

## Source map

[[source-map]] связывает минифицированный production-код с исходными строками. Без него трассировка ошибки выглядит как `a.min.js:1:24518` и ничего не говорит.

Правильная практика в продакшене: source map генерируются, но публично не публикуются — они загружаются только в систему мониторинга (Sentry). Так и трассировки читаемы, и исходный код не становится публичным.
