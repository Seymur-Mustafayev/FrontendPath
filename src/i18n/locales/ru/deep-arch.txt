Пока проект маленький, структура не кажется такой уж важной. Но если после 50–60 компонентов для каждой новой функции приходится заходить в пять разных папок, структура уже стала проблемой.

## Две модели

```
ПО ТЕХНОЛОГИЯМ                ПО ФИЧАМ (feature-based)
src/                          src/
  components/                   features/
  hooks/                          orders/
  services/                         components/
  utils/                            hooks/
  types/                            api.ts
                                    types.ts
                                    index.ts
                                  billing/
                                  inventory/
                                shared/
                                  ui/  lib/  hooks/
```

Первая модель работает в маленьком проекте. По мере роста каждое изменение расползается по всем папкам, и границы между модулями исчезают.

В модели [[feature-folder]] всё, что относится к одной предметной области, лежит в одном месте. Новая функция — это одна папка, а удаление функции — удаление одной папки.

## Правила зависимостей

Ценность структуры защищается правилами:

```
features/* → может использовать shared/*
shared/*   → НЕ может использовать features/*
features/orders → НЕ должен напрямую обращаться внутрь features/billing
```

Эти правила можно применять автоматически плагинами ESLint (`eslint-plugin-boundaries`, `import/no-restricted-paths`) — иначе их записывают в документ и забывают.

## Слои

[[layered-architecture]] сохраняется и внутри фичи: UI-компонент → хук (состояние и оркестрация) → слой API/сервисов. Если видишь прямой вызов `fetch` внутри компонента, этот слой нарушен; выделение такого кода упрощает и тестирование, и повторное использование.

## Barrel-файлы

[[barrel-file]] полезен, чтобы определить публичный интерфейс фичи: внешний код должен импортировать только из корня `features/orders`, а не из внутренней структуры. Но index.ts в каждой папке замедляет сборку и создаёт циклические импорты — пользоваться им нужно в меру.

## Именование

Соглашение для имён папок и файлов выбирается один раз и соблюдается. Самое важное — имена должны быть на языке предметной области: `InvoiceRow` намного ценнее, чем `DataItem2`. В голове того, кто читает код, должна складываться бизнес-модель проекта.

## Практическая проверка

## Что такое дизайн-система

[[design-system]] состоит из трёх слоёв: токены (цвет, отступы, типографика, радиусы, тени), компоненты (Button, Input, Modal, Table) и правила (когда какой вариант использовать).

## Свой слой поверх готовой библиотеки

В проекте, использующем DevExtreme, MUI или Ant Design, правильный подход — создать тонкий слой-обёртку:

```tsx
// shared/ui/DataGrid.tsx
export function DataGrid<T>({ columns, ...rest }: Props<T>){
  return (
    <DxDataGrid
      showBorders
      columnAutoWidth
      noDataText='Нет данных'
      {...defaultGridOptions}
      {...rest}
    />
  );
}
```

Польза: стандартные параметры остаются в одном месте, а при смене версии библиотеки или переходе на другую изменение делается в одном файле.

## Headless-компоненты

Подход [[headless-component]] (Radix UI, Headless UI, TanStack Table) даёт логику и доступность, а внешний вид оставляет тебе. В продуктах с особым дизайном это намного эффективнее, чем пытаться перебить стили готовой библиотеки.

## Storybook

[[storybook]] позволяет разрабатывать компоненты в изоляции: все варианты, граничные случаи (длинный текст, пустые данные, ошибка) и разные темы видны в одном месте. Дополнительная польза — живая документация для дизайнера и бэкенд-разработчика, а также возможность визуального регрессионного тестирования.

## Дизайн API

У хорошего компонента предсказуемые props: `variant`, `size`, `disabled`, `onChange`. Добавлять boolean на каждое новое требование (`isCompactWithIconAndBorder`) — признак слабости; в этот момент нужно переходить к композиции.

## Когда не обобщать

Код, используемый в двух местах, ещё не означает общий компонент. Практичное правило — обобщать после третьего повторения: к тому времени реальные требования проясняются, и абстракция получается правильной.

## SOLID в переводе на фронтенд

Из принципов [[solid]] во фронтенде полезнее всего следующие:

Единственная ответственность: если компонент и загружает данные, и форматирует их, и рендерит — его нужно разделить. Это самый применяемый и самый полезный принцип.

Открытость/закрытость: компонент должен подстраиваться под новые требования через props и композицию, а не менять внутренности каждый раз.

Инверсия зависимостей: вместо импорта конкретного API-модуля компонент должен получать функцию через props или контекст — это резко упрощает тестирование.

## Граница DRY

Принцип [[dry]] правильный, но его преждевременное применение вредно. Два похожих куска кода в будущем могут меняться в разных направлениях; если объединить их рано, потом получишь одну функцию, полную условий, обслуживающих оба случая.

> Неправильная абстракция дороже дублирования. Практическое правило: дождись третьего повторения, потом обобщай.

## Рефакторинг

[[refactoring]] — улучшение структуры без изменения поведения. У него два условия: маленькие шаги и рабочее состояние после каждого шага. Рефакторинг без тестов — просто «переписывание», и он несёт риск; поэтому путь Testing идёт раньше этого.

Типичные рефакторинги во фронтенде: разделить большой компонент, вынести логику в кастомный хук, заменить цепочку props композицией, превратить булевы флаги в модель состояния ([[discriminated-union]]).

## Технический долг

[[technical-debt]] сам по себе не плох — осознанно взятый долг даёт скорость. Плох долг, который не зафиксирован и никогда не возвращается. На практике: когда пишешь временное решение, зафиксируй его причину и условие.

```ts
// TODO(#1284): убрать фильтрацию на клиенте, когда появится поддержка фильтров на бэкенде.
// Временное решение: если в списке больше 2000 строк, возникнет проблема производительности.
```

## Читаемость

Код читают намного чаще, чем пишут. Практические признаки: функция делает одну вещь, и её имя об этом говорит; вложенные условия выпрямляются ранним `return`; магические числа превращаются в именованные константы; комментарий объясняет не «что», а «почему».

```ts
// ПЛОХО: почему 3? чьё это решение?
if (retries > 3) ...
// ХОРОШО
const MAX_RETRIES = 3;   // рекомендация платёжного провайдера (см.: #942)
```

## Оценка задач

[[estimation]] — навык, которому можно научиться. Способ: разбей задачу на части меньше 4 часов, отдельно покажи неизвестные части и попроси на них время для исследования. Заранее сообщить о риске всегда лучше, чем объясняться после задержки.

## Язык компромиссов

Объяснение [[trade-off]] — главный показатель уровня middle. Пример структуры ответа: «Я выбрал SSR, потому что эта страница публичная и есть требование SEO. Цена — нагрузка на сервер и более сложный деплой. Альтернативой был SSG, но данные меняются каждый час, поэтому я выбрал ISR с revalidate раз в 15 минут».

## Собеседование по фронтенд-системному дизайну

Ожидаемая последовательность на вопрос по [[system-design]] (например, «спроектируй панель управления заказами»):

```
1. Уточни требования         → кто пользуется, сколько строк, нужен ли real-time
2. Поток данных              → какие эндпоинты, какая стратегия кэша
3. Разбиение на компоненты   → страница, таблица, панель фильтров, панель деталей
4. Решение о состоянии       → разделение server state / URL state / локальное
5. Граничные случаи          → пусто, ошибка, нет прав, слишком много данных
6. Производительность        → виртуализация, code splitting, измерения
7. Доступность и i18n        → клавиатура, экранный диктор, формат дат/валют
8. Стратегия тестирования    → что unit, что интеграция, что E2E
```

## Интернационализация

[[i18n]] шире, чем перевод текста: формат даты и времени, разделители чисел и валют, формы множественного числа, влияние длины текста на раскладку, правила сортировки.

```ts
new Intl.NumberFormat('az-AZ', { style: 'currency', currency: 'AZN' }).format(1234.5);
new Intl.DateTimeFormat('az-AZ', { dateStyle: 'long' }).format(new Date());
new Intl.RelativeTimeFormat('az', { numeric: 'auto' }).format(-2, 'day');
```

Практические правила: не пиши текст в коде жёстко, не строй предложения склеиванием строк (порядок слов в языках разный), держи раскладку готовой к тексту на 30 процентов длиннее и всегда храни даты в UTC, переводя в локальный формат при отображении.

## Мониторинг

Единственный способ знать, что сломалось в продакшене, — измерения. Инструмент вроде [[sentry]] собирает трассировку ошибки, шаги пользователя (breadcrumbs), информацию о браузере и версии.

```ts
Sentry.init({
  dsn: env.SENTRY_DSN,
  release: __APP_VERSION__,           // для сопоставления с source map
  tracesSampleRate: 0.1,
  beforeSend(event){ return scrubPII(event); }   // очистить личные данные
});
```

Загрузка [[source-map]] важна, иначе трассировки не читаются. А следить, чтобы личные данные (e-mail, карта, токен) не попадали в логи, — требование и этическое, и юридическое.

## Feature flag

[[feature-flag]] позволяет задеплоить код и включить функцию позже. Польза: поэтапно открывать рискованный релиз, отключать его при проблеме без отката кода, проводить A/B-тесты, сливать незавершённую работу в main (условие модели [[trunk-based]]).

```tsx
{flags.newOrderFlow ? <OrderWizard /> : <OrderFormLegacy />}
```

Цена: ветвления в кодовой базе. Поэтому у каждого флага должны быть владелец и дата удаления — устаревшие флаги особенно грязный вид технического долга.

## Аналитика и продуктовые метрики
