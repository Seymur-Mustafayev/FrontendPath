@@ deep.state.0
Самое важное решение об управлении состоянием в React-приложениях — не выбор библиотеки, а правильное определение того, кому принадлежат данные. Проекты, которые не делают этого разделения, превращают Redux в менеджер кэша и в итоге пишут сотни строк кода синхронизации.

## Две разные природы

```
CLIENT STATE                       SERVER STATE
существует только в браузере       живёт на сервере, копия — в браузере
ты его владелец                    ты не владелец
не устаревает                      устаревает (его может изменить другой)
меняется синхронно                 приходит асинхронно
пример: открытое окно, вкладка     пример: заказы, остатки, профиль
```

Для [[client-state]] достаточно `useState`, `useReducer`, Context или Zustand. [[server-state]] же — проблема кэша, а у проблем кэша есть свои решения.

## Что значит управлять серверным состоянием вручную

Если одни и те же данные нужны двум компонентам, не должно уходить два запроса; при возврате на страницу должны показываться старые данные с фоновым обновлением; если запрос упал, нужна повторная попытка; при закрытии компонента запрос нужно отменить; после мутации связанные списки должны обновиться. Если написать всё это самому, ты уже написал библиотеку кэширования.

## Таблица решений

```
Тип данных                             Где хранить
-------------------------------------  ------------------------------------
Список/детали с сервера                TanStack Query (или RTK Query / SWR)
Фильтр, страница, поисковый запрос     URL (search params)
Черновик формы                         библиотека форм / локальное состояние
Модальное окно, выбранная строка       локальное состояние
Тема, язык, контекст аутентификации    Context
Общее состояние UI между страницами    Zustand / Redux Toolkit
```

## Практический итог

Когда применяется это разделение, глобальный store обычно сильно уменьшается. Во многих современных проектах Redux вообще не нужен: серверные данные — в Query, фильтры — в URL, остальное — внутри компонентов.

> В системах вроде AIPOS это разделение особенно полезно: быстро устаревающие данные вроде остатков и статуса заказа управляются правилами кэша, а состояние интерфейса хранится локально. Смешение этих двух вещей — главная причина ошибок в отчётах вида «на экране осталась старая цифра».

@@ deep.state.1
[[tanstack-query]] — отраслевой стандарт для серверного состояния. Его нужно понимать не как «библиотеку, заменяющую fetch», а как «асинхронный менеджер кэша»: запрос по-прежнему отправляет твоя функция, а Query управляет результатом.

## Основная структура

```tsx
const { data, isPending, isError, error, refetch } = useQuery({
  queryKey: ['orders', { status, page }],
  queryFn: ({ signal }) => getOrders({ status, page }, signal),
  staleTime: 60_000
});
```

[[query-key]] — идентичность записи в кэше. Как только ключ меняется, Query загружает новые данные — то есть, положив фильтры в ключ, полностью избавляешься от написания useEffect. Поскольку ключ сериализуется, порядок полей в объектах не важен.

Важно передавать параметр `signal` в queryFn: при закрытии компонента или смене ключа запрос отменяется автоматически ([[abort-controller]]).

## staleTime и gcTime

[[stale-time]] — самый неправильно понимаемый параметр:

```
staleTime : сколько данные считаются «свежими». В это время новый запрос НЕ уходит.
gcTime    : сколько неиспользуемый кэш остаётся в памяти (по умолчанию 5 мин).
```

По умолчанию `staleTime: 0`, то есть данные сразу считаются устаревшими и обновляются в фоне при возврате в окно и повторном монтировании компонента. Часто это именно то, что нужно, но для редко меняющихся данных это неоправданный трафик.

```tsx
// каталог, единицы измерения, валюты — меняются редко
staleTime: 30 * 60_000
// остатки, статус заказа — быстро устаревают
staleTime: 5_000
```

## Правильное чтение состояний

```tsx
if (isPending) return <Skeleton />;          // данных ещё никогда не было
if (isError) return <ErrorBox error={error} retry={refetch} />;
return <Table rows={data} refreshing={isFetching} />;  // isFetching: обновление в фоне
```

Разница между `isPending` и `isFetching` важна для UI: в первом случае показывается skeleton, во втором — аккуратный индикатор загрузки поверх старых данных. Это практика «stale-while-revalidate», и интерфейс кажется быстрее.

## Фабрика ключей

Писать ключи строками повсюду — путь к ошибкам. На практике держат фабрику ключей:

```ts
export const orderKeys = {
  all: ['orders'] as const,
  list: (filters: Filters) => [...orderKeys.all, 'list', filters] as const,
  detail: (id: number) => [...orderKeys.all, 'detail', id] as const
};
```

Так `invalidateQueries({ queryKey: orderKeys.all })` одним движением объявляет устаревшими все запросы заказов.

## Другие полезные возможности

`useInfiniteQuery` — для бесконечной прокрутки; `placeholderData: keepPreviousData` — чтобы экран не пустел при переходе между страницами; а `select` — чтобы отдать компоненту только нужную часть, не меняя кэш.

```tsx
useQuery({ queryKey: orderKeys.list(f), queryFn: ..., select: (rows) => rows.filter(r => r.total > 0) });
```

@@ deep.state.2
Чтение данных — половина работы; вторая половина — запись и поддержание кэша в правильном состоянии. Здесь есть две стратегии, и у каждой своя цена.

## Основы мутаций

```tsx
const qc = useQueryClient();

const { mutate, isPending } = useMutation({
  mutationFn: (input: OrderInput) => api('/orders', { method: 'POST', body: JSON.stringify(input) }),
  onSuccess: (created) => {
    qc.invalidateQueries({ queryKey: orderKeys.all });   // [[cache-invalidation]]
    toast.success(`Заказ #${created.id} создан`);
  },
  onError: (e) => toast.error(toMessage(e))
});
```

Стандартный поток для [[mutation]]: отправить → при успехе инвалидировать связанные запросы → сообщить пользователю. В большинстве случаев этого достаточно, и риск ошибок минимален.

## Optimistic update

[[optimistic-update]] обновляет UI, не дожидаясь ответа. Ощущение скорости отличное, но код усложняется, потому что при ошибке нужен [[rollback]].

```tsx
useMutation({
  mutationFn: toggleFavorite,
  onMutate: async (id) => {
    await qc.cancelQueries({ queryKey: orderKeys.detail(id) });   // остановить летящие запросы
    const prev = qc.getQueryData(orderKeys.detail(id));            // резервная копия
    qc.setQueryData(orderKeys.detail(id), (o) => ({ ...o, isFavorite: !o.isFavorite }));
    return { prev, id };
  },
  onError: (_e, _v, ctx) => qc.setQueryData(orderKeys.detail(ctx.id), ctx.prev),  // откатить
  onSettled: (_d, _e, id) => qc.invalidateQueries({ queryKey: orderKeys.detail(id) })
});
```

Шаг `cancelQueries` важен: иначе ответ летящего запроса может перезаписать твоё оптимистичное изменение.

## Когда не делать optimistic

Если операция выполняется редко, если её результат серьёзен с финансовой точки зрения (оплата, подтверждение удаления) или если есть поля, которые вычисляет сервер (скидка, налог, остаток), оптимистичное обновление может показать пользователю неправду. В таких случаях правильнее индикатор ожидания и точный результат.

## Обновление кэша прямо из ответа

Если сервер возвращает полное состояние созданного объекта, дополнительный запрос не нужен:

```tsx
onSuccess: (created) => {
  qc.setQueryData(orderKeys.detail(created.id), created);
  qc.setQueryData(orderKeys.list(filters), (old) => old ? [created, ...old] : old);
}
```

Этот приём сокращает трафик, но если есть поля, вычисляемые на сервере, результат в кэше может остаться неполным — поэтому `invalidateQueries` часто безопаснее.

## Защита от повторной отправки

Блокировать кнопку в состоянии `isPending` — минимальная мера. Для серьёзных операций используют согласованный с сервером [[idempotent]] ключ — когда сеть обрывается и запрос повторяется, второй заказ не создаётся.

@@ deep.state.3
После отделения серверных данных на глобальное клиентское состояние обычно остаётся немного. Этот раздел охватывает выбор и правила правильного использования для этой оставшейся части.

## Zustand

[[zustand]] создаёт store с минимальным API и не требует Provider:

```ts
import { create } from 'zustand';

type UiState = {
  sidebarOpen: boolean;
  selectedIds: number[];
  toggleSidebar: () => void;
  select: (id: number) => void;
};

export const useUi = create<UiState>((set) => ({
  sidebarOpen: true,
  selectedIds: [],
  toggleSidebar: () => set(s => ({ sidebarOpen: !s.sidebarOpen })),
  select: (id) => set(s => ({ selectedIds: [...s.selectedIds, id] }))
}));
```

## Селектор — ключ к производительности

Брать весь store — значит получать рендер на каждое изменение. Через [[selector]] подписываешься только на нужную часть:

```tsx
// НЕПРАВИЛЬНО — рендер при любом изменении
const { sidebarOpen } = useUi();

// ПРАВИЛЬНО
const sidebarOpen = useUi(s => s.sidebarOpen);
const toggle = useUi(s => s.toggleSidebar);   // ссылка на функцию стабильна
```

Если селектор возвращает объект, нужно поверхностное сравнение (`useShallow`), иначе каждый раз создаётся новый объект, и подписка теряет смысл — всё то же правило [[referential-equality]].

## Redux Toolkit

[[redux-toolkit]] в больших командах даёт порядок, строгую структуру и мощные DevTools (путешествие во времени, след каждого действия):

```ts
const uiSlice = createSlice({
  name: 'ui',
  initialState: { sidebarOpen: true },
  reducers: {
    toggleSidebar(state){ state.sidebarOpen = !state.sidebarOpen; }   // выглядит как мутация благодаря Immer
  }
});
```

RTK Query — решение для серверного состояния внутри экосистемы Redux: если проект и так построен на Redux, логично выбрать его вместо TanStack Query.

## Критерии выбора

```
Малое/среднее приложение, мало глобального состояния → Context + useState или Zustand
Большая команда, строгие требования аудита            → Redux Toolkit
Сложные переходы состояний                            → XState (state machine)
Серверные данные                                      → TanStack Query / RTK Query
```

## Частые ошибки

Складывать в store всё подряд (состояние модальных окон, значения input) — значит сделать код неотслеживаемым. Хранить в store производное значение — значит создать долг синхронизации; правильнее вычислять его внутри селектора. Наконец, читать store вне компонента (например, в слое API) можно (`useUi.getState()`), но злоупотребление этой возможностью скрывает поток кода.

@@ deep.state.4
Факт, который фронтенд-разработчики часто упускают из виду: адресная строка браузера — уже хранилище состояния, причём таким состоянием можно делиться, по нему можно перемещаться кнопкой «назад», и оно переживает перезагрузку страницы.

## Что относится к URL

Всё, о чём пользователь скажет «мне нужно иметь возможность отправить этот экран другому»: фильтры, номер страницы, поисковый запрос, сортировка, выбранная вкладка, открытая панель деталей. Когда их хранит [[url-state]], решаются сразу три проблемы: шеринг, история навигации и перезагрузка страницы.

## Чтение и запись

```tsx
// Next.js App Router
const searchParams = useSearchParams();
const router = useRouter();
const pathname = usePathname();

const status = searchParams.get('status') ?? 'all';
const page = Number(searchParams.get('page') ?? 1);

function setParam(key: string, value: string){
  const params = new URLSearchParams(searchParams);
  value ? params.set(key, value) : params.delete(key);
  params.set('page', '1');                 // при смене фильтра сбросить страницу
  router.replace(`${pathname}?${params}`, { scroll: false });
}
```

Выбор между `push` и `replace` важен: `push` на каждый символ засоряет историю и ломает кнопку «назад». Изменения фильтров обычно делают через `replace`, переходы по страницам — через `push`.

## Объединение с Query

Когда параметры URL напрямую передаются в [[query-key]], система становится однонаправленной и предсказуемой:

```tsx
const filters = { status, page, q: debouncedQ };
const { data } = useQuery({ queryKey: orderKeys.list(filters), queryFn: () => getOrders(filters) });
```

Теперь единый источник истины — URL: пользователь открывает ссылку и видит тот же экран.

## Типобезопасность

Всё, что приходит из URL, — строки, и пользователь может изменить их вручную. Поэтому параметры нужно проверять:

```ts
const Params = z.object({
  status: z.enum(['all','new','paid']).catch('all'),
  page: z.coerce.number().int().min(1).catch(1)
});
const { status, page } = Params.parse(Object.fromEntries(searchParams));
```

Библиотеки вроде `nuqs` предлагают это в готовом виде — как типизированные хуки.

## Когда не писать в URL

Чувствительные данные (токены, личные идентификаторы), очень быстро меняющиеся значения (каждое нажатие клавиши — сначала сделай debounce) и временное состояние UI, относящееся только к одному пользователю. URL виден и в истории браузера, и в логах сервера, и в заголовке referrer.
