@@ sec.ydkjs-scope.ch2.marbles.heading
Шарики, корзины и пузыри

@@ sec.ydkjs-scope.ch2.marbles.note
Самая важная фраза: цвет шарика определяется местом, где он **объявлен**, а не местом, где он используется.

Видимость работает в одну сторону: изнутри можно смотреть наружу, а снаружи внутрь — нельзя.

```js
function outer() {
  const a = 1;          // СИНИЙ
  if (true) {
    const b = 2;        // ЗЕЛЁНЫЙ
    console.log(a, b);  // ЗЕЛЁНОЕ выражение видит и СИНИЙ, и ЗЕЛЁНЫЙ
  }
  console.log(b);       // ReferenceError — СИНИЙ не видит ЗЕЛЁНЫЙ
}
```

В React обработчик, написанный внутри компонента, видит state и props компонента — потому что он написан внутри «корзины» этого компонента.

@@ sec.ydkjs-scope.ch2.conversation.heading
Разговор друзей

@@ sec.ydkjs-scope.ch2.conversation.note
Смысл этого раздела: одна строка — это две работы: **объявление** (компиляция) и **присваивание** (выполнение). В этом и весь «секрет» hoisting.

```js
console.log(x);   // undefined — переменная уже есть, значение ещё не записано
var x = 5;
```

Ответ на собеседовании: «Объявление var поднимается в начало scope и инициализируется undefined, а присваивание остаётся на своём месте».

@@ sec.ydkjs-scope.ch2.nested-scope.heading
Вложенные области видимости

@@ sec.ydkjs-scope.ch2.nested-scope.note
«Каждый scope получает свой экземпляр при каждом выполнении» — запомни эту фразу. Если вызвать функцию 3 раза, создаются 3 отдельных набора её локальных переменных.

Состояние в начале scope в зависимости от вида объявления:

```text
function f() {}  → сразу инициализируется функцией
var x            → инициализируется undefined
let / const      → не инициализирована (TDZ) — до строки объявления
```

Эта таблица отвечает на 90% вопросов про [[tdz]] и [[hoisting]].

@@ sec.ydkjs-scope.ch2.lookup-failures.heading
Неудачный поиск

@@ sec.ydkjs-scope.ch2.lookup-failures.note
Частый вопрос на собеседовании: «Чем `undefined` отличается от `not defined`?»

- `undefined` — переменная **существует**, просто у неё нет значения.
- `not defined` — переменная **нигде не объявлена** → `ReferenceError`.

Практическое замечание: ES-модули (`import`/`export`) и тела `class` автоматически работают в строгом режиме. Код, который ты пишешь в проекте на Vite/React, уже является ES-модулем, так что там проблема случайной глобальной переменной проявится как `ReferenceError`.

@@ sec.ydkjs-scope.ch2.building.heading
Строим на метафорах

@@ sec.ydkjs-scope.ch2.building.note
Упражнение: для каждой ссылки на переменную в коде ниже скажи, на каком этаже «здания» она находится.

```js
const theme = 'dark';
function App() {
  const user = 'Aysel';
  function Header() {
    return `${user} / ${theme}`;
  }
  return Header();
}
```

`user` → на 1 этаж выше (App), `theme` → на 2 этажа выше (глобальный). Эта привычка нужна и для того, чтобы читать, откуда приходят props в React.

@@ sec.ydkjs-scope.ch2.intro.b0
В главе 1 мы разобрали, как scope определяется во время компиляции кода; эта модель называется [[lexical-scope]]. Термин «lexical» указывает на первый этап компиляции (lexing/парсинг).

@@ sec.ydkjs-scope.ch2.intro.b1
Чтобы правильно *рассуждать* о наших программах, важно иметь прочный концептуальный фундамент того, как работает scope. Если полагаться на догадки и интуицию, иногда мы случайно получим правильный ответ, но во многих других случаях сильно ошибёмся. Это не рецепт успеха.

@@ sec.ydkjs-scope.ch2.intro.b2
Как когда-то на уроках математики в начальной школе, правильного ответа недостаточно, если не показать верные шаги, которые к нему привели! Нам нужно построить точные и полезные ментальные модели как фундамент для дальнейшего движения.

@@ sec.ydkjs-scope.ch2.intro.b3
В этой главе scope будет проиллюстрирован с помощью нескольких метафор. Цель — *думать* о том, как JS-движок обрабатывает твою программу, так, чтобы это было ближе к тому, как движок работает на самом деле.

@@ sec.ydkjs-scope.ch2.marbles.b0
Одна из метафор, которую я считаю эффективной для понимания scope, — сортировка цветных шариков по вёдрам соответствующего цвета.

@@ sec.ydkjs-scope.ch2.marbles.b1
Представь, что ты наткнулся на кучу шариков и заметил, что все они красные, синие или зелёные. Давай рассортируем их: красные — в красное ведро, зелёные — в зелёное, синие — в синее. После сортировки, когда тебе понадобится зелёный шарик, ты уже знаешь, что за ним нужно идти к зелёному ведру.

@@ sec.ydkjs-scope.ch2.marbles.b2
В этой метафоре шарики — это переменные нашей программы. Вёдра — это области видимости (функции и блоки), которым мы для удобства обсуждения условно присваиваем отдельные цвета. Таким образом, цвет каждого шарика определяется тем, в области видимости какого *цвета* шарик был изначально создан.

@@ sec.ydkjs-scope.ch2.marbles.b3
Давай разметим наш сквозной пример программы из главы 1 метками цветов областей видимости:

@@ sec.ydkjs-scope.ch2.marbles.b5
Мы обозначили три цвета областей видимости комментариями в коде: КРАСНЫЙ (самая внешняя, глобальная область), СИНИЙ (область функции `getStudentName(..)`) и ЗЕЛЁНЫЙ (область цикла `for`, то есть его внутренность). Но глядя на листинг кода, всё равно может быть трудно различить границы этих вёдер-областей.

@@ sec.ydkjs-scope.ch2.marbles.b6
Рисунок 2 помогает увидеть границы областей видимости, обводя каждую цветным пузырём (то есть ведром):

@@ sec.ydkjs-scope.ch2.marbles.cap7
Рисунок 2: цветные пузыри областей видимости

@@ sec.ydkjs-scope.ch2.marbles.b8
1. **Пузырь 1** (КРАСНЫЙ) охватывает глобальную область, в которой три идентификатора/переменные: `students` (строка 1), `getStudentName` (строка 8) и `nextStudent` (строка 16).
2. **Пузырь 2** (СИНИЙ) охватывает область функции `getStudentName(..)` (строка 8), в которой только один идентификатор/переменная: параметр `studentID` (строка 8).
3. **Пузырь 3** (ЗЕЛЁНЫЙ) охватывает область цикла `for` (строка 9), в которой только один идентификатор/переменная: `student` (строка 9).

@@ sec.ydkjs-scope.ch2.marbles.b9
> **ПРИМЕЧАНИЕ:** Технически параметр `studentID` находится не совсем в СИНЕЙ(2) области. Мы распутаем эту путаницу в разделе «Implied Scopes» (неявные области видимости) в Приложении A. Пока достаточно точно называть `studentID` СИНИМ(2) шариком.

@@ sec.ydkjs-scope.ch2.marbles.b10
Пузыри областей видимости определяются во время компиляции — по тому, где написаны функции/блоки, как они вложены друг в друга и так далее. Каждый пузырь целиком содержится внутри родительского пузыря — область видимости никогда не находится частично в двух разных внешних областях.

@@ sec.ydkjs-scope.ch2.marbles.b11
Каждый шарик (переменная/идентификатор) окрашивается в цвет пузыря (ведра), в котором он объявлен, а не в цвет области, из которой к нему могут обращаться (например, `students` в строке 9 и `studentID` в строке 10).

@@ sec.ydkjs-scope.ch2.marbles.b12
> **ПРИМЕЧАНИЕ:** Помни, в главе 1 мы утверждали, что `id`, `name` и `log` — это свойства, а не переменные; иначе говоря, они не шарики в вёдрах и поэтому не окрашиваются ни по одному из правил, которые мы обсуждаем в этой книге. Чтобы понять, как обрабатываются такие обращения к свойствам, смотри третью книгу серии — *Objects & Classes*.

@@ sec.ydkjs-scope.ch2.marbles.b13
Когда JS-движок обрабатывает программу (во время компиляции) и находит объявление переменной, он, по сути, спрашивает: «В области видимости (пузыре или ведре) какого *цвета* я сейчас нахожусь?» Переменная получает этот же цвет, то есть принадлежит этому ведру/пузырю.

@@ sec.ydkjs-scope.ch2.marbles.b14
ЗЕЛЁНОЕ(3) ведро целиком вложено в СИНЕЕ(2), а СИНЕЕ(2) ведро так же целиком вложено в КРАСНОЕ(1). Области видимости могут вкладываться друг в друга, как показано, на любую глубину, которая нужна твоей программе.

@@ sec.ydkjs-scope.ch2.marbles.b15
Обращения (не объявления) к переменным/идентификаторам допустимы, если есть подходящее объявление либо в текущей области, либо в любой области выше/снаружи текущей, но не с объявлениями из нижних/вложенных областей.

@@ sec.ydkjs-scope.ch2.marbles.b16
Выражение в КРАСНОМ(1) ведре имеет доступ только к КРАСНЫМ(1) шарикам, **но не** к СИНИМ(2) или ЗЕЛЁНЫМ(3). Выражение в СИНЕМ(2) ведре может обращаться к СИНИМ(2) или КРАСНЫМ(1) шарикам, **но не** к ЗЕЛЁНЫМ(3). А выражение в ЗЕЛЁНОМ(3) ведре имеет доступ к КРАСНЫМ(1), СИНИМ(2) и ЗЕЛЁНЫМ(3) шарикам.

@@ sec.ydkjs-scope.ch2.marbles.b17
Процесс определения цвета этих шариков-«не объявлений» во время выполнения можно представить как *поиск* (lookup). Поскольку обращение к переменной `students` в выражении цикла `for` в строке 9 не является объявлением, у него нет цвета. Поэтому мы спрашиваем текущее СИНЕЕ(2) ведро, есть ли в нём шарик с таким именем. Поскольку нет, поиск продолжается в следующей внешней/охватывающей области: КРАСНОЙ(1). В КРАСНОМ(1) ведре есть шарик с именем `students`, поэтому обращение `students` в выражении цикла определяется как КРАСНЫЙ(1) шарик.

@@ sec.ydkjs-scope.ch2.marbles.b18
Аналогично определяется, что выражение `if (student.id == studentID)` в строке 10 обращается к ЗЕЛЁНОМУ(3) шарику `student` и СИНЕМУ(2) шарику `studentID`.

@@ sec.ydkjs-scope.ch2.marbles.b19
> **ПРИМЕЧАНИЕ:** Обычно JS-движок не определяет цвета шариков во время выполнения; «поиск» здесь — риторический приём, который помогает понять идеи. Во время компиляции большинство или все обращения к переменным сопоставляются с уже известными вёдрами-областями, поэтому их цвет уже определён и хранится вместе с каждым обращением к шарику, чтобы избежать лишних поисков во время работы программы. Подробнее об этом нюансе — в главе 3.

@@ sec.ydkjs-scope.ch2.marbles.b20
Главные выводы из шариков и вёдер (и пузырей!):

- Переменные объявляются в конкретных областях видимости; их можно представить как цветные шарики из вёдер соответствующего цвета.
- Любое обращение к переменной, которое встречается в области, где она объявлена, или в любой более глубоко вложенной области, будет помечено шариком того же цвета — если только промежуточная область не «затеняет» (shadowing) объявление переменной; смотри «Shadowing» в главе 3.
- Определение цветных вёдер и шариков в них происходит во время компиляции. Эта информация используется для «поиска» переменных (цвета шариков) во время выполнения кода.

@@ sec.ydkjs-scope.ch2.conversation.b0
Ещё одна полезная метафора для анализа переменных и областей, из которых они берутся, — представить разные разговоры, которые происходят внутри движка, пока код обрабатывается, а затем выполняется. Мы можем «подслушать» эти разговоры, чтобы получить более прочный концептуальный фундамент того, как работают области видимости.

@@ sec.ydkjs-scope.ch2.conversation.b1
Давай познакомимся с участниками JS-движка, которые будут разговаривать, обрабатывая нашу программу:

@@ sec.ydkjs-scope.ch2.conversation.b2
- **Engine (Движок):** отвечает за компиляцию и выполнение нашей JavaScript-программы от начала до конца.
- **Compiler (Компилятор):** один из друзей *Движка*; выполняет всю «грязную» работу парсинга и генерации кода (см. предыдущий раздел).
- **Scope Manager (Менеджер области видимости):** ещё один друг *Движка*; собирает и поддерживает список поиска всех объявленных переменных/идентификаторов и следит за соблюдением правил, по которым они доступны выполняющемуся в данный момент коду ([[scope-manager]]).

@@ sec.ydkjs-scope.ch2.conversation.b3
Чтобы *полностью понять*, как работает JavaScript, тебе нужно начать *думать* так, как думает *Движок* (и его друзья), задавать те же вопросы, что и они, и так же отвечать на их вопросы.

@@ sec.ydkjs-scope.ch2.conversation.b4
Чтобы изучить эти разговоры, снова вспомним наш сквозной пример программы:

@@ sec.ydkjs-scope.ch2.conversation.b6
Давай разберём, как JS будет обрабатывать эту программу, начиная с первого выражения. Массив и его содержимое — это просто базовые литералы значений JS (и поэтому их не касаются вопросы областей видимости), так что здесь мы сосредоточимся на частях объявления и инициализации-присваивания `var students = [ .. ]`.

@@ sec.ydkjs-scope.ch2.conversation.b7
Обычно мы считаем это одним выражением, но наш друг *Движок* видит его иначе. На самом деле JS рассматривает это как две отдельные операции: одну обработает *Компилятор* во время компиляции, а другую — *Движок* во время выполнения.

@@ sec.ydkjs-scope.ch2.conversation.b8
Первое, что *Компилятор* сделает с этой программой, — проведёт lexing, чтобы разбить её на токены, которые затем распарсит в дерево (AST).

@@ sec.ydkjs-scope.ch2.conversation.b9
Когда *Компилятор* доходит до генерации кода, нужно учесть больше деталей, чем может показаться. Разумно предположить, что *Компилятор* создаст для первого выражения примерно такой код: «Выдели память под переменную, назови её `students`, затем помести в эту переменную ссылку на массив». Но это ещё не вся история.

@@ sec.ydkjs-scope.ch2.conversation.b10
Вот шаги, которые *Компилятор* выполнит, чтобы обработать это выражение:

@@ sec.ydkjs-scope.ch2.conversation.b11
1. Встретив `var students`, *Компилятор* попросит *Scope Manager* проверить, существует ли уже переменная `students` в этом конкретном ведре-области. Если да, *Компилятор* проигнорирует это объявление и пойдёт дальше. Иначе *Компилятор* создаст код, который (во время выполнения) попросит *Scope Manager* создать в этом ведре новую переменную `students`.
2. Затем *Компилятор* создаёт код, который *Движок* позже выполнит, чтобы обработать присваивание `students = []`. Код, который запускает *Движок*, сначала спросит *Scope Manager*, есть ли переменная `students`, доступная в текущем ведре-области. Если нет, *Движок* продолжит искать в других местах (см. «Вложенные области видимости» ниже). Найдя переменную, *Движок* присвоит ей ссылку на массив `[ .. ]`.

@@ sec.ydkjs-scope.ch2.conversation.b12
В форме разговора первый этап компиляции программы между *Компилятором* и *Scope Manager* может выглядеть так:

@@ sec.ydkjs-scope.ch2.conversation.b13
> **Компилятор**: Привет, *Scope Manager* (глобальной области), я нашёл формальное объявление идентификатора `students`, слышал о таком?
>
> **(Глобальный) Scope Manager**: Не-а, никогда не слышал, поэтому я только что создал его для тебя.
>
> **Компилятор**: Привет, *Scope Manager*, я нашёл формальное объявление идентификатора `getStudentName`, слышал о таком?
>
> **(Глобальный) Scope Manager**: Не-а, но я только что создал его для тебя.
>
> **Компилятор**: Привет, *Scope Manager*, `getStudentName` указывает на функцию, значит, нам нужно новое ведро-область.
>
> **(Функциональный) Scope Manager**: Понял, вот ведро-область.
>
> **Компилятор**: Привет, *Scope Manager* (функции), я нашёл формальное объявление параметра `studentID`, слышал о таком?
>
> **(Функциональный) Scope Manager**: Не-а, но теперь он создан в этой области.
>
> **Компилятор**: Привет, *Scope Manager* (функции), я нашёл цикл `for`, которому понадобится собственное ведро-область.
>
> ...

@@ sec.ydkjs-scope.ch2.conversation.b14
Разговор — это обмен вопросами и ответами: *Компилятор* спрашивает текущий *Scope Manager*, встречалось ли уже найденное объявление идентификатора. Если «нет», *Scope Manager* создаёт эту переменную в этой области. Если ответ «да», объявление фактически пропускается, потому что этому *Scope Manager* больше нечего делать.

@@ sec.ydkjs-scope.ch2.conversation.b15

@@ sec.ydkjs-scope.ch2.conversation.b19
Повторим и подытожим, как выражение вроде `var students = [ .. ]` обрабатывается в два отдельных шага:

1. *Компилятор* настраивает объявление переменной области видимости (поскольку в текущей области она раньше не объявлялась).
2. Во время выполнения, чтобы обработать часть выражения с присваиванием, *Движок* просит *Scope Manager* найти переменную, инициализирует её значением `undefined`, чтобы она была готова к использованию, а затем присваивает ей значение-массив.

@@ sec.ydkjs-scope.ch2.nested-scope.b0
Когда приходит время выполнить функцию `getStudentName()`, *Движок* запрашивает экземпляр *Scope Manager* для области видимости этой функции, а затем ищет параметр (`studentID`), чтобы присвоить ему значение аргумента `73`, и так далее.

@@ sec.ydkjs-scope.ch2.nested-scope.b1
Область видимости функции `getStudentName(..)` вложена в глобальную область. Блочная область цикла `for` точно так же вложена в эту функциональную область. Области видимости могут быть лексически вложены на любую глубину, которую определяет программа.

@@ sec.ydkjs-scope.ch2.nested-scope.b2
Каждая область видимости получает собственный экземпляр *Scope Manager* каждый раз, когда эта область выполняется (один или несколько раз). У каждой области все её идентификаторы автоматически регистрируются в начале выполнения этой области (это называется «variable hoisting»; см. главу 5).

@@ sec.ydkjs-scope.ch2.nested-scope.b3
Если в начале области какой-то идентификатор пришёл из объявления `function`, эта переменная автоматически инициализируется ссылкой на соответствующую функцию. А если идентификатор пришёл из объявления `var` (в отличие от `let` / `const`), переменная автоматически инициализируется значением `undefined`, чтобы её можно было использовать; в противном случае переменная остаётся неинициализированной (то есть находится в своей «TDZ», см. главу 5) и не может использоваться, пока не выполнятся её полное объявление и инициализация.

@@ sec.ydkjs-scope.ch2.nested-scope.b4
В выражении `for (let student of students) {` `students` — это *source*-обращение, которое нужно найти. Но как будет выполнен этот поиск, если в области видимости функции такого идентификатора нет?

@@ sec.ydkjs-scope.ch2.nested-scope.b5

@@ sec.ydkjs-scope.ch2.nested-scope.b7
Один из ключевых аспектов лексической области видимости: каждый раз, когда обращение к идентификатору не удаётся найти в текущей области, проверяется следующая внешняя область во вложенности; этот процесс повторяется, пока не найдётся ответ или пока не закончатся области для проверки.

@@ sec.ydkjs-scope.ch2.lookup-failures.b0
Когда *Движок* исчерпывает все *лексически доступные* области (двигаясь наружу) и всё равно не может разрешить поиск идентификатора, возникает ошибочная ситуация. Однако в зависимости от режима программы (строгий или нет) и роли переменной (то есть *target* или *source*; см. главу 1) эта ситуация обрабатывается по-разному.

@@ sec.ydkjs-scope.ch2.lookup-failures.b1
## Путаница с undefined

@@ sec.ydkjs-scope.ch2.lookup-failures.b2
Если переменная — *source*, неразрешённый поиск идентификатора считается необъявленной (неизвестной, отсутствующей) переменной, что всегда приводит к выбрасыванию `ReferenceError`. Кроме того, если переменная — *target*, а код в этот момент выполняется в строгом режиме, переменная тоже считается необъявленной и так же выбрасывается `ReferenceError` ([[undeclared]]).

@@ sec.ydkjs-scope.ch2.lookup-failures.b3
Сообщение об ошибке для необъявленной переменной в большинстве JS-сред выглядит так: «Reference Error: XYZ is not defined.» С точки зрения английского языка фраза «not defined» кажется почти идентичной слову «undefined». Но в JS это совсем разные вещи, и это сообщение об ошибке, к сожалению, порождает стойкую путаницу.

@@ sec.ydkjs-scope.ch2.lookup-failures.b4
«Not defined» на самом деле означает «не объявлена», а точнее — «undeclared», то есть переменная, у которой нет подходящего формального объявления ни в одной *лексически доступной* области. «Undefined» же означает, что переменная найдена (объявлена), но в данный момент в ней нет никакого другого значения, поэтому по умолчанию она содержит значение `undefined`.

@@ sec.ydkjs-scope.ch2.lookup-failures.b5
Чтобы ещё сильнее закрепить путаницу, оператор `typeof` в JS возвращает строку `"undefined"` для обращений к переменным в обоих состояниях:

@@ sec.ydkjs-scope.ch2.lookup-failures.b7
Эти два обращения к переменным находятся в совершенно разных состояниях, но JS изрядно мутит воду. Эта терминологическая путаница сбивает с толку и крайне досадна. К сожалению, JS-разработчикам просто приходится внимательно следить, чтобы не перепутать, с каким именно «undefined» они имеют дело!

@@ sec.ydkjs-scope.ch2.lookup-failures.b9
