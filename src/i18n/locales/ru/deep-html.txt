@@ deep.html.0
Главная задача HTML — не создавать внешний вид, а придавать содержимому смысл. На этот смысл опираются браузер, поисковик, экранный диктор и даже твой CSS. Страница, собранная из «кучи div» (divitis), визуально может выглядеть так же, но для машины она совершенно бессмысленна.

## Скелет документа

```html
<body>
  <header>       <!-- шапка сайта, логотип -->
    <nav>...</nav>
  </header>
  <main>         <!-- на странице ТОЛЬКО ОДИН -->
    <h1>Заказы</h1>
    <section aria-labelledby='filters-h'>
      <h2 id='filters-h'>Фильтры</h2>
    </section>
    <article>...</article>   <!-- самостоятельная смысловая единица -->
  </main>
  <aside>...</aside>          <!-- дополнительное, второстепенное содержимое -->
  <footer>...</footer>
</body>
```

Эти элементы одновременно создают роли [[landmark]]. Пользователь [[screen-reader]] может открыть список ориентиров и сразу перейти к `main` — то есть твоя разметка превращается в систему навигации.

## Выбор между section и div

Правило простое: `section` требует собственного заголовка. Если дать ему заголовок не получается, это не `section`, а `div`. `article` — единица, которая сохраняет смысл и вне контекста: запись в блоге, карточка товара, комментарий.

## Иерархия заголовков

Уровни от `h1` до `h6` строят дерево содержания документа. Два правила: не перескакивать уровни (после h2 не должен сразу идти h4) и не выбирать заголовок по размеру. Визуальный размер — задача CSS:

```css
.card h3 { font-size: 1rem; }  /* семантически h3, визуально маленький */
```

## Кликабельные элементы

Это правило нарушают чаще всего. Если элемент выполняет навигацию — `a href`. Если выполняет действие — `button`. `div onClick` ломает три вещи: до него нельзя добраться с клавиатуры (нет tabindex), Enter/Space не работают, экранный диктор не объявляет его интерактивным.

```html
<!-- неправильно -->
<div class='btn' onclick='save()'>Сохранить</div>
<!-- правильно -->
<button type='button' onclick='save()'>Сохранить</button>
```

У кнопок внутри формы обязательно указывай `type`: значение по умолчанию — `submit`, и это приводит к неожиданной отправке формы.

## В контексте React

В JSX действуют те же правила. Кроме того, благодаря `Fragment` не нужно создавать лишний div-обёртку — это и облегчает DOM, и не ломает структуру CSS Grid/Flex. В списках сохраняй структуру `ul > li`: список, собранный из `div`, не сообщает экранному диктору «список из 5 элементов».

Форма — основной договор между пользователем и системой и та часть HTML, которая даёт больше всего функциональности. Незнание встроенных возможностей браузера заставляет заново писать на JavaScript уже существующее поведение.

## Label и связь с полем

У каждого поля должно быть имя, и оно должно быть связано с полем так, чтобы его могла прочитать программа:

```html
<label for='email'>Эл. почта</label>
<input id='email' name='email' type='email' autocomplete='email' required>
```

Placeholder не заменяет label: он исчезает, как только начинаешь печатать, у него низкий контраст и нестабильное поведение в экранных дикторах. Атрибут `autocomplete` позволяет подставить данные, сохранённые в браузере, — в мобильных формах это заметно повышает процент заполнения.

## Правильный тип поля

Выбор [[input-type]] — бесплатный выигрыш в UX: `type=email` добавляет @ на мобильную клавиатуру, `type=tel` открывает цифровую клавиатуру, `type=date` даёт встроенный выбор даты. Осторожно с числами: поле `type=number` может случайно измениться при прокрутке и для пустого значения возвращает `''` — для денежных сумм часто надёжнее текстовое поле с `inputmode='decimal'`.

## Валидация браузером

Для [[form-validation]] в HTML есть готовые атрибуты: `required`, `min`, `max`, `minlength`, `pattern`. Constraint Validation API позволяет управлять ими из JS:

```js
if (!input.checkValidity()) {
  input.setCustomValidity('Этот код уже используется');
  input.reportValidity();
}
```

Но золотое правило не меняется: валидация в браузере — для удобства пользователя, а не для безопасности. Всё должно заново проверяться на сервере, потому что запрос можно отправить напрямую.

## Показ сообщений об ошибках

Текст ошибки должен быть связан с полем на программном уровне, иначе экранный диктор его не прочитает:

```html
<input id='code' aria-invalid='true' aria-describedby='code-err'>
<p id='code-err' role='alert'>Код должен содержать не менее 6 символов</p>
```

## FormData и отправка

[[formdata]] автоматически собирает поля формы и сам формирует формат `multipart/form-data` для загрузки файлов:

```js
const fd = new FormData(formEl);
fd.append('source', 'web');
await fetch('/api/orders', { method: 'POST', body: fd });
// Внимание: НЕ ЗАДАВАЙ заголовок Content-Type ВРУЧНУЮ — потеряется boundary
```

## Практические замечания

Оборачивай форму в тег `form` — от этого зависят отправка по Enter, работа менеджера паролей браузера и кнопка «Отправить» на мобильной клавиатуре. Во время отправки делай кнопку `disabled` и сообщай о состоянии текстом («Сохранение…»), потому что спиннер сам по себе ничего не говорит экранному диктору.

## Четыре принципа (POUR)

Воспринимаемость (Perceivable), управляемость (Operable), понятность (Understandable), надёжность (Robust). На практике это сводится к четырём проверкам: есть ли текстовые альтернативы? можно ли до всего добраться с клавиатуры? понятны ли ошибки? стандартна ли разметка?

## Клавиатура

До каждого интерактивного элемента должно быть можно добраться через Tab, и [[tab-order]] должен совпадать с визуальным порядком. Задавать `tabindex` положительным числом (tabindex=5) почти всегда ошибка — порядок ломается. Используются только `0` (включить в естественный порядок) и `-1` (фокусируется программно, но не входит в Tab).

Фокус должен быть виден. `outline: none` — самая вредная CSS-строка; вместо этого измени его внешний вид:

```css
:focus-visible { outline: 2px solid var(--accent); outline-offset: 2px; }
```

## Модальное окно и фокус

[[focus-management]] критически важен в диалогах. Последовательность: модальное окно открывается → фокус переходит внутрь → Tab циклически ходит только внутри окна (focus trap) → Escape закрывает → при закрытии фокус возвращается на кнопку, которая его открыла. Нативный элемент `<dialog>` даёт большую часть этого из коробки и полностью поддерживается современными браузерами.

## ARIA — мало, но правильно

Атрибуты [[aria]] используются там, где семантики не хватает:

```html
<button aria-expanded='false' aria-controls='menu-1'>Меню</button>
<ul id='menu-1' hidden>...</ul>

<div role='status' aria-live='polite'>Найдено 3 заказа</div>
```

`aria-live` объявляет динамически меняющееся содержимое — это нужно для результатов поиска, toast-сообщений, статуса загрузки, потому что экранный диктор сам не читает появившийся на экране текст.

Первое правило ARIA: если есть подходящий семантический элемент, ARIA не пиши. Лучше div с `role='button'` — просто `button`.

## Изображения и иконки

Для изображения, несущего смысл, пишется описательный `alt`; для чисто декоративного ставится `alt=''` (пустой), чтобы диктор его пропустил. У кнопок, состоящих только из иконки, обязательно должен быть `aria-label`.

## Контраст и текст

Минимальный контраст для обычного текста — 4.5:1, для крупного — 3:1. Используй `rem` вместо `px`, чтобы работала настройка размера шрифта в браузере пользователя.

## Как проверять

Автоматические инструменты (Lighthouse, axe DevTools) находят примерно 30 процентов проблем. Остальное проверяется вручную: отложи мышь и пройди весь сценарий только с клавиатуры. По количеству найденных ошибок этот пятиминутный тест — самая эффективная практика.

## Минимальный набор

```html
<meta charset='utf-8'>
<meta name='viewport' content='width=device-width, initial-scale=1'>
<title>Заказ #1042 — AIPOS</title>
<meta name='description' content='Детали заказа, статус оплаты и дата доставки.'>
<link rel='canonical' href='https://example.com/orders/1042'>
```

Без [[meta-tag]] `viewport` мобильный браузер отрисует страницу шириной 980px и уменьшит её — то есть весь адаптивный CSS теряет смысл. `title` виден и во вкладке браузера, и в результатах поиска: самое важное слово ставь в начало.

## Фронтенд-сторона SEO

[[seo]] — это работа с контентом, но его техническая часть целиком на ответственности фронтенда: скорость ([[lcp]], [[cls]]), семантическая структура, уникальные title/description, canonical, правильные коды состояния и управление индексацией (`robots.txt`, `noindex`).

Критический нюанс: поисковые роботы выполняют JS, но это происходит на втором этапе и с ограниченным бюджетом. Поэтому публичные страницы в режиме [[csr]] попадают в индекс поздно и не полностью — решение [[ssr]] или [[ssg]].

## Структурированные данные

С помощью JSON-LD можно описать содержимое страницы для машин. В результате в выдаче появляются расширенные блоки вроде цены, рейтинга, вопросов и ответов:

```html
<script type='application/ld+json'>
{ '@context':'https://schema.org', '@type':'Product',
  'name':'Клавиатура K95', 'offers':{'@type':'Offer','price':'189.00','priceCurrency':'AZN'} }

```

## Карточки для шеринга

Теги [[open-graph]] определяют, как ссылка будет выглядеть в соцсетях:

```html
<meta property='og:title' content='Система управления заказами'>
<meta property='og:description' content='...'>
<meta property='og:image' content='https://example.com/og.png'>  <!-- 1200x630 -->
```

## Резервирование размеров

Атрибуты `width` и `height` у изображения нужно писать, даже если размер задан через CSS: браузер вычислит по этим двум числам пропорцию и зарезервирует место, и при загрузке изображения страница не прыгнет. Это прямое решение для метрики [[cls]].

```html
<img src='product.webp' width='800' height='600' alt='Клавиатура' style='width:100%;height:auto'>
```

## Выбор формата

[[webp]] при том же качестве примерно на 25–35 процентов меньше JPEG, AVIF — ещё меньше. Если нужна прозрачность, вместо PNG тоже подходит WebP. Для иконок и логотипов выбирают SVG: будучи векторным, он чёткий при любом размере и часто занимает всего несколько килобайт.

## Адаптивные изображения

[[srcset]] предлагает браузеру варианты одного изображения, а выбор делает браузер — с учётом плотности экрана и размера контейнера:

```html
<img src='p-800.webp'
     srcset='p-400.webp 400w, p-800.webp 800w, p-1600.webp 1600w'
     sizes='(max-width: 700px) 100vw, 700px'
     alt='Товар'>
```

Без `sizes` `srcset` работает неправильно — браузеру нужно знать размер изображения в раскладке.

## Стратегия загрузки

[[lazy-loading]] применяют к изображениям ниже первого экрана: `loading='lazy'`. Но ставить lazy на главное изображение вверху экрана вредно — это часто элемент [[lcp]], и его нельзя задерживать. Наоборот, полезно дать ему `fetchpriority='high'`.

```html
<img src='hero.webp' fetchpriority='high' alt='...'>          <!-- первый экран -->
<img src='row-9.webp' loading='lazy' decoding='async' alt='...'>  <!-- ниже -->
```

## Видео и тяжёлые медиа

Для автоматически воспроизводимого видео нужны `muted`, `playsinline` и `poster`; `preload='metadata'` облегчает первую загрузку. Встраивать сторонние видеоплееры (iframe YouTube) напрямую — значит добавить странице сотни килобайт; стандартное решение — показать изображение, а плеер загрузить по клику (приём facade).

## Контекст Next.js

Компонент `next/image` автоматизирует резервирование размеров, конвертацию формата и генерацию srcset. Если пишешь своё решение, те же три вещи нужно обеспечить вручную: размеры, формат, варианты.
