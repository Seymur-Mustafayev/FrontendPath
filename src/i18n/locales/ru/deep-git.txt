Изучать Git как набор заученных команд — самая распространённая ошибка. Когда понимаешь модель, команды сами собой становятся логичными, и страх исчезает.

## Внутренняя модель Git

Git хранит не изменения, а снимки (snapshot). Каждый [[commit]] состоит из трёх вещей: полного состояния дерева, ссылки на родительский коммит (или коммиты) и метаданных. Так коммиты образуют направленный граф.

[[branch]] — просто 41-байтовый указатель на коммит, поэтому создание ветки мгновенно и дёшево. [[head]] показывает, в какой ветке ты находишься.

```
A──B──C  (main)
      \
       D──E  (feature/orders)
```

## Три области

```
Working tree  → текущее состояние файлов
Staging area  → то, что войдёт в следующий коммит (git add)
Repository    → закоммиченная история (git commit)
```

Staging area — то, что отличает Git от других систем: можно закоммитить только часть изменений в одном файле (`git add -p`). Это главный инструмент, чтобы разбить запутанную работу на чистые коммиты.

## Повседневные команды

```bash
git status                 # до и после каждой операции
git add -p                 # добавлять в stage по частям
git commit -m 'feat(orders): добавлена панель фильтров'
git log --oneline --graph --decorate -20
git diff / git diff --staged
git switch -c feature/x    # новая ветка (по-старому: checkout -b)
git restore --staged file  # убрать из stage
git restore file           # отменить изменение (ВНИМАНИЕ: не возвращается)
```

## Сообщение коммита

Хороший коммит атомарен — одно логическое изменение. А сообщение объясняет не только «что», но и «зачем». В командах широко используется формат Conventional Commits:

```
feat(orders): в фильтр заказов добавлен выбор статуса
fix(auth): при ответе 401 процесс обновления запускался дважды
refactor(ui): компонент Button переведён на prop variant

Body: зачем это понадобилось, какая альтернатива рассматривалась.
Refs: #1042
```

Этот формат и читаем, и даёт основу для автоматического changelog и [[semantic-versioning]].

## Откат ошибок

```bash
git commit --amend           # исправить ПОСЛЕДНИЙ коммит (если он не запушен)
git revert <hash>            # НОВЫЙ коммит, отменяющий коммит, — безопасно для общей истории
git reset --soft HEAD~1      # разобрать коммит, сохранив изменения
git reset --hard HEAD~1      # удалить ВСЁ — осторожно
git reflog                   # ПОСЛЕДНЕЕ СРЕДСТВО: найти потерянный коммит
```

Знание `git reflog` реально спасает: даже после неправильного `reset` коммиты какое-то время хранятся, и их можно восстановить.

Слияние и конфликты — часть Git, которая пугает больше всего, хотя механизм прост. Этот раздел даёт и теоретическую разницу, и практическую последовательность решения.

## Разница между merge и rebase

```
MERGE:                          REBASE:
A──B──C──────M  (main)          A──B──C  (main)
      \     /                          \
       D──E                             D'──E'  (feature)

история остаётся как есть       коммиты переписываются, история становится прямой
появляется merge-коммит         merge-коммита нет
```

[[merge]] безопасен и показывает, что произошло, как есть. [[rebase]] делает историю читаемой, но меняет хэши коммитов.

## Золотое правило

Не делай rebase общей ветки. Если в твоей ветке работает кто-то ещё или ветка уже запушена, rebase ломает их историю. А перебазировать свою локальную ветку на main совершенно нормально и рекомендуется:

```bash
git fetch origin
git rebase origin/main        # положить свою работу поверх последнего main
```

## Разрешение конфликтов

[[merge-conflict]] — не ошибка: Git признаёт, что не смог автоматически объединить два изменения, и отдаёт решение тебе.

```
<<<<<<< HEAD
const pageSize = 20;
=======
const pageSize = 50;
>>>>>>> feature/orders
```

Шаги: (1) через `git status` посмотри конфликтные файлы, (2) открой каждый файл и напиши ПРАВИЛЬНЫЙ результат — просто выбрать одну сторону не всегда верно, иногда нужны обе, (3) полностью удали маркеры, (4) запусти код и прогони тесты, (5) `git add` + `git rebase --continue` (или `git commit`).

Выход есть всегда: `git rebase --abort` или `git merge --abort` вернёт тебя в исходное состояние.

## Очистка истории

[[interactive-rebase]] нужен, чтобы навести порядок в коммитах перед отправкой PR:

```bash
git rebase -i origin/main

pick a1b2c3 feat: панель фильтров
squash d4e5f6 fix: опечатка         # объединить с предыдущим
reword 78g9h0 refactor: именование  # изменить сообщение
drop  i1j2k3 debug log              # удалить полностью
```

[[squash]] превращает коммиты вроде «wip», «fix typo», «опять fix» в один осмысленный коммит. Многие команды используют автоматический squash при слиянии PR — тогда локальная история не так важна.

[[cherry-pick]] переносит один коммит в другую ветку — классическое решение, чтобы применить hotfix и к main, и к release-ветке.

## Практический совет

Единственный способ избавиться от страха — практика: создай пустой репозиторий, намеренно устрой конфликт и разреши его, попробуй команды `reset`, `revert`, `reflog`. Терять нечего, а эти 30 минут экономят часы в реальном проекте.

## Две основные модели

Разработка [[trunk-based]]: короткоживущие ветки (1–2 дня), частое слияние в main, незавершённые функции прячутся за [[feature-flag]]. Лучше всего сочетается с CI/CD и считается современным выбором по умолчанию.

[[git-flow]]: более тяжёлая структура с ветками develop, release, hotfix. Всё ещё уместна в продуктах с версиями и графиком выпуска (десктопные приложения, устанавливаемые системы).

## Именование веток

```
feature/1042-order-filters
fix/1108-refresh-loop
chore/upgrade-vite
```

Номер рабочего элемента в имени или сообщении коммита создаёт автоматическую связь с Boards в [[azure-devops]] — зачем было сделано изменение, можно отследить и через полгода.

## Хороший Pull Request

[[pull-request]] — ворота для ревью кода, и его размер напрямую влияет на качество. В PR больше 400 строк внимание ревьюера резко падает — исследования подтверждали это много раз.

Описание PR должно отвечать на три вопроса: что изменилось, зачем это понадобилось, как проверено. Скриншот или короткое видео вдвое сокращают время ревьюера при изменениях UI.

## Культура ревью кода

Как ревьюер: смотри на код, а не на человека. Пиши предложение вместе с причиной — не «измени это», а «здесь значение может быть undefined, потому что API возвращает поле как необязательное». Автоматизируй вопросы стиля ([[prettier]]), чтобы в ревью осталась только суть. Отделяй важное от предложений: блокирующая проблема, предложение и дело вкуса — разные вещи.

```
blocking: при 401 пользователь попадает в бесконечный цикл
suggestion: если вынести эту часть в кастомный хук, её можно использовать в двух местах
nit: именование — `orders` понятнее, чем `data`
```

Как автор: не защищайся, задавай вопросы. Если не согласен, объясни причину техническим языком. Не воспринимать отзыв как личную оценку — часть профессионализма.

## Branch policy

В реальной команде это применяется через конфигурацию: запрет прямого push в main, минимум одно одобрение, обязательный успешный build и тесты, требование связи с рабочим элементом, выбранный способ слияния (squash). Эти правила — не обсуждение, а автоматический контроль, и именно поэтому они работают.

## Boards — отслеживание работы

Иерархия рабочих элементов: Epic → Feature → User Story / Bug → Task. При планировании спринта даётся оценка в story point или часах. Практический вывод для фронтенд-разработчика: принимая задачу, проверь, понятны ли критерии приёмки (acceptance criteria), — если нет, спроси ДО того, как писать код.

Запись `#1042` в коммите или PR создаёт автоматическую связь с рабочим элементом. Это самый простой способ в будущем найти ответ на вопрос «почему этот код такой?».

## Repos и политики

Здесь настраиваются branch policy: минимальное число ревьюеров, build validation, связь с рабочим элементом, правило сообщений коммитов, автоматическое назначение ревьюеров по путям файлов (аналог CODEOWNERS).

## Pipelines — через YAML

[[yaml-pipeline]] хранится в репозитории, то есть версионируется и проходит ревью в PR. Типичный фронтенд-конвейер:

```yaml
trigger:
  branches: { include: [main] }

pool: { vmImage: 'ubuntu-latest' }

steps:
  - task: NodeTool@0
    inputs: { versionSpec: '20.x' }

  - script: npm ci
    displayName: 'Установить зависимости'

  - script: npm run typecheck && npm run lint
    displayName: 'Проверка типов и линтинг'

  - script: npm test -- --coverage
    displayName: 'Тесты'

  - script: npm run build
    displayName: 'Build'

  - task: PublishBuildArtifacts@1
    inputs: { pathToPublish: 'dist', artifactName: 'web' }
```

## Важные детали

Используется `npm ci`, а не `npm install`: первый строго следует [[lock-file]] и даёт воспроизводимую сборку.

Кэширование зависимостей (`~/.npm` через задачу `Cache@2`) заметно сокращает время конвейера.

Публикация [[artifact]] важна: сборка выполняется один раз, затем тот же пакет разворачивается в тестовой и продакшен-среде. Пересборка под каждое окружение — источник проблем вида «в тесте работало».

## Поэтапный деплой

Pipeline делятся на стадии: Build → Deploy Dev → Deploy Test → Deploy Prod. Перед продакшен-стадией ставится ручное подтверждение (approval gate). В Azure App Service через deployment slots можно сначала развернуть в staging-слот, а потом сделать swap — это даёт нулевой простой и мгновенный откат.

## Чтение результата

Когда pipeline падает, паниковать не нужно: найди в логе упавший шаг, прочитай сообщение и выполни ту же команду локально. Если есть разница, причина обычно в версии Node, переменной окружения или отсутствии lock-файла в репозитории.

## Шаги конвейера и их порядок

```
1. install    → npm ci                       (с кэшем)
2. typecheck  → tsc --noEmit                 (быстро, падает рано)
3. lint       → eslint .
4. test       → vitest run --coverage
5. build      → vite build / next build
6. e2e        → playwright test              (на результате сборки)
7. artifact   → сохранить результат
8. deploy     → развернуть в окружение
```

Важен принцип ставить быстрые и рано падающие шаги в начало: разработчик не должен ждать 12 минут, чтобы увидеть ошибку линтера.

## Локальная защита

[[pre-commit-hook]] ловит ошибку до того, как она дойдёт до CI:

```json
// package.json
{
  'lint-staged': {
    '*.{ts,tsx}': ['eslint --fix', 'prettier --write'],
    '*.{json,css,md}': ['prettier --write']
  }
}
```

Через Husky подключается к хуку `pre-commit`. Внимание: запуск всего набора тестов в хуке замедляет коммиты и подталкивает разработчиков писать `--no-verify` — туда стоит ставить только быстрые проверки изменённых файлов.

## Версионирование и выпуск

[[semantic-versioning]] — MAJOR.MINOR.PATCH — несовместимое изменение, новая функция, исправление. В сочетании с Conventional Commits версию и changelog можно генерировать автоматически (semantic-release, changesets). Во внутренних приложениях версию часто заменяет номер сборки — главное, чтобы было известно, какой коммит работает в продакшене.

## Окружения

```
Dev      → автоматически при каждом слиянии
Test/UAT → в конце спринта или по подтверждению
Prod     → ручное подтверждение с учётом рабочих часов
```

Конфигурация не пишется в коде, а приходит из переменных окружения и хранилища секретов ([[env-variable]]).

## Стратегии деплоя

Blue-green: два одинаковых окружения, трафик переключается с одного на другое мгновенно — моментальный откат. Canary: новая версия сначала выдаётся небольшой части пользователей. А для фронтенда самое простое и эффективное правило: публикуй статические файлы с хэшированными именами, не кэшируй `index.html`, а при проблеме возвращайся к предыдущему деплою.

## Здоровье конвейера

Конвейер, который постоянно падает или без причины требует «перезапустить», теряет доверие команды. Нестабильные тесты ([[flaky-test]]) сразу изолируй и исправляй — состояние «иногда падает» обнуляет всю ценность CI.
