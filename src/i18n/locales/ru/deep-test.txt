Тестирование — самый откладываемый навык во фронтенде, и результат всегда один: код становится страшным, рефакторинг останавливается, каждый релиз проверяется вручную. Этот раздел отвечает на вопрос «что тестировать», потому что тестировать не то может обойтись дороже, чем не тестировать вовсе.

## Пирамида и реальность фронтенда

[[test-pyramid]] классически предлагает много [[unit-test]], умеренное количество [[integration-test]] и мало [[e2e]]. Во фронтенде же центр тяжести в середине — модель «testing trophy»: больше всего ценности дают интеграционные тесты, потому что пользователь пользуется не отдельной функцией, а совместной работой компонентов.

```
Статика (TS + ESLint)  → самое дешёвое, работает при каждом наборе
Unit                   → чистые функции: вычисления, форматирование, reducer
Интеграция             → компонент + хук + mock API  ← ОСНОВНОЙ ОБЪЁМ
E2E                    → критические сценарии: вход, заказ, оплата
```

## Что нужно тестировать

Критерий простой: поведение, поломка которого дорого обходится бизнесу. На практике это три категории — логика денег и вычислений, поведение прав и безопасности, сложные сценарии, которые часто меняются.

Что тестировать НЕ СТОИТ: CSS-классы, имя внутреннего состояния компонента, собственную функциональность библиотеки, простые геттеры. Это детали реализации, и при каждом рефакторинге они ломают тест.

## Разница между поведением и реализацией

```tsx
// тест РЕАЛИЗАЦИИ — хрупкий
expect(wrapper.state('isOpen')).toBe(true);

// тест ПОВЕДЕНИЯ — устойчивый
await user.click(screen.getByRole('button', { name: 'Фильтры' }));
expect(screen.getByRole('dialog', { name: 'Фильтры' })).toBeVisible();
```

Первый тест ломается, когда компонент переводят на `useReducer`, а второй продолжает работать — хотя для пользователя ничего не изменилось.

## О покрытии

[[coverage]] — полезный показатель, но не цель. 100 процентов покрытия не гарантируют качество: код, выполненный без проверок, тоже считается покрытым. Практичный подход: требовать высокого покрытия в критических модулях, а общую цифру отслеживать как тренд.

## Стратегия для старта

Если начинаешь с нуля, самый эффективный способ такой: на каждый исправляемый баг сначала пиши тест, который его воспроизводит, и только потом исправляй. За месяц-два появится настоящий набор тестов, покрывающий самые хрупкие места, — причём построенный по реальным рискам твоего проекта.

> Этот путь — твой приоритетный пробел. Для разработчика, не умеющего тестировать, рефакторинг всегда остаётся риском, и это главное препятствие на пути к уровню middle.

## Структура теста

Хороший тест состоит из трёх частей: подготовка, действие, проверка (Arrange – Act – Assert). А его название должно описывать поведение:

```ts
describe('calcTotal', () => {
  it('применяет скидку и возвращает итоговую сумму', () => {
    const items = [{ price: 10, qty: 2 }, { price: 5, qty: 1 }];
    const total = calcTotal(items, { discount: 0.1 });
    expect(total).toBe(22.5);
  });

  it('для пустой корзины возвращает ноль', () => {
    expect(calcTotal([], {})).toBe(0);
  });
});
```

## Полезные assertion

```ts
expect(v).toBe(3);                 // равенство ссылок/примитивов (Object.is)
expect(obj).toEqual({ id: 1 });    // глубокое сравнение
expect(obj).toStrictEqual({...});  // учитывает и поля со значением undefined
expect(fn).toThrow('Сообщение');
expect(arr).toHaveLength(3);
await expect(promise).rejects.toThrow(ApiError);
expect(spy).toHaveBeenCalledWith({ id: 1 });
```

## Время и случайность

Тест должен быть детерминированным. Даты и таймеры берут под контроль:

```ts
vi.useFakeTimers();
vi.setSystemTime(new Date('2026-01-15T10:00:00Z'));
// ...
vi.advanceTimersByTime(5000);
vi.useRealTimers();
```

## Параметризованные тесты

Когда одну и ту же логику нужно проверить для нескольких входных данных:

```ts
it.each([
  [0, '0,00 ₼'],
  [1234.5, '1 234,50 ₼'],
  [-20, '-20,00 ₼']
])('formatMoney(%s) → %s', (input, expected) => {
  expect(formatMoney(input)).toBe(expected);
});
```

## Привычка к скорости

В режиме `vitest --watch` запускаются только тесты, относящиеся к изменённому файлу, и результат приходит за несколько сотен миллисекунд. Держать этот режим открытым во время написания — самый простой способ встроить тесты в ежедневную работу.

## Приоритет запросов

[[query-by-role]] — первый выбор, потому что работает через дерево доступности — в результате тест проверяет и поведение, и a11y:

```
1. getByRole('button', { name: 'Сохранить' })
2. getByLabelText('Эл. почта')          — поля формы
3. getByPlaceholderText / getByText     — следующие варианты
4. getByTestId                          — только когда другого пути нет
```

Разница префиксов важна: `getBy` должен найти элемент сразу (иначе ошибка), `queryBy` — для проверки отсутствия (`toBeNull`), а `findBy` асинхронный и ждёт.

## Асинхронные результаты

```tsx
expect(await screen.findByText('Заказ создан')).toBeInTheDocument();
await waitForElementToBeRemoved(() => screen.queryByRole('progressbar'));
```

Если видишь предупреждение [[act]], значит, обновление состояния произошло вне контроля теста. Решение почти всегда — правильно дождаться результата через `findBy...` или `waitFor`; оборачивать в `act` вручную нужно редко.

## Обёртка для тестов

Реальным компонентам нужны провайдеры. Чтобы не повторять их в каждом тесте, напиши свою функцию `render`:

```tsx
function renderWithProviders(ui: ReactElement){
  const qc = new QueryClient({ defaultOptions: { queries: { retry: false } } });
  return render(
    <QueryClientProvider client={qc}>
      <MemoryRouter>{ui}</MemoryRouter>
    </QueryClientProvider>
  );
}
```

В тесте важно `retry: false` — иначе сценарии с ошибками повторяются трижды, и тест замедляется.

## Что проверять

Результат, видимый на экране, вызванные колбэки и переходы состояний: загрузка → данные, пустой результат, ошибка и повторная попытка. Имена классов, структура DOM и вызовы внутренних функций предметом теста не являются.

Тесту нужна изоляция: результат не должен зависеть от сети, времени и сторонних сервисов. Но уровень изоляции нужно выбирать правильно — избыток моков делает тест бессмысленным.

## Уровни моков

```
Мок функции : vi.fn() — вызван ли колбэк, с какими аргументами
Мок модуля  : vi.mock('./api') — заменить весь модуль
Мок сети    : MSW — самый реалистичный, код выполняет настоящий fetch
```

[[msw]] предпочтительнее, потому что твой слой API (заголовки, проверка статуса, преобразование ошибок) ДЕЙСТВИТЕЛЬНО выполняется внутри теста. Если мокать `fetch`, этот слой пропускается, и его ошибки в тесте не видны.

## Настройка MSW

```ts
import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

export const server = setupServer(
  http.get('/api/orders', () => HttpResponse.json([{ id: 1, total: 20 }])),
  http.post('/api/orders', async ({ request }) => {
    const body = await request.json();
    return HttpResponse.json({ id: 99, ...body }, { status: 201 });
  })
);

beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());
```

Параметр `onUnhandledRequest: 'error'` выявляет неожиданные запросы — полезно, чтобы увидеть, что скрывает тест.

## Повторное использование в dev-среде

Обработчики MSW можно запускать и в браузере (`setupWorker`). Это позволяет писать UI, пока бэкенд не готов, а один и тот же набор моков используется и в тестах, и при разработке — двойная польза.

## Когда не мокать

Мокать чистые функции, собственные утилиты и внутренности тестируемого модуля — значит выхолостить тест. Правило: мокай только границы — сеть, время, случайность, API браузера, платёжного провайдера.

Эта тема — пересечение двух твоих слабых областей: оптимизации производительности React и тестирования. Главный принцип здесь такой: тестировать сами `useMemo` и `useCallback` нельзя — нужно тестировать их РЕЗУЛЬТАТ.

## Изолированный тест хука

[[renderhook]] позволяет тестировать хук, не написав компонента:

```tsx
import { renderHook, act } from '@testing-library/react';

it('обновляет значение по истечении задержки debounce', () => {
  vi.useFakeTimers();
  const { result, rerender } = renderHook(
    ({ value }) => useDebouncedValue(value, 300),
    { initialProps: { value: 'a' } }
  );

  expect(result.current).toBe('a');
  rerender({ value: 'ab' });
  expect(result.current).toBe('a');          // ещё не изменилось

  act(() => { vi.advanceTimersByTime(300); });
  expect(result.current).toBe('ab');
  vi.useRealTimers();
});
```

Функция [[rerender]] имитирует изменение props — это ключ к тесту мемоизации.

## Проверка результата useMemo

Есть два способа. Первый — доказать, что дорогая функция не вызывается повторно:

```tsx
const calc = vi.fn((rows) => rows.reduce((s, r) => s + r.total, 0));

function useTotal(rows){ return useMemo(() => calc(rows), [rows]); }

it('не повторяет вычисление для того же массива', () => {
  const rows = [{ total: 10 }];
  const { rerender } = renderHook(({ r }) => useTotal(r), { initialProps: { r: rows } });

  expect(calc).toHaveBeenCalledTimes(1);
  rerender({ r: rows });                    // ТА ЖЕ ссылка
  expect(calc).toHaveBeenCalledTimes(1);    // не пересчитано

  rerender({ r: [...rows] });               // НОВАЯ ссылка
  expect(calc).toHaveBeenCalledTimes(2);    // пересчитано
});
```

Второй — проверить, что ссылка остаётся стабильной:

```tsx
const first = result.current;
rerender({ r: rows });
expect(result.current).toBe(first);   // toBe = та же ссылка
```

## useCallback и React.memo

Настоящая цель `useCallback` — чтобы мемоизированный потомок не перерендеривался. Значит, и тест должен измерять именно это:

```tsx
let childRenders = 0;
const Child = React.memo(function Child({ onPick }: { onPick: () => void }){
  childRenders++;
  return <button onClick={onPick}>Выбрать</button>;
});

function Parent(){
  const [n, setN] = useState(0);
  const onPick = useCallback(() => {}, []);     // стабильная ссылка
  return <><button onClick={() => setN(n + 1)}>{n}</button><Child onPick={onPick} /></>;
}

it('мемоизированный потомок не рендерится при рендере родителя', async () => {
  const user = userEvent.setup();
  render(<Parent />);
  expect(childRenders).toBe(1);
  await user.click(screen.getByText('0'));
  expect(childRenders).toBe(1);                 // без useCallback было бы 2
});
```

Для [[memoization-test]] этот приём со счётчиком рендеров — самое наглядное доказательство.

## Важное предупреждение

Писать такие тесты для каждого memo не нужно — иначе тесты привязываются к реализации и ломаются при изменениях вроде React Compiler. Пиши их только в критичных местах, где мемоизация добавлена по ИЗМЕРЕННОЙ причине производительности, и указывай причину в названии теста: «строки большой таблицы не должны перерендериваться при смене фильтра».

## Замечание о StrictMode

В режиме разработки React намеренно рендерит компоненты дважды. При тесте со счётчиком рендеров это может удвоить ожидаемое число — надёжнее не использовать `StrictMode` в тестовой среде или проверять относительный прирост.

[[playwright]] — современный стандарт E2E-тестирования: проверяет весь пользовательский сценарий в настоящем браузере (Chromium, Firefox, WebKit). Но E2E дорог — работает медленно и склонен к нестабильности. Поэтому его оставляют только для критических сценариев.

## Что покрывать E2E

Сценарии, которые могут привести к потере денег или данных: вход, создание заказа, оплата, экспорт отчёта, ограничения прав. Всё остальное дешевле проверяется интеграционными тестами.

## Основной пример

```ts
import { test, expect } from '@playwright/test';

test('пользователь может создать заказ', async ({ page }) => {
  await page.goto('/orders');
  await page.getByRole('button', { name: 'Новый заказ' }).click();

  await page.getByLabel('Клиент').selectOption('42');
  await page.getByLabel('Сумма').fill('250');
  await page.getByRole('button', { name: 'Сохранить' }).click();

  await expect(page.getByRole('alert')).toHaveText(/создан/);
  await expect(page.getByRole('row', { name: /250/ })).toBeVisible();
});
```

## Auto-wait и стабильность

Перед каждым действием Playwright ждёт, пока элемент станет видимым, активным и стабильным. Это почти полностью избавляет от необходимости писать `waitForTimeout`. Первая причина [[flaky-test]] — как раз фиксированные ожидания:

```ts
await page.waitForTimeout(2000);           // НЕПРАВИЛЬНО — хрупко
await expect(page.getByRole('row')).toHaveCount(3);   // ПРАВИЛЬНО — ожидание по условию
```

## Стратегия селекторов

[[selector-strategy]] определяет срок жизни теста. Приоритет: `getByRole` → `getByLabel` → `getByText` → `data-testid`. Селектор, привязанный к CSS-классу и структуре DOM, ломается при первом рефакторинге.

## Аутентификация и скорость

Заполнять форму входа в каждом тесте — потеря времени. Playwright позволяет сохранить состояние один раз и использовать его повторно:

```ts
// global setup
await page.context().storageState({ path: 'auth.json' });
// в конфигурации
use: { storageState: 'auth.json' }
```

## Тестовые данные

E2E-тесты в общей среде не должны мешать друг другу. Практичные решения: каждый тест сам создаёт свои данные через API и удаляет их в конце, использует уникальные идентификаторы (`order-${Date.now()}`), а тесты не зависят друг от друга.

## Запуск в CI

```yaml
- script: npx playwright install --with-deps chromium
- script: npx playwright test --reporter=html
```

Для упавших тестов Playwright автоматически сохраняет скриншот, видео и trace. Trace Viewer показывает состояние DOM на каждом шаге — тесты, которые падают в CI и проходят локально, нужно исследовать именно этим инструментом.
