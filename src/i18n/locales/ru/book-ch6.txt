Наименьшая открытость

@@ sec.ydkjs-scope.ch6.least-exposure.note
POLE — не просто правило JS, а основа хорошей фронтенд-архитектуры:

- Внутренний state компонента не выносится наружу как props.
- Модуль делает `export` только нужного, вспомогательные функции остаются внутри файла.
- Кастомный хук возвращает только нужные значения.

Особенно болезненна «нежелательная зависимость»: когда от экспортированной тобой вспомогательной функции зависят 20 файлов, её изменение превращается в полноценный рефакторинг.

@@ sec.ydkjs-scope.ch6.iife.heading
Немедленный вызов функциональных выражений

@@ sec.ydkjs-scope.ch6.iife.note
IIFE — главный инструмент «модульности» эпохи до ES-модулей: на нём строились плагины jQuery и старые библиотеки. Сегодня ты чаще всего встретишь его в двух местах:

```js
// 1. Асинхронная функция внутри useEffect
useEffect(() => {
  (async () => {
    const res = await fetch(url);
    setData(await res.json());
  })();
}, [url]);
```

2. В выходных файлах бандлера (результат сборки) — Vite/Rollup часто собирает код в формате IIFE.

@@ sec.ydkjs-scope.ch6.block-scoping.heading
Области видимости с помощью блоков

@@ sec.ydkjs-scope.ch6.block-scoping.note
Явный блок `{ }` редко встречается в повседневном коде, но очень полезен в `switch`:

```js
switch (action.type) {
  case 'add': {
    const item = action.payload;   // только внутри этого case
    return [...state, item];
  }
  case 'remove': {
    const item = action.payload;   // конфликта нет
    return state.filter((x) => x.id !== item.id);
  }
}
```

Без блоков два `const item` дали бы `SyntaxError` — ведь `{ }` у `switch` — это один общий scope. Ты будешь часто использовать этот паттерн при написании редьюсеров.

@@ sec.ydkjs-scope.ch6.var-and-let.heading
var и let

@@ sec.ydkjs-scope.ch6.var-and-let.note
Здесь личная позиция автора расходится с практикой индустрии — знай это:

- **Автор:** `var` на уровне функции, `let` в блоках.
- **Индустрия (Airbnb style guide, ESLint `no-var`, проекты на TypeScript):** `var` не пишут вообще; по умолчанию `const`, а если значение должно меняться — `let`.

В команде следуй правилам линтера команды. Но главный вопрос автора остаётся в обоих подходах: **«какой наименьший достаточный scope для этой переменной?»**

@@ sec.ydkjs-scope.ch6.catch.heading
В чём подвох catch?

@@ sec.ydkjs-scope.ch6.catch.note
Практическое правило: `err` живёт только внутри блока `catch`. Если он нужен снаружи, объяви его снаружи через `let` и присвой внутри.

Форма `catch {}` (без параметра) удобна, например, с `JSON.parse`:

```js
function safeParse(str) {
  try { return JSON.parse(str); }
  catch { return null; }
}
```

@@ sec.ydkjs-scope.ch6.fib.heading
Объявления функций в блоках (FiB)

@@ sec.ydkjs-scope.ch6.fib.note
Коротко: **не пиши `function name() {}` внутри блока**. Если нужна функция, зависящая от условия, используй выражение:

```js
const format = isMobile
  ? (d) => d.toLocaleDateString()
  : (d) => d.toLocaleString();
```

В ES-модулях (строгий режим) FiB работает с блочным scope, как требует спецификация, но всё равно сбивает читателя с толку — безопаснее всего его избегать.

@@ sec.ydkjs-scope.ch6.blocked-over.heading
Итоги про блоки

@@ sec.ydkjs-scope.ch6.blocked-over.note
Преврати главу в чек-лист — для каждой переменной:

```text
1. Где нужна эта переменная? → выбери наименьший scope
2. Должна ли она жить между вызовами? → промежуточный scope (функция / модуль)
3. Нужна только в половине блока? → внутренний блок { }
4. Условная функция? → выражение, а не объявление (избегай FiB)
```

@@ sec.ydkjs-scope.ch6.intro.b0
До сих пор мы сосредотачивались на объяснении механики того, как работают области видимости и переменные. Теперь, когда этот фундамент прочно заложен, наше внимание поднимается на более высокий уровень мышления: решения и паттерны, которые мы применяем во всей программе.

@@ sec.ydkjs-scope.ch6.intro.b1
Для начала мы рассмотрим, как и почему следует использовать разные уровни областей видимости (функции и блоки) для организации переменных программы, в частности чтобы уменьшить чрезмерную открытость областей.

@@ sec.ydkjs-scope.ch6.least-exposure.b0
Логично, что функции определяют собственные области видимости. Но зачем нужны ещё и блоки, создающие области?

@@ sec.ydkjs-scope.ch6.least-exposure.b1
Программная инженерия формулирует фундаментальную дисциплину, обычно применяемую к безопасности ПО, — «Принцип наименьших привилегий» (POLP). А вариант этого принципа, относящийся к нашему обсуждению, обычно называют «Наименьшей открытостью» ([[pole]]).

@@ sec.ydkjs-scope.ch6.least-exposure.b2
POLP выражает оборонительную позицию в архитектуре ПО: компоненты системы должны проектироваться так, чтобы работать с наименьшими привилегиями, наименьшим доступом, наименьшей открытостью. Если каждая часть связана с минимально необходимыми возможностями, система в целом прочнее с точки зрения безопасности, потому что компрометация или сбой одной части минимально влияет на остальную систему.

@@ sec.ydkjs-scope.ch6.least-exposure.b3
Если POLP сосредоточен на проектировании компонентов уровня системы, то вариант POLE — про *открытость* — сосредоточен на более низком уровне; мы применим его к тому, как области видимости взаимодействуют друг с другом.

@@ sec.ydkjs-scope.ch6.least-exposure.b4
Следуя POLE, открытость чего мы хотим минимизировать? Просто: переменных, зарегистрированных в каждой области.

@@ sec.ydkjs-scope.ch6.least-exposure.b5
Подумай так: почему бы просто не поместить все переменные программы в глобальную область? Это, вероятно, сразу кажется плохой идеей, но стоит понять почему. Когда переменные, которые использует одна часть программы, через область видимости открыты другой части программы, часто возникают три основные опасности:

@@ sec.ydkjs-scope.ch6.least-exposure.b6
- **Коллизии имён:** если ты используешь распространённое и удобное имя переменной/функции в двух разных частях программы, но идентификатор берётся из одной общей области (например, глобальной), возникает коллизия имён, и весьма вероятно появление багов, поскольку одна часть использует переменную/функцию не так, как ожидает другая.

@@ sec.ydkjs-scope.ch6.least-exposure.b7
Например, представь, что все твои циклы используют одну глобальную индексную переменную `i`, и случается так, что цикл в одной функции выполняется во время итерации цикла из другой функции — и теперь общая переменная `i` получает неожиданное значение.

@@ sec.ydkjs-scope.ch6.least-exposure.b8
- **Неожиданное поведение:** если открыть переменные/функции, использование которых иначе было бы приватным для части программы, это позволит другим разработчикам использовать их так, как ты не задумывал, что может нарушить ожидаемое поведение и вызвать баги.

@@ sec.ydkjs-scope.ch6.least-exposure.b9
Например, если твоя часть программы предполагает, что массив содержит только числа, а чужой код обращается к массиву и добавляет в него булевы значения и строки, твой код может повести себя неожиданным образом.

@@ sec.ydkjs-scope.ch6.least-exposure.b10
Хуже того, открытость приватных деталей побуждает злоумышленников пытаться обойти наложенные тобой ограничения и делать с твоей частью ПО то, что не должно быть разрешено.

@@ sec.ydkjs-scope.ch6.least-exposure.b11
- **Нежелательная зависимость:** если без необходимости открывать переменные/функции, это побуждает других разработчиков использовать эти приватные части и зависеть от них. Сегодня это программу не ломает, но создаёт опасность при будущем рефакторинге: теперь ты не можешь так же легко переделать эту переменную или функцию, не рискуя сломать другие части ПО, которые ты не контролируешь.

@@ sec.ydkjs-scope.ch6.least-exposure.b12
Например, если твой код опирается на массив чисел, а потом ты решаешь, что лучше использовать вместо массива другую структуру данных, тебе теперь приходится брать на себя ответственность за исправление других затронутых частей ПО.

@@ sec.ydkjs-scope.ch6.least-exposure.b13
POLE применительно к областям видимости переменных/функций, по сути, говорит: по умолчанию открывай лишь необходимый минимум, а всё остальное держи как можно более приватным. Объявляй переменные в как можно меньших и глубже вложенных областях, а не помещай всё в глобальную (или даже внешнюю функциональную) область.

@@ sec.ydkjs-scope.ch6.least-exposure.b14
Если проектировать ПО таким образом, шансы избежать этих трёх опасностей (или хотя бы свести их к минимуму) гораздо выше.

@@ sec.ydkjs-scope.ch6.function-scope-hiding.b0
Теперь должно быть понятно, почему важно прятать объявления переменных и функций в самых нижних (глубже всего вложенных) областях. Но как это сделать?

@@ sec.ydkjs-scope.ch6.function-scope-hiding.b1
Мы уже видели ключевые слова `let` и `const` — блочные объявления; скоро вернёмся к ним подробнее. Но сначала: как спрятать в области объявления `var` или `function`? Это легко сделать, обернув объявление в область `function`.

@@ sec.ydkjs-scope.ch6.function-scope-hiding.b2
Рассмотрим пример, где функциональная область `function` может быть полезна.

@@ sec.ydkjs-scope.ch6.function-scope-hiding.b3
Математическая операция «факториал» (обозначается «6!») — это умножение данного целого числа на все последовательно меньшие целые числа вплоть до `1`; на самом деле можно остановиться на `2`, ведь умножение на `1` ничего не меняет. Иными словами, «6!» — то же самое, что «6 * 5!», а это то же, что «6 * 5 * 4!», и так далее. Из-за природы этой математики, как только факториал какого-то числа (например, «4!») вычислен, выполнять эту работу снова не нужно — ответ всегда будет тем же.

FP-библиотеки обычно предоставляют оптимизированную и проверенную утилиту для мемоизации функций, которая заняла бы здесь место `hideTheCache(..)`. Мемоизация выходит за *рамки* (каламбур намеренный!) нашего обсуждения, подробнее — в моей книге *Functional-Light JavaScript*.

@@ sec.ydkjs-scope.ch6.iife.b0
В предыдущей рекурсивной программе с факториалом есть ещё одна важная деталь, которую легко упустить: строка в конце `function`-выражения, содержащая `})();`.

@@ sec.ydkjs-scope.ch6.iife.b1
Обрати внимание: мы окружили всё `function`-выражение скобками `( .. )`, а в конце добавили вторую пару скобок `()`; это и есть вызов только что определённого `function`-выражения. Более того, в этом случае первая пара скобок `( .. )` вокруг функционального выражения не строго обязательна (подробнее чуть позже), но мы всё равно использовали её ради читаемости.

@@ sec.ydkjs-scope.ch6.iife.b2
Иными словами, мы определяем `function`-выражение, которое затем сразу же вызывается. У этого распространённого паттерна есть (очень креативное!) имя: Immediately Invoked Function Expression ([[iife]]) — немедленно вызываемое функциональное выражение.

@@ sec.ydkjs-scope.ch6.iife.b3
IIFE полезно, когда мы хотим создать область для скрытия переменных/функций. Поскольку это выражение, его можно использовать в **любом** месте JS-программы, где допустимо выражение. IIFE может быть именованным, как `hideTheCache()`, или (гораздо чаще!) безымянным/анонимным. И оно может быть самостоятельным или, как раньше, частью другого выражения — `hideTheCache()` возвращает ссылку на функцию `factorial()`, которая затем через `=` присваивается переменной `factorial`.

Для сравнения, вот пример самостоятельного IIFE:

@@ sec.ydkjs-scope.ch6.iife.b6
В отличие от примера с `hideTheCache()`, где внешние скобки `(..)` были отмечены как необязательный стилистический выбор, в самостоятельном IIFE они **обязательны**: они отличают `function` как выражение, а не как объявление. Однако ради единообразия всегда окружай функцию IIFE скобками `( .. )`.

## Границы функций

@@ sec.ydkjs-scope.ch6.iife.b9
Имей в виду, что использование IIFE для создания области может иметь непредвиденные последствия в зависимости от окружающего кода. Поскольку IIFE — полноценная функция, граница функции меняет поведение некоторых выражений/конструкций.

@@ sec.ydkjs-scope.ch6.iife.b10
Например, выражение `return` в каком-то фрагменте кода изменит своё значение, если обернуть этот код в IIFE, потому что теперь `return` будет относиться к функции IIFE. IIFE на основе нестрелочных функций также меняют привязку ключевого слова `this` — подробнее об этом в книге *Objects & Classes*. А выражения вроде `break` и `continue` не будут работать через границу функции IIFE, чтобы управлять внешним циклом или блоком.

@@ sec.ydkjs-scope.ch6.iife.b11
Поэтому, если в коде, который нужно обернуть областью, есть `return`, `this`, `break` или `continue`, IIFE, вероятно, не лучший подход. В этом случае стоит создать область с помощью блока, а не функции.

@@ sec.ydkjs-scope.ch6.block-scoping.b0
К этому моменту ты уже должен хорошо понимать преимущества создания областей для ограничения открытости идентификаторов.

@@ sec.ydkjs-scope.ch6.block-scoping.b1
До сих пор мы делали это через область `function` (то есть IIFE). Но теперь рассмотрим использование объявлений `let` во вложенных блоках. В целом любая пара фигурных скобок `{ .. }`, являющаяся выражением, работает как блок, но **не обязательно** как область видимости.

@@ sec.ydkjs-scope.ch6.block-scoping.b2
Блок становится областью, только если это необходимо, чтобы содержать его блочные объявления (то есть `let` или `const`). Рассмотрим:

@@ sec.ydkjs-scope.ch6.block-scoping.b4
Не все пары фигурных скобок `{ .. }` создают блоки (а значит, могут стать областями видимости):

- Объектные литералы используют `{ .. }`, чтобы ограничить список пар ключ-значение, но такие объекты **не** являются областями видимости.
- `class` использует `{ .. }` вокруг определения тела, но это не блок и не область.
- `function` использует `{ .. }` вокруг тела, но технически это не блок — это единое выражение тела функции. Однако это *является* (функциональной) областью видимости.
- Пара `{ .. }` в выражении `switch` (вокруг набора `case`) не определяет блок/область.

@@ sec.ydkjs-scope.ch6.block-scoping.b5
Помимо таких неблочных примеров, пара `{ .. }` может определять блок, привязанный к выражению (например, `if` или `for`), или стоять сама по себе — см. самую внешнюю пару `{ .. }` в предыдущем фрагменте. Явный блок такого рода — если в нём нет объявлений, он на самом деле не область — не несёт никакой практической функции, хотя может быть полезен как семантический сигнал.

@@ sec.ydkjs-scope.ch6.block-scoping.b6
Явные самостоятельные блоки `{ .. }` всегда были допустимым синтаксисом JS, но поскольку до `let`/`const` из ES6 они не могли быть областями, они встречаются довольно редко. Однако после ES6 они понемногу набирают популярность.

@@ sec.ydkjs-scope.ch6.block-scoping.b7
В большинстве языков с поддержкой блочных областей явная блочная область — крайне распространённый паттерн для создания узкого среза области для одной или нескольких переменных. Поэтому, следуя принципу POLE, нам стоит шире использовать этот паттерн и в JS: применяй (явные) блочные области, чтобы сузить открытость идентификаторов до практического минимума.

@@ sec.ydkjs-scope.ch6.block-scoping.b8

@@ sec.ydkjs-scope.ch6.var-and-let.b0
Теперь поговорим об объявлении `var buckets`. Эта переменная используется во всей функции (кроме финального `return`). Любая переменная, нужная во всей (или хотя бы большей части) функции, должна быть объявлена так, чтобы такое использование было очевидно.

@@ sec.ydkjs-scope.ch6.var-and-let.b1
> **ПРИМЕЧАНИЕ:** Параметр `names` используется не во всей функции, но ограничить область параметра невозможно, поэтому он в любом случае ведёт себя как объявление уровня всей функции.

@@ sec.ydkjs-scope.ch6.var-and-let.b2
Так почему для объявления переменной `buckets` мы использовали `var`, а не `let`? Для выбора `var` здесь есть и семантические, и технические причины.

@@ sec.ydkjs-scope.ch6.var-and-let.b3
Стилистически `var` с самых ранних дней JS всегда сигнализировал «переменная, принадлежащая всей функции». Как мы утверждали в разделе «Лексическая область видимости» (глава 1), `var` привязывается к ближайшей охватывающей функциональной области, где бы он ни находился. Это верно, даже если `var` стоит внутри блока:

@@ sec.ydkjs-scope.ch6.var-and-let.b5
Хотя `var` находится внутри блока, его объявление имеет функциональную (в пределах `diff(..)`), а не блочную область.

@@ sec.ydkjs-scope.ch6.var-and-let.b6
Хотя `var` можно объявить внутри блока (и он всё равно будет функциональным), я бы не советовал так делать, кроме нескольких особых случаев (обсуждаются в Приложении A). В остальном `var` стоит оставлять для верхнего уровня области функции.

@@ sec.ydkjs-scope.ch6.var-and-let.b7
Почему бы просто не использовать `let` в том же месте? Потому что `var` визуально отличается от `let` и поэтому ясно сигнализирует: «эта переменная функциональная». `let` на верхнем уровне, особенно не в первых строках функции и когда все остальные объявления в блоках тоже используют `let`, визуально не привлекает внимания к отличию от объявления уровня функции.

@@ sec.ydkjs-scope.ch6.var-and-let.b8
Иными словами, я считаю, что `var` лучше передаёт функциональную область, чем `let`, а `let` и передаёт (и обеспечивает!) блочную область там, где `var` недостаточно. Пока твоим программам нужны и функциональные, и блочные переменные, самый разумный и читаемый подход — использовать `var` *и* `let` вместе, каждое по своему лучшему назначению.

@@ sec.ydkjs-scope.ch6.var-and-let.b9
Есть и другие семантические и практические причины выбирать `var` или `let` в разных сценариях. Аргументы в пользу `var` и `let` мы подробнее разберём в Приложении A.

@@ sec.ydkjs-scope.ch6.var-and-let.b10
> **ПРЕДУПРЕЖДЕНИЕ:** Моя рекомендация использовать и `var`, и `let` явно спорна и противоречит мнению большинства. Гораздо чаще можно услышать: «var сломан, let его исправляет» и «никогда не используй var, let — его замена». Эти мнения обоснованны, но это всего лишь мнения, как и моё. `var` фактически не сломан и не устарел; он работает с ранних дней JS и будет работать, пока существует JS.

@@ sec.ydkjs-scope.ch6.var-and-let.b11
## Где использовать `let`?

@@ sec.ydkjs-scope.ch6.var-and-let.b12
Мой совет оставлять `var` (в основном) только для верхнего уровня функциональной области означает, что большинство остальных объявлений должны использовать `let`. Но ты, возможно, всё ещё задаёшься вопросом, как решить, где должно находиться каждое объявление в программе?

@@ sec.ydkjs-scope.ch6.var-and-let.b13
POLE уже направляет тебя в этих решениях, но давай сформулируем это явно. Решение принимается не на основе того, какое ключевое слово ты хочешь использовать. Решать нужно, задав вопрос: «Какая минимальная открытость области достаточна для этой переменной?»

@@ sec.ydkjs-scope.ch6.var-and-let.b14

Если сначала ты решил, что переменная должна быть блочной, а потом понял, что её нужно поднять до функциональной, это требует изменить не только место её объявления, но и используемое ключевое слово. Процесс принятия решения действительно должен идти именно так.

@@ sec.ydkjs-scope.ch6.var-and-let.b15
Если объявление относится к блочной области, используй `let`. Если к функциональной — используй `var` (опять же, это лишь моё мнение).
