@@ sec.ydkjs-scope.ch4.intro.heading
Глава 4: Вокруг глобальной области видимости

@@ sec.ydkjs-scope.ch4.why-global.heading
Зачем глобальный scope?

@@ sec.ydkjs-scope.ch4.why-global.note
Этот раздел объясняет, **зачем** существуют современные инструменты сборки. До Vite/webpack каждый `<script>` бросал переменные в глобальный scope, и когда две библиотеки использовали одно имя, одна затирала другую.

Для защиты от этого сначала появились обёртки [[iife]], затем [[commonjs]], а теперь [[esm]]. Каждый этап решает одну и ту же проблему: **не загрязнять глобальный scope**.

@@ sec.ydkjs-scope.ch4.browser-window.heading
Где же этот глобальный scope? Браузерный «window»

@@ sec.ydkjs-scope.ch4.browser-window.note
Пример реального бага: имена вроде `var name`, `var status`, `var top` ведут себя в браузере неожиданно, потому что `window.name`, `window.status`, `window.top` уже существуют.

При переходе на модульную систему (Vite, React) эти проблемы исчезают — твои переменные верхнего уровня не попадают в глобальный объект. Но эти знания понадобятся при работе со старыми скриптами или библиотеками, подключёнными через тег `<script>`.

@@ sec.ydkjs-scope.ch4.web-workers.heading
Web Workers

@@ sec.ydkjs-scope.ch4.web-workers.note
Воркеры нужны, чтобы вынести тяжёлые вычисления (парсинг большого JSON, обработку изображений, поисковый индекс) из основного потока, чтобы интерфейс не зависал. Связь с основным потоком идёт только через `postMessage` — общих переменных нет, потому что глобальные области раздельны.

Создание воркера в Vite: `new Worker(new URL('./worker.ts', import.meta.url), { type: 'module' })`.

@@ sec.ydkjs-scope.ch4.devtools.heading
Консоль Developer Tools/REPL

@@ sec.ydkjs-scope.ch4.devtools.note
Практический пример: введи в консоли `let x = 1` и нажми Enter, затем снова `let x = 2` — Chrome это разрешит, хотя в настоящей программе это `SyntaxError`.

Правило: если хочешь проверить поведение scope/hoisting, напиши код в файле или запусти его небольшим тестом (Vitest). Консоль — для быстрых проверок, а не для доказательства спецификации.

@@ sec.ydkjs-scope.ch4.esm.heading
ES-модули (ESM)

@@ sec.ydkjs-scope.ch4.esm.note
Это и есть твой повседневный React/Vite-код: каждый файл `.tsx` — отдельный модуль. `const API_URL = ...`, написанный в начале файла, не виден из другого файла — только если сделать `export`.

Это полностью устраняет конфликты глобальных имён и делает возможным [[tree-shaking]]: неиспользуемые экспорты выбрасываются из бандла.

@@ sec.ydkjs-scope.ch4.node.heading
Node

@@ sec.ydkjs-scope.ch4.node.note
Что это значит для фронтенд-разработчика: `vite.config.ts`, конфиг ESLint и тестовые файлы выполняются в Node. Там нет `window`, а `__dirname` есть только в CommonJS (в ESM используется `import.meta.url`).

Ошибка «window is not defined» при SSR (Next.js) возникает именно поэтому: код компонента выполняется на сервере, то есть в Node.

@@ sec.ydkjs-scope.ch4.global-this.heading
Global This

@@ sec.ydkjs-scope.ch4.global-this.note
Сегодня практический ответ прост: если пишешь универсальный код (браузер + Node + воркер), используй `globalThis`. Все современные среды его поддерживают.

```js
if (typeof globalThis.fetch !== 'function') {
  // старая среда — загрузить полифил
}
```

@@ sec.ydkjs-scope.ch4.globally-aware.heading
Глобальная осведомлённость

@@ sec.ydkjs-scope.ch4.globally-aware.note
Таблица главы — обращение к глобальному объекту:

```text
Браузер (обычный скрипт) → window   (var/function становятся свойствами)
Web Worker               → self
Node                     → global   (файл = модуль, верхний уровень не глобальный)
ES-модуль                → верхний уровень — scope модуля, не глобальный
Везде                    → globalThis
```

@@ sec.ydkjs-scope.ch4.intro.b0
В главе 3 «глобальная область видимости» упоминалась несколько раз, но ты, возможно, всё ещё задаёшься вопросом, почему самая внешняя область программы так важна в современном JS. Подавляющая часть работы теперь выполняется внутри функций и модулей, а не глобально.

@@ sec.ydkjs-scope.ch4.intro.b1
Достаточно ли просто заявить: «Избегай глобальной области видимости» — и на этом закончить?

@@ sec.ydkjs-scope.ch4.intro.b2
[[global-scope]] JS-программы — богатая тема, в ней гораздо больше пользы и нюансов, чем ты, вероятно, предполагаешь. Эта глава сначала разбирает, чем глобальная область (всё ещё) полезна и актуальна для написания JS-программ сегодня, а затем рассматривает различия в том, где находится глобальная область и *как к ней обращаться* в разных JS-средах.

@@ sec.ydkjs-scope.ch4.intro.b3
Полное понимание глобальной области видимости критически важно для того, чтобы освоить построение программ с помощью лексической области видимости.

@@ sec.ydkjs-scope.ch4.why-global.b0
Читателей, скорее всего, не удивит, что большинство приложений состоит из нескольких (иногда многих!) отдельных JS-файлов. Так как же именно JS-движок сшивает все эти отдельные файлы в единый контекст выполнения?

@@ sec.ydkjs-scope.ch4.why-global.b1
Для приложений, выполняемых в браузере, есть три основных способа.

@@ sec.ydkjs-scope.ch4.why-global.b2
**Первый**: если ты напрямую используешь ES-модули (не транспилируя их в какой-то другой формат бандла модулей), эти файлы загружаются JS-средой по отдельности. Затем каждый модуль `import`-ирует ссылки на те модули, к которым ему нужен доступ. Отдельные файлы модулей взаимодействуют друг с другом исключительно через эти общие импорты, без какой-либо общей внешней области.

@@ sec.ydkjs-scope.ch4.why-global.b3
**Второй**: если в процессе сборки ты используешь [[bundler]], все файлы обычно склеиваются вместе до передачи в браузер и JS-движок, который затем обрабатывает только один большой файл. Даже когда все части приложения находятся в одном файле, нужен какой-то механизм, чтобы каждая часть регистрировала *имя*, по которому к ней будут обращаться другие части, а также какая-то возможность для такого обращения.

@@ sec.ydkjs-scope.ch4.why-global.b4
В некоторых сборках всё содержимое файла оборачивается в одну охватывающую область — функцию-обёртку, универсальный модуль (UMD — см. Приложение A) и т. п. Каждая часть может зарегистрировать себя для доступа из других частей через локальные переменные в этой общей области. Например:

Как показано, локальные переменные `moduleOne` и `moduleTwo` внутри области функции `wrappingOuterScope()` объявлены для того, чтобы эти модули могли обращаться друг к другу для совместной работы.

@@ sec.ydkjs-scope.ch4.why-global.b7
Хотя область `wrappingOuterScope()` — это функция, а не полноценная глобальная область среды, она действует как своего рода «область всего приложения» — ведро, в котором можно хранить все идентификаторы верхнего уровня, хотя и не в настоящей глобальной области. В этом смысле она нечто вроде заменителя глобальной области.

@@ sec.ydkjs-scope.ch4.why-global.b8
И наконец, **третий** способ: используется ли для приложения бандлер или (не ES-модульные) файлы просто загружаются в браузер по отдельности (через теги `<script>` или другую динамическую загрузку JS-ресурсов), — если нет единой охватывающей области для всех этих частей, **глобальная область** остаётся для них единственным способом взаимодействовать друг с другом.

@@ sec.ydkjs-scope.ch4.why-global.b14
Если эти файлы загружаются по отдельности как обычные самостоятельные .js-файлы в браузере, каждое объявление переменной верхнего уровня станет глобальной переменной, потому что глобальная область — единственный общий ресурс между этими двумя отдельными файлами: с точки зрения JS-движка это независимые программы.

@@ sec.ydkjs-scope.ch4.why-global.b15
Помимо того, что глобальная область (потенциально) определяет, где находится код приложения во время выполнения и как каждая часть может обращаться к другим частям для взаимодействия, это ещё и место, где:

- JS предоставляет свои встроенные возможности:
- примитивы: `undefined`, `null`, `Infinity`, `NaN`
- нативные конструкторы: `Date()`, `Object()`, `String()` и т. д.
- глобальные функции: `eval()`, `parseInt()` и т. д.
- пространства имён: `Math`, `Atomics`, `JSON`
- друзья JS: `Intl`, `WebAssembly`

@@ sec.ydkjs-scope.ch4.why-global.b16
- Среда, в которой работает JS-движок, предоставляет свои встроенные возможности:
- `console` (и его методы)
- DOM (`window`, `document` и т. д.)
- таймеры (`setTimeout(..)` и т. д.)
- API веб-платформы: `navigator`, `history`, геолокация, WebRTC и т. д.

@@ sec.ydkjs-scope.ch4.why-global.b17
Это лишь некоторые из множества *глобальных* сущностей, с которыми будут взаимодействовать твои программы.

@@ sec.ydkjs-scope.ch4.why-global.b18
> **ПРИМЕЧАНИЕ:** Node тоже предоставляет несколько элементов «глобально», но технически они не находятся в области `global`: `require()`, `__dirname`, `module`, `URL` и так далее.

@@ sec.ydkjs-scope.ch4.why-global.b19
Большинство разработчиков согласны, что глобальная область не должна быть свалкой для всех переменных приложения. Это куча багов, которые только и ждут своего часа. Но нельзя отрицать и того, что глобальная область — важный *клей* практически для любого JS-приложения.

@@ sec.ydkjs-scope.ch4.browser-window.b0
Может показаться очевидным, что глобальная область находится в самой внешней части файла, то есть не внутри какой-либо функции или другого блока. Но всё не так просто.

@@ sec.ydkjs-scope.ch4.browser-window.b1
Разные JS-среды по-разному обращаются с областями видимости твоих программ, особенно с глобальной. JS-разработчики довольно часто имеют неверные представления, даже не подозревая об этом.

## Что в имени (window)?

@@ sec.ydkjs-scope.ch4.browser-window.b28
Ещё одна странность глобальной области в браузерном JS:

@@ sec.ydkjs-scope.ch4.browser-window.b30
`window.name` — предопределённая «глобальная» сущность в браузере; это свойство глобального объекта, поэтому она выглядит как обычная глобальная переменная (но она какая угодно, только не «обычная»).

@@ sec.ydkjs-scope.ch4.browser-window.b31
Мы использовали для объявления `var`, который **не** затеняет предопределённое глобальное свойство `name`. Это значит, что объявление `var` фактически игнорируется, поскольку у объекта глобальной области уже есть свойство с таким именем. Как мы обсуждали ранее, если бы мы использовали `let name`, то затенили бы `window.name` отдельной глобальной переменной `name`.

@@ sec.ydkjs-scope.ch4.browser-window.b32
Но по-настоящему удивительно то, что хотя мы присвоили `name` (а значит, и `window.name`) число `42`, при чтении его значения мы получаем строку `"42"`! В этом случае странность объясняется тем, что `name` на самом деле — предопределённый геттер/сеттер объекта `window`, который настаивает на строковом значении. Ой!

@@ sec.ydkjs-scope.ch4.browser-window.b33
За исключением некоторых редких пограничных случаев вроде ID DOM-элементов и `window.name`, JS, работающий как самостоятельный файл на странице браузера, обладает одним из самых чистых поведений глобальной области, с которыми мы столкнёмся.

@@ sec.ydkjs-scope.ch4.web-workers.b0
[[web-worker]] — это расширение веб-платформы поверх поведения браузерного JS, которое позволяет JS-файлу работать в совершенно отдельном потоке (на уровне операционной системы) от потока, выполняющего основную JS-программу.

@@ sec.ydkjs-scope.ch4.web-workers.b1
Поскольку программы Web Worker работают в отдельном потоке, их взаимодействие с основным потоком приложения ограничено, чтобы избежать/ограничить состояния гонки и другие осложнения. Например, у кода Web Worker нет доступа к DOM. Однако некоторые веб-API, например `navigator`, воркеру доступны.

@@ sec.ydkjs-scope.ch4.web-workers.b2
Поскольку Web Worker считается полностью отдельной программой, он не разделяет глобальную область с основной JS-программой. Однако код всё равно выполняет JS-движок браузера, поэтому можно ожидать похожей чистоты поведения его глобальной области. Так как доступа к DOM нет, псевдонима `window` для глобальной области не существует.

@@ sec.ydkjs-scope.ch4.devtools.b0
Вспомни из главы 1 книги *Get Started*, что Developer Tools не создают полностью соответствующую спецификации JS-среду. Они обрабатывают JS-код, но при этом склоняются к тому, чтобы взаимодействие было максимально удобным для разработчиков (developer experience, DX).

@@ sec.ydkjs-scope.ch4.devtools.b1
В некоторых случаях предпочтение DX при вводе коротких фрагментов JS вместо обычных строгих шагов, ожидаемых при обработке полной JS-программы, приводит к наблюдаемым различиям в поведении кода между программами и инструментами. Например, некоторые ошибочные ситуации, применимые к JS-программе, могут смягчаться и не отображаться, когда код вводится в инструмент разработчика.

@@ sec.ydkjs-scope.ch4.devtools.b2
В отношении наших обсуждений области видимости такие наблюдаемые различия в поведении могут включать:

- Поведение глобальной области
- Hoisting (см. главу 5)
- Блочные объявления (`let` / `const`, см. главу 6) при использовании в самой внешней области

@@ sec.ydkjs-scope.ch4.devtools.b3
Хотя при работе с консолью/REPL может казаться, что выражения, введённые в самой внешней области, обрабатываются в настоящей глобальной области, это не совсем так. Такие инструменты обычно в той или иной мере эмулируют положение глобальной области; это эмуляция, а не строгое соответствие. Эти среды ставят на первое место удобство разработчика, а значит, иногда (как в наших текущих обсуждениях области видимости) наблюдаемое поведение может отклоняться от спецификации JS.

@@ sec.ydkjs-scope.ch4.devtools.b4
Вывод: Developer Tools, хотя и оптимизированы для удобства и пользы в самых разных задачах разработчика, **не** подходят для определения или проверки точных и тонких особенностей поведения реального контекста JS-программы.

@@ sec.ydkjs-scope.ch4.esm.b0
ES6 ввёл полноценную поддержку паттерна «модуль» (он рассматривается в главе 8). Одно из самых очевидных последствий использования [[esm]] — то, как меняется поведение видимой области верхнего уровня в файле.

@@ sec.ydkjs-scope.ch4.esm.b1
Вспомним фрагмент кода, приведённый ранее (адаптируем его к формату ESM с помощью ключевого слова `export`):

Если этот код находится в файле, загружаемом как ES-модуль, он по-прежнему будет работать точно так же. Однако наблюдаемые эффекты с точки зрения приложения в целом будут другими.

@@ sec.ydkjs-scope.ch4.esm.b4
Несмотря на то что `studentName` и `hello` объявлены на верхнем уровне (модульного) файла, в самой внешней очевидной области, это не глобальные переменные. Они действуют в пределах модуля, или, если угодно, являются «модульно-глобальными».

@@ sec.ydkjs-scope.ch4.esm.b5
Однако в модуле нет неявного «объекта области всего модуля», в который эти объявления верхнего уровня добавлялись бы как свойства, как это происходит с объявлениями на верхнем уровне немодульных JS-файлов. Это не значит, что в таких программах не может быть глобальных переменных или к ним нельзя обратиться. Просто объявление переменных в области верхнего уровня модуля не *создаёт* глобальных переменных.

@@ sec.ydkjs-scope.ch4.esm.b6
Область верхнего уровня модуля происходит от глобальной области — почти так, будто всё содержимое модуля обёрнуто в функцию. Поэтому все переменные, существующие в глобальной области (независимо от того, есть ли они на глобальном объекте!), доступны как лексические идентификаторы изнутри области модуля.

@@ sec.ydkjs-scope.ch4.esm.b7
ESM поощряет минимальную зависимость от глобальной области: ты импортируешь те модули, которые нужны текущему модулю для работы. Поэтому использование глобальной области или её глобального объекта встречается реже.

@@ sec.ydkjs-scope.ch4.esm.b8
Однако, как отмечалось ранее, по-прежнему существует множество глобальных сущностей JS и веба, к которым ты будешь обращаться из глобальной области, осознаёшь ты это или нет!

@@ sec.ydkjs-scope.ch4.node.b0
Одна особенность Node, которая часто застаёт JS-разработчиков врасплох: Node считает *модулем* (ES-модулем или модулем CommonJS, см. главу 8) каждый загружаемый .js-файл, включая главный, с которого ты запускаешь процесс Node. На практике это значит, что верхний уровень твоих Node-программ **никогда** не является глобальной областью, в отличие от загрузки немодульного файла в браузере.

@@ sec.ydkjs-scope.ch4.global-this.b0
Если подытожить рассмотренные JS-среды, программа может как делать, так и не делать следующее:

- Объявлять глобальную переменную в области верхнего уровня через объявления `var` или `function` — или через `let`, `const` и `class`.
- Также добавлять объявления глобальных переменных как свойства объекта глобальной области, если для объявления используются `var` или `function`.
- Обращаться к объекту глобальной области (чтобы добавлять или читать глобальные переменные как свойства) через `window`, `self` или `global`.
