@@ sec.ydkjs-scope.ch4.intro.heading
Глава 4: Вокруг глобальной области видимости

@@ sec.ydkjs-scope.ch4.intro.b0
В главе 3 несколько раз упоминался «глобальный scope», но ты, возможно, всё ещё задаёшься вопросом, почему самая внешняя область программы так важна в современном JS. Подавляющая часть работы теперь выполняется внутри функций и модулей, а не глобально. Достаточно ли просто сказать «не используй глобальный scope» и на этом закончить?

@@ sec.ydkjs-scope.ch4.intro.b1
[[global-scope]] JS-программы — богатая тема, в ней гораздо больше пользы и нюансов, чем ты, вероятно, предполагаешь. Эта глава сначала рассматривает, чем глобальный scope (всё ещё) полезен и актуален при написании JS-программ сегодня, а затем — различия в том, где и как получить к нему доступ в разных JS-средах.

@@ sec.ydkjs-scope.ch4.why-global.heading
Зачем глобальный scope?

@@ sec.ydkjs-scope.ch4.why-global.b0
Большинство приложений состоит из нескольких (иногда многих!) отдельных JS-файлов. Как же JS-движок сшивает все эти файлы в единый контекст выполнения? Для приложений, выполняемых в браузере, есть три основных способа.

@@ sec.ydkjs-scope.ch4.why-global.b1
**Во-первых**, если ты напрямую используешь ES-модули (не транспилируя их в другой формат бандла), эти файлы загружаются JS-средой по отдельности. Каждый модуль затем через `import` получает ссылки на нужные ему модули. Отдельные файлы модулей взаимодействуют друг с другом исключительно через эти общие импорты, без необходимости в общем внешнем scope.

@@ sec.ydkjs-scope.ch4.why-global.b2
**Во-вторых**, если в процессе сборки используется [[bundler]], все файлы обычно склеиваются перед отправкой в браузер, и движок обрабатывает только один большой файл. В некоторых конфигурациях сборки всё содержимое файла оборачивается в единый охватывающий scope, например в функцию-обёртку. Каждая часть может зарегистрировать себя для других частей через локальные переменные в этом общем scope:

@@ sec.ydkjs-scope.ch4.why-global.b4
Хотя scope `wrappingOuterScope()` — это функция, а не глобальный scope всей среды, он играет роль своего рода «общеприкладного scope» — корзины, где могут храниться все идентификаторы верхнего уровня, но не в настоящем глобальном scope.

@@ sec.ydkjs-scope.ch4.why-global.b5
**И наконец, третий способ:** если нет единого scope, охватывающего все части (например, файлы загружаются по отдельности через теги `<script>`), глобальный scope — единственный способ для них взаимодействовать. Каждое объявление переменной верхнего уровня становится глобальной переменной, так как глобальный scope — единственный общий ресурс между этими файлами: с точки зрения JS-движка это независимые программы.

@@ sec.ydkjs-scope.ch4.why-global.b6
Глобальный scope — это также место, где JS предоставляет свои встроенные сущности (`undefined`, `null`, `Infinity`, `NaN`; `Date()`, `Object()`, `String()`; `eval()`, `parseInt()`; `Math`, `JSON`; `Intl`, `WebAssembly`), и где среда, в которой работает движок, предоставляет свои (`console`; DOM — `window`, `document`; таймеры — `setTimeout(..)`; API веб-платформы — `navigator`, `history`, геолокация, WebRTC).

@@ sec.ydkjs-scope.ch4.why-global.b7
Большинство разработчиков согласны, что глобальный scope не должен быть свалкой для всех переменных приложения. Это клубок багов, которые только и ждут своего часа. Но также бесспорно, что глобальный scope — важный «клей» практически для любого JS-приложения.

@@ sec.ydkjs-scope.ch4.why-global.note
Этот раздел объясняет, **зачем** существуют современные инструменты сборки. До Vite/webpack каждый `<script>` бросал переменные в глобальный scope, и когда две библиотеки использовали одно имя, одна затирала другую.

Для защиты от этого сначала появились обёртки [[iife]], затем [[commonjs]], а теперь [[esm]]. Каждый этап решает одну и ту же проблему: **не загрязнять глобальный scope**.

@@ sec.ydkjs-scope.ch4.browser-window.heading
Где же этот глобальный scope? Браузерный «window»

@@ sec.ydkjs-scope.ch4.browser-window.b0
Может показаться очевидным, что глобальный scope находится в самой внешней части файла, то есть не внутри какой-либо функции или блока. Но всё не так просто. Разные JS-среды по-разному обрабатывают области видимости программ, особенно глобальную.

С точки зрения обращения с глобальным scope самая «чистая» среда для JS — отдельный .js-файл, загруженный на веб-страницу в браузере:

Необычное следствие различия между глобальной переменной и одноимённым глобальным свойством: даже внутри самого глобального scope свойство глобального объекта может быть затенено глобальной переменной:

Создавать расхождение между глобальным объектом и глобальным scope — почти наверняка плохая идея. Простой способ избежать этой ловушки с глобальными объявлениями: всегда используй `var` для глобальных переменных. Оставь `let` и `const` для блочных областей.

@@ sec.ydkjs-scope.ch4.browser-window.b7
## Глобальные переменные DOM

@@ sec.ydkjs-scope.ch4.browser-window.b8
Одно удивительное поведение глобального scope в браузерных JS-приложениях: DOM-элемент с атрибутом `id` автоматически создаёт глобальную переменную, ссылающуюся на него.

@@ sec.ydkjs-scope.ch4.browser-window.b10
Автоматическая регистрация всех DOM-элементов с `id` как глобальных переменных — старое унаследованное поведение браузеров, которое тем не менее должно сохраняться, потому что на него всё ещё полагаются многие старые сайты. Мой совет: никогда не используй эти глобальные переменные, хотя они всегда будут молча создаваться.

@@ sec.ydkjs-scope.ch4.browser-window.b11
## Что в имени (window)?

@@ sec.ydkjs-scope.ch4.browser-window.b13
`window.name` — заранее определённая «глобальная» в браузере. Мы использовали для объявления `var`, который не затеняет предопределённое глобальное свойство `name`, так что объявление `var` фактически игнорируется. И хотя мы присвоили число `42`, при чтении получаем строку `"42"`! Странность в том, что `name` на самом деле — предопределённый геттер/сеттер объекта `window`, который настаивает, чтобы значение было строкой. Ой!

@@ sec.ydkjs-scope.ch4.browser-window.note
Пример реального бага: имена вроде `var name`, `var status`, `var top` ведут себя в браузере неожиданно, потому что `window.name`, `window.status`, `window.top` уже существуют.

При переходе на модульную систему (Vite, React) эти проблемы исчезают — твои переменные верхнего уровня не попадают в глобальный объект. Но эти знания понадобятся при работе со старыми скриптами или библиотеками, подключёнными через тег `<script>`.

@@ sec.ydkjs-scope.ch4.web-workers.heading
Web Workers

@@ sec.ydkjs-scope.ch4.web-workers.b0
[[web-worker]] — расширение веб-платформы поверх поведения браузерного JS, позволяющее JS-файлу выполняться в полностью отдельном потоке (на уровне операционной системы) от потока основной JS-программы. Например, у кода Web Worker нет доступа к DOM. Однако некоторые веб-API ему доступны, например `navigator`.

@@ sec.ydkjs-scope.ch4.web-workers.b1
Поскольку Web Worker считается полностью отдельной программой, он не делит глобальный scope с основной JS-программой. Так как доступа к DOM нет, псевдонима `window` для глобального scope не существует. В Web Worker на глобальный объект обычно ссылаются через `self`:

@@ sec.ydkjs-scope.ch4.web-workers.note
Воркеры нужны, чтобы вынести тяжёлые вычисления (парсинг большого JSON, обработку изображений, поисковый индекс) из основного потока, чтобы интерфейс не зависал. Связь с основным потоком идёт только через `postMessage` — общих переменных нет, потому что глобальные области раздельны.

Создание воркера в Vite: `new Worker(new URL('./worker.ts', import.meta.url), { type: 'module' })`.

@@ sec.ydkjs-scope.ch4.devtools.heading
Консоль Developer Tools/REPL

@@ sec.ydkjs-scope.ch4.devtools.b0
Developer Tools не создают полностью соответствующую стандарту JS-среду. Они обрабатывают JS-код, но склоняются к тому, чтобы взаимодействие было максимально удобным для разработчиков (developer experience, DX). Некоторые ошибочные ситуации, применимые к JS-программе, при вводе кода в инструмент разработчика могут смягчаться и не отображаться.

@@ sec.ydkjs-scope.ch4.devtools.b1
Применительно к нашим обсуждениям scope такие наблюдаемые различия могут касаться: поведения глобального scope; hoisting (см. главу 5); блочных объявлений (`let` / `const`, см. главу 6) при использовании в самой внешней области.

@@ sec.ydkjs-scope.ch4.devtools.b2
Вывод: Developer Tools, хотя и оптимизированы для удобства и пользы в самых разных задачах разработчика, не подходят для определения или проверки точных и тонких особенностей поведения реального контекста JS-программы.

@@ sec.ydkjs-scope.ch4.devtools.note
Практический пример: введи в консоли `let x = 1` и нажми Enter, затем снова `let x = 2` — Chrome это разрешит, хотя в настоящей программе это `SyntaxError`.

Правило: если хочешь проверить поведение scope/hoisting, напиши код в файле или запусти его небольшим тестом (Vitest). Консоль — для быстрых проверок, а не для доказательства спецификации.

@@ sec.ydkjs-scope.ch4.esm.heading
ES-модули (ESM)

@@ sec.ydkjs-scope.ch4.esm.b0
ES6 ввёл полноценную поддержку паттерна «модуль» (он рассматривается в главе 8). Одно из самых заметных последствий использования [[esm]] — изменение поведения видимого верхнего уровня файла.

@@ sec.ydkjs-scope.ch4.esm.b2
Хотя `studentName` и `hello` объявлены на верхнем уровне файла (модуля), в самом внешнем видимом scope, они не глобальные переменные. Они уровня модуля или, если угодно, «модульно-глобальные». Однако в модуле нет неявного «объекта scope модуля», куда эти объявления добавлялись бы как свойства.

@@ sec.ydkjs-scope.ch4.esm.b3
Scope верхнего уровня модуля происходит от глобального scope — почти как если бы всё содержимое модуля было обёрнуто в функцию. Поэтому все переменные глобального scope (находятся ли они на глобальном объекте или нет!) доступны как лексические идентификаторы изнутри scope модуля. ESM поощряет минимальную зависимость от глобального scope: ты делаешь `import` тех модулей, которые нужны текущему модулю для работы.

@@ sec.ydkjs-scope.ch4.esm.note
Это и есть твой повседневный React/Vite-код: каждый файл `.tsx` — отдельный модуль. `const API_URL = ...`, написанный в начале файла, не виден из другого файла — только если сделать `export`.

Это полностью устраняет конфликты глобальных имён и делает возможным [[tree-shaking]]: неиспользуемые экспорты выбрасываются из бандла.

@@ sec.ydkjs-scope.ch4.node.heading
Node

@@ sec.ydkjs-scope.ch4.node.b0
Одна особенность Node, которая часто застаёт JS-разработчиков врасплох: Node считает модулем (ES-модулем или CommonJS-модулем) каждый загружаемый .js-файл, включая главный, с которого запускается процесс. Практическое следствие: верхний уровень Node-программ никогда не является глобальным scope так, как при загрузке немодульного файла в браузере.

@@ sec.ydkjs-scope.ch4.node.b1
С самого начала Node поддерживает формат модулей [[commonjs]]. Перед обработкой Node фактически оборачивает такой код в функцию, чтобы объявления `var` и `function` оставались в scope этой функции-обёртки и не считались глобальными переменными:

@@ sec.ydkjs-scope.ch4.node.cap2
Как Node видит CommonJS-файл (иллюстрация, не реальный код)

@@ sec.ydkjs-scope.ch4.node.b3
Node определяет ряд «глобальных» вроде `require()`, но на самом деле это не идентификаторы глобального scope (и не свойства глобального объекта). Они внедряются в scope каждого модуля — по сути, как параметры, перечисленные в объявлении функции `Module(..)`.

@@ sec.ydkjs-scope.ch4.node.b4
Как же определить настоящую глобальную переменную в Node? Единственный способ — добавить свойство в ещё одну автоматически предоставляемую Node «глобальную», которая по иронии называется `global`. `global` — ссылка на настоящий объект глобального scope, примерно как `window` в браузере. Помни: идентификатор `global` определяет не JS, а именно Node.

@@ sec.ydkjs-scope.ch4.node.note
Что это значит для фронтенд-разработчика: `vite.config.ts`, конфиг ESLint и тестовые файлы выполняются в Node. Там нет `window`, а `__dirname` есть только в CommonJS (в ESM используется `import.meta.url`).

Ошибка «window is not defined» при SSR (Next.js) возникает именно поэтому: код компонента выполняется на сервере, то есть в Node.

@@ sec.ydkjs-scope.ch4.global-this.heading
Global This

@@ sec.ydkjs-scope.ch4.global-this.b0
Если подытожить рассмотренные JS-среды, программа может (или не может): объявить глобальную переменную на верхнем уровне через `var` или `function` — либо `let`, `const` и `class`; при использовании `var` или `function` также добавить объявления как свойства объекта глобального scope; обращаться к объекту глобального scope через `window`, `self` или `global`.

@@ sec.ydkjs-scope.ch4.global-this.b1
Начиная с ES2020 в JS наконец появилась стандартная ссылка на объект глобального scope — [[globalthis]]. Так что, если движки, в которых работает твой код, достаточно свежие, вместо всех прочих подходов можно использовать `globalThis`.

@@ sec.ydkjs-scope.ch4.global-this.cap2
Полифил для сред без globalThis

@@ sec.ydkjs-scope.ch4.global-this.b3
Предложенное имя `globalThis` вызвало немало споров, когда эту возможность добавляли в JS. В частности, я и многие другие считали слово «this» в названии вводящим в заблуждение, ведь к этому объекту обращаются, чтобы получить доступ к глобальному scope, а не к какой-то глобальной привязке `this` по умолчанию.

@@ sec.ydkjs-scope.ch4.global-this.note
Сегодня практический ответ прост: если пишешь универсальный код (браузер + Node + воркер), используй `globalThis`. Все современные среды его поддерживают.

```js
if (typeof globalThis.fetch !== 'function') {
  // старая среда — загрузить полифил
}
```

@@ sec.ydkjs-scope.ch4.globally-aware.heading
Глобальная осведомлённость

@@ sec.ydkjs-scope.ch4.globally-aware.b0
Глобальный scope присутствует и актуален в каждой JS-программе, хотя современные подходы к организации кода в модули во многом снижают зависимость от хранения идентификаторов в этом пространстве имён.

@@ sec.ydkjs-scope.ch4.globally-aware.b1
И всё же, поскольку наш код всё больше выходит за пределы браузера, особенно важно хорошо понимать, как глобальный scope (и объект глобального scope!) ведёт себя в разных JS-средах.

@@ sec.ydkjs-scope.ch4.globally-aware.note
Таблица главы — обращение к глобальному объекту:

```text
Браузер (обычный скрипт) → window   (var/function становятся свойствами)
Web Worker               → self
Node                     → global   (файл = модуль, верхний уровень не глобальный)
ES-модуль                → верхний уровень — scope модуля, не глобальный
Везде                    → globalThis
```
