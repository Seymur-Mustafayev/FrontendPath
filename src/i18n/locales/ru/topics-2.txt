@@ topic.js.5.t
DOM API и обработка событий

@@ topic.js.5.body
В DOM событие сначала спускается вниз, а затем поднимается вверх — механизм [[bubbling]]. Использовать его, чтобы повесить один [[event-listener]] на родителя, а не на каждую строку списка, называется [[event-delegation]].

В React напрямую работать с DOM приходится редко, но закрытие по клику снаружи, отслеживание размеров (ResizeObserver) и горячие клавиши всё ещё требуют этих знаний. Для каждого добавленного слушателя продумай очистку — иначе получишь [[memory-leak]].

@@ topic.async.0.t
Promise, async/await и обработка ошибок

@@ topic.async.0.body
[[promise]] представляет будущий результат; [[async-await]] позволяет записать его в читаемом виде. Вокруг каждого await нужно продумать [[try-catch]] — необработанный rejection означает тихую поломку в продакшене.

Последовательно ждать независимые друг от друга запросы — самая частая ошибка производительности; запускай их параллельно через [[promise-all]]. Если даже при неудаче одного остальные всё равно нужны, выбирай Promise.allSettled.

@@ topic.async.0.note
Блок finally идеально подходит, чтобы выключить состояние загрузки: он срабатывает и при успехе, и при ошибке.

@@ topic.async.1.t
fetch, отмена, таймаут и повторные попытки

@@ topic.async.1.body
[[fetch]] не выбрасывает ошибку на 404 и 500 — проверка res.ok остаётся на тебе. Это один из самых частых скрытых багов в коде junior-разработчиков.

Если поисковый запрос уходит по мере ввода, отменяй старый через [[abort-controller]]; иначе ответы перемешаются и на экран попадёт устаревший результат. Для сетевых ошибок нужна стратегия [[retry]] (с нарастающей задержкой) — TanStack Query даёт её из коробки.

@@ topic.async.2.t
Правильное чтение REST API на стороне потребителя

@@ topic.async.2.body
На что обращать внимание при работе с [[rest]] API: формат [[pagination]] (offset/limit или cursor), правила именования фильтров, формат дат (ISO 8601 и часовой пояс) и структура ответа с ошибкой.

Понятие [[idempotent]] пригождается в проблеме повторного клика: если POST повторится, могут создаться два заказа — нужно блокировать кнопку в UI или запрашивать у сервера ключ идемпотентности.

@@ topic.async.3.t
Аутентификация: JWT, cookie и процесс обновления

@@ topic.async.3.body
[[jwt]] — подписанный токен, и его содержимое не зашифровано: секреты туда не кладут. Где его хранить — это решение о безопасности: [[http-only-cookie]] намного лучше localStorage с точки зрения защиты от XSS.

Access token живёт недолго и по истечении обновляется через [[refresh-token]]. На фронтенде это нужно один раз настроить в interceptor и направить все параллельные 401 в единственный запрос обновления. В корпоративной среде вход часто идёт через [[oauth]]/OIDC.

@@ topic.async.4.t
CORS, preflight и политика same-origin

@@ topic.async.4.body
Политика [[same-origin]] — основа безопасности браузера. Когда запрос уходит на другой домен, заголовки [[cors]] разрешают прочитать ответ; при нестандартных заголовках или PUT/DELETE сначала отправляется [[preflight]]-запрос OPTIONS.

Важный нюанс: проблема CORS не решается на фронтенде — заголовки ответа должен отдавать сервер. Прокси в dev-среде — временное решение, для продакшена нужна настройка бэкенда.

@@ topic.async.4.note
Эту тему часто спрашивают на собеседованиях, и ответа «я написал прокси» недостаточно — объясни механизм.

@@ topic.async.5.t
Real-time: WebSocket, SSE и polling

@@ topic.async.5.body
Для живых данных есть три варианта: простой [[polling]] (запросы по интервалу), однонаправленный [[sse]] и двусторонний [[websocket]].

Выбор зависит от требований: для уведомлений и живого статуса хватит SSE, для чата и совместной работы нужен WebSocket. Разрыв соединения, переподключение и очистка при размонтировании компонента — забыть эту часть значит пойти классическим путём к утечке памяти.

@@ topic.ts.0.t
Основы системы типов и вывод типов

@@ topic.ts.0.body
[[static-typing]] ловит ошибку в момент написания, а не во время выполнения. Благодаря [[type-inference]] не нужно везде писать аннотации — тип возвращаемого значения функции TS часто выводит сам.

Ограничить возможные значения через [[union-type]] и [[literal-type]] — самый простой способ смоделировать состояние UI: status: 'idle' | 'loading' | 'error'.

@@ topic.ts.1.t
interface, type и дженерики

@@ topic.ts.1.body
[[interface]] удобен для формы объектов и расширения, а type силён в union, кортежах и условных типах. На практике важно, чтобы команда придерживалась единого правила.

[[generic]] — основа переиспользуемого кода: например, useApi<Order[]>(). Через [[constraint]] ты ограничиваешь, что принимает дженерик: <T extends {id:number}>. Хороший дженерик делает API гибким, а избыток дженериков делает код нечитаемым.

@@ topic.ts.2.t
Вывод новых типов из существующих через utility types

@@ topic.ts.2.body
Набор [[utility-type]] убирает дублирование: [[partial]] для PATCH DTO, [[pick-omit]] для исключения чувствительных полей, [[record]] для словарей.

Главный принцип: не копируй тип вручную, выводи его из существующего. Когда источник меняется, производные типы подстраиваются автоматически, и ничего не устаревает.

@@ topic.ts.3.t
Narrowing, type guard и discriminated union

@@ topic.ts.3.body
[[narrowing]] — это спуск от union-типа к конкретному типу с помощью проверок typeof, in, Array.isArray. В сложных случаях ты пишешь собственную функцию [[type-guard]].

Самый мощный приём — [[discriminated-union]]: модель {status:'success', data} | {status:'error', message} делает невозможные комбинации (одновременно loading и data) невозможными на уровне типа. Если добавить в switch исчерпывающую проверку через [[never]], компилятор сам найдёт тебя, когда появится новый вариант.

@@ topic.ts.3.note
Это самое заметное отличие TS уровня junior от TS уровня middle — единая модель состояния вместо кучи булевых isLoading/isError.

@@ topic.ts.4.t
Типобезопасность на границе API (Zod)

@@ topic.ts.4.body
Во время выполнения типов TS не существует. Значит, если API вернёт неправильные данные, тип тебе солжёт. Решение — [[schema-validation]] на границе: схема [[zod]] и проверяет данные, и сама выводит TS-тип.

Правило: принимай внешние данные как [[unknown-type]], проверь их и только потом используй. [[type-assertion]] (as) — это не проверка, а просто обещание; на границе его избегай.

@@ topic.ts.5.t
tsconfig, строгий режим и конфигурация

@@ topic.ts.5.body
[[strict-mode]] должен быть включён; особенно strictNullChecks, который блокирует большую часть багов с null/undefined. Настройка алиасов через paths в [[tsconfig]] делает пути импорта чище.

Если у JS-библиотеки нет типов, пишется [[declaration-file]]. В CI tsc --noEmit нужно запускать отдельным шагом — сборка Vite/Next не всегда полностью проверяет типы.

@@ topic.react.0.t
Компоненты, props, JSX и композиция

@@ topic.react.0.body
[[component]] — функция, которая принимает props и возвращает [[jsx]]. [[props]] только для чтения — потомок их не меняет; если нужно что-то изменить, наверх передаётся колбэк.

В React повторное использование строится не на наследовании, а на [[composition]]: передача children, render prop, компонентов в виде слотов. Если видишь компонент с разбухающими конфиг-пропсами, это обычно сигнал, что его нужно разделить через композицию.

@@ topic.react.1.t
State, ре-рендер и батчинг

@@ topic.react.1.body
Когда меняется [[state]], функция компонента вызывается заново — это называется [[re-render]]. Важный нюанс: ре-рендер не означает обновления DOM; React сравнивает виртуальный результат и применяет только разницу.

React 18+ с помощью [[batching]] объединяет несколько setState в один рендер, даже в асинхронном коде. Держи состояние как можно ближе к месту использования — поднятое наверх состояние заставляет перерендериваться всё дерево.

@@ topic.react.2.t
useEffect и управление побочными эффектами

@@ topic.react.2.body
[[useeffect]] нужен для синхронизации с внешним миром после рендера: подписки, таймеры, аналитика, измерения DOM — то есть [[side-effect]]. Это не должен быть первый выбор для загрузки данных; серверные данные — задача TanStack Query или серверного компонента.

[[dependency-array]] определяет, когда эффект запустится снова; отключить правило exhaustive-deps — значит спрятать проблему, а не решить её. Если настраиваешь подписку или таймер, обязательно возвращай [[cleanup]].

@@ topic.react.2.note
Спроси себя: «Этот эффект синхронизирует с внешним миром или это можно просто вычислить во время рендера?» Если второе — эффект не нужен.

@@ topic.react.3.t
Формы: controlled, uncontrolled и React Hook Form

@@ topic.react.3.body
[[controlled-component]] даёт полный контроль, но перерендеривается на каждый символ. В больших формах подход [[uncontrolled]] (значение хранится в DOM и читается через ref) быстрее.

[[react-hook-form]] — практичный баланс между ними: минимум ре-рендеров, валидация через Zod resolver, простой вывод ошибок. При работе с DevExtreme Form ты применяешь те же принципы через его собственный механизм валидации — важно, чтобы правила валидации хранились в одном источнике (в схеме).

@@ topic.react.4.t
Кастомные хуки и разделение логики

@@ topic.react.4.body
[[custom-hook]] — стандартный способ вынести логику хуков из компонента: useOrders, useDebouncedValue, usePermissions. Тогда компонент показывает «что», а не «как» — [[separation-of-concerns]].

[[rules-of-hooks]] нарушать нельзя: хук нельзя вызывать внутри условия, цикла или после раннего return, потому что React сопоставляет хуки по порядку. Хороший кастомный хук делает одну вещь и возвращает понятный интерфейс.

@@ topic.react.5.t
Context API и prop drilling

@@ topic.react.5.body
[[prop-drilling]] — передача одних и тех же props вниз через несколько уровней; в малом масштабе это не проблема, а при росте решается через [[context]] или композицию.

У контекста есть ловушка производительности: когда меняется value у [[provider]], перерендериваются все потребители. Поэтому стабилизируй value через useMemo и выноси часто меняющиеся данные в отдельный контекст. Context — не глобальный менеджер состояния; для серверных данных его не используй.

@@ topic.react.6.t
Производительность: memo, useMemo, useCallback

@@ topic.react.6.body
[[react-memo]] не даёт компоненту перерендериться, если props не изменились. Но если в props есть объект или функция, создаваемые заново на каждом рендере, memo ломается — причина в [[referential-equality]]. [[usecallback]] сохраняет стабильной ссылку на функцию, [[usememo]] — результат вычисления.

Самое важное правило: сначала измерь, потом оптимизируй. С помощью [[profiler]] посмотри, какой компонент и сколько рендерится. Рассыпать useMemo повсюду — значит утяжелить код, и это само по себе стоит ресурсов. В будущем React Compiler автоматизирует большую часть этого, но знать причину всё равно необходимо.

@@ topic.react.6.note
Здесь твоё слабое место пересекается с тестированием: проверка мемоизации в тесте через счётчик рендеров — смотри тему «Тест мемоизации» в пути Testing.

@@ topic.react.7.t
Error boundary, Suspense и ленивая загрузка

@@ topic.react.7.body
[[error-boundary]] перехватывает ошибку рендера и показывает запасной UI; без него ошибка одного компонента превращает всё приложение в белый экран. На уровне маршрута должен быть хотя бы один.

[[suspense]] показывает fallback для ещё не готового контента и вместе с React.lazy позволяет делать [[code-splitting]]. Если так отделить тяжёлые страницы (отчёты, графики, редакторы), первая загрузка станет заметно легче.

@@ topic.state.0.t
Client state и server state

@@ topic.state.0.body
[[client-state]] относится только к UI: открытое модальное окно, выбранная вкладка, черновик формы. [[server-state]] живёт на сервере, устаревает, может быть изменён другим пользователем и должен кэшироваться.

Эти два вида требуют разных инструментов. Когда ты вручную копируешь серверные данные в глобальный store, ты фактически начинаешь писать менеджер кэша — синхронизация, устаревание, повторные попытки. Готовая библиотека справляется с этим лучше.

@@ topic.state.1.t
Server state с TanStack Query

@@ topic.state.1.body
[[tanstack-query]] кэширует данные по [[query-key]]. Когда ключ меняется, новый запрос уходит автоматически — если положить фильтры в ключ, избавишься от кучи useEffect.

[[stale-time]] задаёт, сколько данные считаются свежими: при 0 [[refetch]] происходит при каждом фокусе, при большом значении показываются старые данные. На экране отчётов разумен большой staleTime, на экране остатков — маленький. Научись принимать это решение осознанно.

@@ topic.state.1.note
В системах вроде AIPOS типичная ошибка — задавать одинаковый staleTime для часто меняющихся данных (остатки, статус заказа) и стабильных (каталог, единицы измерения).

@@ topic.state.2.t
Мутации, инвалидация и optimistic update

@@ topic.state.2.body
Операция, которая записывает данные, — это [[mutation]]. Стандартный шаг после успеха — [[cache-invalidation]]: пометить изменившиеся списки как устаревшие и обновить их.

Для ощущения скорости используют [[optimistic-update]]: UI обновляется сразу, а при ошибке выполняется [[rollback]]. Этот подход не бесплатный — логику onSuccess/onError/onSettled нужно написать правильно. Для простых и редких операций достаточно инвалидации.

@@ topic.state.3.t
Глобальный client state с Zustand и Redux Toolkit

@@ topic.state.3.body
[[zustand]] даёт глобальное клиентское состояние с минимумом шаблонного кода; [[redux-toolkit]] силён в больших командах благодаря строгому порядку и поддержке DevTools.

Главное правило производительности в обоих одинаково: подписывайся через [[selector]] только на нужную часть, а не на весь [[store]]. Иначе каждое изменение store перерендеривает все компоненты.

@@ topic.state.4.t
URL как состояние

@@ topic.state.4.body
Фильтры, номер страницы, поисковый запрос и выбранная вкладка часто должны быть [[url-state]]. Причина проста: ссылкой можно поделиться, кнопка «назад» работает, а при перезагрузке страницы состояние не теряется.

Значения [[query-param]] читаются и записываются через хук [[search-params]], и те же значения передаются в query key — так URL, кэш и UI объединяются вокруг единого источника истины.
