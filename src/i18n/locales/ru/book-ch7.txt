Увидеть замыкание

@@ sec.ydkjs-scope.ch7.adding-up.heading
Складываем замыкания

@@ sec.ydkjs-scope.ch7.adding-up.note
Это ключевой механизм React: каждый рендер — новый вызов функции компонента, значит, каждый созданный внутри обработчик — **новый экземпляр**, замкнутый на переменные **этого рендера**.

```js
function Counter() {
  const [count, setCount] = useState(0);
  const log = () => console.log(count);   // count этого рендера
  return <button onClick={log}>{count}</button>;
}
```

Отсюда и «устаревшее замыкание» (stale closure): функция, созданная в старом рендере, видит старый `count`.

@@ sec.ydkjs-scope.ch7.live-link.heading
Живая связь, а не снимок

@@ sec.ydkjs-scope.ch7.live-link.note
**Замыкание хранит переменную, а не значение** — самая важная фраза главы.

В React ты видишь обратную сторону: `count` — это `const`, и каждый рендер создаёт новую переменную, поэтому старое замыкание видит старую переменную (старое значение). Решения:

```js
setCount((c) => c + 1);          // функциональное обновление — берёт последнее значение
const ref = useRef(count);       // ref — одна «переменная» на все рендеры
```

`useRef` работает ровно как `count` в `makeCounter`: одна переменная, много читателей.

@@ sec.ydkjs-scope.ch7.common-closures.heading
Обычные замыкания: Ajax и события

@@ sec.ydkjs-scope.ch7.common-closures.note
Почти весь асинхронный код, который ты пишешь на фронтенде, — это замыкания:

```js
async function loadUser(id) {
  const res = await fetch(`/api/users/${id}`);
  // `id` доступна и после await — замыкание
  return { id, ...(await res.json()) };
}
```

`fetch(...).then(...)`, `setTimeout`, `addEventListener`, `useEffect` — все они передают функцию «на потом», и эта функция уносит с собой окружение, в котором была создана.

@@ sec.ydkjs-scope.ch7.observable-definition.heading
А если я его не вижу?

@@ sec.ydkjs-scope.ch7.observable-definition.note
На собеседовании отвечай на вопрос «что такое замыкание?» этим определением с тремя условиями, а затем напиши пример `makeCounter`. Это гораздо сильнее, чем половинчатый ответ вроде «функция внутри функции».

Запомни: если функция вызывается внутри своего же scope — это **просто лексический scope**. Замыкание проявляется, когда функция «уходит в другое место».

@@ sec.ydkjs-scope.ch7.alternative.heading
Альтернативный взгляд

@@ sec.ydkjs-scope.ch7.alternative.note
Обе модели дают одинаковый результат, просто смотрят с разных сторон:

- **Модель наблюдения:** функция «путешествует» и уносит своё окружение с собой.
- **Модель реализации:** функция остаётся на месте, наружу уходит только **ссылка** на неё; пока ссылка жива, живёт и всё окружение.

Вторая модель полезнее для понимания GC и утечек памяти: она учит спрашивать «кто всё ещё удерживает это окружение?»

@@ sec.ydkjs-scope.ch7.why-closure.heading
Зачем нужны замыкания?

@@ sec.ydkjs-scope.ch7.why-closure.note
Частичное применение нужно в React каждый день:

```js
const handleChange = (field) => (e) =>
  setForm((f) => ({ ...f, [field]: e.target.value }));
<input onChange={handleChange('email')} />
<input onChange={handleChange('password')} />
```

`handleChange('email')` возвращает новую функцию, которая хранит `field` в замыкании, — не нужно писать отдельный обработчик для каждого поля ввода.

@@ sec.ydkjs-scope.ch7.intro.b2

Уверенное владение замыканиями необходимо, чтобы освоить JS и эффективно применять многие важные паттерны проектирования.

@@ sec.ydkjs-scope.ch7.see-closure.b0
Замыкание изначально — математическое понятие из лямбда-исчисления. Но я не собираюсь перечислять формулы или использовать кучу обозначений и жаргона, чтобы его определить.

@@ sec.ydkjs-scope.ch7.see-closure.b1
Вместо этого я сосредоточусь на практической точке зрения. Начнём с определения замыкания через то, что мы можем наблюдать в поведении программ, в отличие от ситуации, если бы замыканий в JS не было. Однако позже в этой главе мы перевернём замыкание и посмотрим на него с *альтернативной точки зрения*.

@@ sec.ydkjs-scope.ch7.see-closure.b2
Замыкание — поведение функций и только функций. Если ты имеешь дело не с функцией, замыкание неприменимо. У объекта не может быть замыкания, как и у класса (хотя у его функций/методов может). Замыкания есть только у функций.

@@ sec.ydkjs-scope.ch7.see-closure.b3
Чтобы замыкание можно было наблюдать, функция должна быть вызвана, причём именно в другой ветке цепочки областей видимости, чем та, где она была определена. Функция, выполняющаяся в той же области, где была определена, не показала бы никакого наблюдаемо иного поведения — независимо от того, возможны замыкания или нет; с наблюдательной точки зрения и по определению это не замыкание.

@@ sec.ydkjs-scope.ch7.see-closure.b4
Рассмотрим код, размеченный цветами соответствующих пузырей областей видимости (см. главу 2):

@@ sec.ydkjs-scope.ch7.see-closure.b6
Первое, что нужно заметить: внешняя функция `lookupStudent(..)` создаёт и возвращает внутреннюю функцию `greetStudent(..)`. `lookupStudent(..)` вызывается дважды и создаёт два отдельных экземпляра внутренней функции `greetStudent(..)`, оба сохраняются в массив `chosenStudents`.

@@ sec.ydkjs-scope.ch7.see-closure.b7
Мы проверяем это, посмотрев свойство `.name` возвращённой функции, сохранённой в `chosenStudents[0]`, — и это действительно экземпляр внутренней `greetStudent(..)`.

@@ sec.ydkjs-scope.ch7.see-closure.b8
Казалось бы, после завершения каждого вызова `lookupStudent(..)` все её внутренние переменные должны быть отброшены и собраны сборщиком мусора (GC). Похоже, единственное, что возвращается и сохраняется, — внутренняя функция. Но именно здесь поведение начинает различаться так, что мы можем это наблюдать.

@@ sec.ydkjs-scope.ch7.see-closure.b9
Хотя `greetStudent(..)` получает один аргумент в параметре `greeting`, она также обращается к `students` и `studentID` — идентификаторам из охватывающей области `lookupStudent(..)`. Каждое такое обращение внутренней функции к переменной во внешней области называется *замыканием*. Академически говоря, каждый экземпляр `greetStudent(..)` *замыкается над* внешними переменными `students` и `studentID`.

@@ sec.ydkjs-scope.ch7.see-closure.b10
Так что же делают эти замыкания здесь в конкретном, наблюдаемом смысле?

@@ sec.ydkjs-scope.ch7.see-closure.b11
Замыкание позволяет `greetStudent(..)` продолжать обращаться к этим внешним переменным даже после завершения внешней области (когда завершается каждый вызов `lookupStudent(..)`). Экземпляры `students` и `studentID` не собираются GC, а остаются в памяти. Когда позже вызывается любой экземпляр `greetStudent(..)`, эти переменные всё ещё на месте и хранят свои текущие значения.

@@ sec.ydkjs-scope.ch7.see-closure.b12
Если бы у функций JS не было замыканий, завершение каждого вызова `lookupStudent(..)` немедленно уничтожало бы её область и отдавало бы переменные `students` и `studentID` сборщику мусора. Что тогда произошло бы, когда мы позже вызвали бы одну из функций `greetStudent(..)`?

@@ sec.ydkjs-scope.ch7.see-closure.b13
Если бы `greetStudent(..)` попыталась обратиться к тому, что считала СИНИМ(2) шариком, а этого шарика на самом деле (уже) не существовало, разумно было бы ожидать `ReferenceError`, верно?

@@ sec.ydkjs-scope.ch7.see-closure.b14
Но ошибки нет. То, что выполнение `chosenStudents[0]("Hello")` работает и возвращает нам сообщение «Hello, Sarah!», означает, что функция всё ещё имеет доступ к переменным `students` и `studentID`. Это прямое наблюдение замыкания!

## Замыкание с острым концом

@@ sec.ydkjs-scope.ch7.see-closure.b16
На самом деле в предыдущем обсуждении мы проскочили одну маленькую деталь, которую, подозреваю, многие читатели пропустили!

@@ sec.ydkjs-scope.ch7.see-closure.b17

@@ sec.ydkjs-scope.ch7.adding-up.b0
Рассмотрим один из канонических примеров, которые часто приводят для замыканий:

@@ sec.ydkjs-scope.ch7.adding-up.b2
Каждый экземпляр внутренней функции `addTo(..)` замыкается над своей переменной `num1` (со значениями `10` и `42` соответственно), поэтому эти `num1` не исчезают только потому, что `adder(..)` завершилась. Когда позже мы вызываем один из этих экземпляров `addTo(..)`, например `add10To(15)`, её замкнутая переменная `num1` всё ещё существует и хранит исходное значение `10`. Поэтому операция может выполнить `10 + 15` и вернуть ответ `25`.

@@ sec.ydkjs-scope.ch7.adding-up.b3
Важную деталь в предыдущем абзаце было слишком легко пропустить, так что подчеркнём её: замыкание связано с экземпляром функции, а не с её единственным лексическим определением. В предыдущем фрагменте внутри `adder(..)` определена только одна внутренняя функция `addTo(..)`, поэтому может показаться, что это подразумевает одно замыкание.

@@ sec.ydkjs-scope.ch7.adding-up.b4
Но на самом деле при каждом выполнении внешней функции `adder(..)` создаётся *новый* экземпляр внутренней функции `addTo(..)`, а для каждого нового экземпляра — новое замыкание. Так что у каждого экземпляра внутренней функции (в нашей программе — `add10To(..)` и `add42To(..)`) есть собственное замыкание над собственным экземпляром окружения области из соответствующего выполнения `adder(..)`.

@@ sec.ydkjs-scope.ch7.adding-up.b5
Хотя замыкание основано на лексической области видимости, которая обрабатывается во время компиляции, наблюдается оно как характеристика экземпляров функций во время выполнения.

@@ sec.ydkjs-scope.ch7.live-link.b0
В обоих примерах из предыдущих разделов мы **читали значение из переменной**, которая хранилась в замыкании. Из-за этого кажется, что замыкание может быть снимком значения в какой-то момент. Действительно, это распространённое заблуждение.

@@ sec.ydkjs-scope.ch7.live-link.b1
Замыкание на самом деле — живая связь, сохраняющая доступ к самой переменной целиком. Мы не ограничены чтением значения; замкнутую переменную можно и обновлять (переприсваивать)! Замыкаясь над переменной в функции, мы можем продолжать использовать эту переменную (читать и писать), пока в программе существует ссылка на эту функцию, и откуда бы мы ни захотели её вызвать. Вот почему замыкание — такой мощный приём, широко используемый в самых разных областях программирования!

@@ sec.ydkjs-scope.ch7.observable-definition.b22
## Наблюдаемое определение

@@ sec.ydkjs-scope.ch7.observable-definition.b23
Теперь мы готовы дать определение замыкания:

@@ sec.ydkjs-scope.ch7.observable-definition.b24
> Замыкание наблюдается, когда функция использует переменную(ые) из внешней(их) области(ей), даже выполняясь в области, где эта переменная(ые) была бы недоступна.

@@ sec.ydkjs-scope.ch7.observable-definition.b25
Ключевые части этого определения:

- Должна участвовать функция
- Она должна обращаться хотя бы к одной переменной из внешней области
- Она должна вызываться в другой ветке цепочки областей, чем переменная(ые)

@@ sec.ydkjs-scope.ch7.observable-definition.b26
Такое ориентированное на наблюдение определение означает, что не стоит отмахиваться от замыкания как от косвенной академической мелочи. Наоборот, нужно видеть и учитывать прямые, конкретные эффекты замыкания на поведение программы.

@@ sec.ydkjs-scope.ch7.lifecycle-gc.b0
Поскольку замыкание по своей сути привязано к экземпляру функции, её замыкание над переменной длится, пока существует ссылка на эту функцию.

@@ sec.ydkjs-scope.ch7.lifecycle-gc.b1
Если десять функций замкнуты над одной переменной и со временем девять из этих ссылок на функции отбрасываются, единственная оставшаяся ссылка всё ещё сохраняет эту переменную. Как только отбрасывается последняя ссылка на функцию, исчезает последнее замыкание над этой переменной, и сама переменная собирается GC.

@@ sec.ydkjs-scope.ch7.lifecycle-gc.b2
Это важно для построения эффективных и производительных программ. Замыкание может неожиданно помешать сборке переменной, с которой ты уже закончил работу, что со временем приводит к неконтролируемому расходу памяти. Поэтому важно отбрасывать ссылки на функции (а значит, и их замыкания), когда они больше не нужны.

@@ sec.ydkjs-scope.ch7.lifecycle-gc.b3
Рассмотрим:

@@ sec.ydkjs-scope.ch7.lifecycle-gc.b5
В этой программе внутренняя функция `onClick(..)` держит замыкание над переданным `cb` (предоставленным колбэком события). Это значит, что ссылки на функциональные выражения `checkout()` и `trackAction()` удерживаются через замыкание (и не могут быть собраны GC), пока эти обработчики событий подписаны.

@@ sec.ydkjs-scope.ch7.lifecycle-gc.b6
Когда в последней строке мы вызываем `onSubmit()` без аргументов, все обработчики событий отписываются, а массив `clickHandlers` очищается. Как только все ссылки на функции-обработчики кликов отброшены, отбрасываются и замыкания `cb`, ссылающиеся на `checkout()` и `trackAction()`.

@@ sec.ydkjs-scope.ch7.lifecycle-gc.b7
С точки зрения общего здоровья и эффективности программы отписка от обработчика событий, когда он больше не нужен, может быть даже важнее, чем первоначальная подписка!

Значит, все переменные определённо сохранились через замыкание, хотя внутренняя функция явно к ним не обращается. Опровергает ли это утверждение *по переменной* в пользу *по области*? Зависит от обстоятельств.

@@ sec.ydkjs-scope.ch7.per-variable.b19
Многие современные JS-движки применяют *оптимизацию*, убирающую из области замыкания переменные, к которым нет явных обращений. Иными словами, с точки зрения реализации замыкание должно быть *по области*, а затем необязательная оптимизация урезает область до того, над чем реально произошло замыкание (результат, похожий на замыкание *по переменной*).

@@ sec.ydkjs-scope.ch7.per-variable.b20
Ещё несколько лет назад многие JS-движки не применяли эту оптимизацию; возможно, твои сайты до сих пор работают в таких браузерах, особенно на старых или слабых устройствах. Это значит, что долгоживущие замыкания, например обработчики событий, могут удерживать память гораздо дольше, чем мы предполагаем.

@@ sec.ydkjs-scope.ch7.per-variable.b21
А то, что это вообще необязательная оптимизация, а не требование спецификации, означает, что не стоит беззаботно рассчитывать на её применение.

@@ sec.ydkjs-scope.ch7.per-variable.b22
Если переменная содержит большое значение (например, объект или массив) и находится в области замыкания, а это значение тебе больше не нужно и ты не хочешь удерживать память, безопаснее (с точки зрения памяти) вручную отбросить значение, чем полагаться на оптимизацию замыканий/GC.

@@ sec.ydkjs-scope.ch7.per-variable.b23
Применим *исправление* к примеру `manageStudentGrades(..)`, чтобы потенциально большой массив в `studentRecords` без нужды не попадал в область замыкания:

@@ sec.ydkjs-scope.ch7.per-variable.b25
Мы не удаляем `studentRecords` из области замыкания — этим мы управлять не можем. Мы гарантируем, что даже если `studentRecords` останется в области замыкания, эта переменная больше не ссылается на потенциально большой массив данных; массив может быть собран GC.

@@ sec.ydkjs-scope.ch7.per-variable.b26
Опять же, во многих случаях JS может автоматически оптимизировать программу с тем же эффектом. Но всё равно полезная привычка — быть внимательным и явно следить, чтобы значительный объём памяти устройства не удерживался дольше необходимого.

@@ sec.ydkjs-scope.ch7.per-variable.b27
Собственно, технически после завершения вызова `.map(getGrade)` функция `getGrade()` нам тоже больше не нужна. Если бы профилирование приложения показало, что это критичное место избыточного расхода памяти, можно было бы выжать ещё немного памяти, освободив и эту ссылку. В этом игрушечном примере это, скорее всего, лишнее, но это общий приём, о котором стоит помнить при оптимизации объёма памяти приложения.

@@ sec.ydkjs-scope.ch7.per-variable.b28
Вывод: важно знать, где в программах появляются замыкания и какие переменные в них входят. Нужно аккуратно управлять этими замыканиями, удерживая лишь минимально необходимое и не тратя память впустую.

@@ sec.ydkjs-scope.ch7.alternative.b0
Возвращаясь к нашему рабочему определению замыкания: утверждается, что функции — это «значения первого класса» ([[first-class-function]]), которые можно передавать по программе, как любые другие значения. Замыкание — это связь, соединяющая функцию с областью/переменными вне её, куда бы эта функция ни отправилась.

@@ sec.ydkjs-scope.ch7.alternative.b1

@@ sec.ydkjs-scope.ch7.alternative.b12
Так что же тогда *такое* замыкание, если не *магия*, позволяющая функции сохранять связь с исходной цепочкой областей, даже когда она перемещается по другим областям? В этой альтернативной модели функции остаются на месте и продолжают обращаться к исходной цепочке областей, как могли всегда.

@@ sec.ydkjs-scope.ch7.alternative.b13
Вместо этого замыкание описывает *магию* **сохранения жизни экземпляра функции вместе со всем его окружением и цепочкой областей, пока хотя бы одна ссылка на этот экземпляр функции гуляет в какой-либо другой части программы.**

@@ sec.ydkjs-scope.ch7.alternative.b14
Такое определение замыкания менее наблюдательное и звучит чуть менее привычно по сравнению с традиционной академической точкой зрения. Но оно всё же полезно, потому что упрощает объяснение замыкания до понятного сочетания ссылок и остающихся на месте экземпляров функций.

@@ sec.ydkjs-scope.ch7.alternative.b15
Предыдущая модель (рисунок 4) не *ошибочна* в описании замыкания в JS. Она просто более концептуальна — академический взгляд на замыкание. Альтернативная модель (рисунок 5), напротив, более ориентирована на реализацию — на то, как JS работает на самом деле.

@@ sec.ydkjs-scope.ch7.alternative.b16
Обе точки зрения/модели полезны для понимания замыкания, но читателю одну из них может быть чуть проще удерживать в голове, чем другую. Какую бы ты ни выбрал, наблюдаемые результаты в программе одинаковы.

@@ sec.ydkjs-scope.ch7.closer.b1
Мы рассмотрели две модели осмысления замыкания:

- **Наблюдательная:** замыкание — это экземпляр функции, помнящий свои внешние переменные, даже когда функция передаётся в другие области и вызывается там.
- **Реализационная:** замыкание — это экземпляр функции и его окружение области, сохраняемые на месте, пока ссылки на него передаются и вызываются из других областей.

@@ sec.ydkjs-scope.ch7.closer.b2
Подытожим выгоды для наших программ:

- Замыкание может повысить эффективность, позволяя экземпляру функции помнить ранее определённую информацию, а не вычислять её каждый раз.
- Замыкание может повысить читаемость кода, ограничивая открытость областей за счёт инкапсуляции переменных внутри экземпляров функций и при этом гарантируя, что информация в этих переменных доступна для будущего использования. Получающиеся более узкие, специализированные экземпляры функций удобнее в работе, поскольку сохранённую информацию не нужно передавать при каждом вызове.
