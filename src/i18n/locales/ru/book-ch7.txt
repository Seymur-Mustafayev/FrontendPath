@@ sec.ydkjs-scope.ch7.intro.heading
Глава 7: Использование замыканий

@@ sec.ydkjs-scope.ch7.intro.b0
Наше внимание снова переходит на более высокий уровень абстракции — к исторически несколько пугающей теме замыканий. Не волнуйся! Чтобы разобраться в ней, не нужна учёная степень по информатике. Общая цель этой книги — не просто понять scope, а эффективнее использовать его в структуре программ; замыкание — центральная часть этой задачи.

@@ sec.ydkjs-scope.ch7.intro.b1
Замыкание развивает подход POLE: переменные, которые нужны нам на протяжении времени, можно не выносить в большие внешние области, а инкапсулировать (сузить их scope), сохранив при этом доступ к ним изнутри функций для более широкого использования. Функции запоминают эти переменные через замыкание.

@@ sec.ydkjs-scope.ch7.intro.b2
Если ты когда-нибудь писал колбэк, обращающийся к переменным за пределами своего scope... угадай что!? Это замыкание. Замыкание — одна из важнейших особенностей языков, когда-либо придуманных в программировании: оно лежит в основе крупных парадигм, включая функциональное программирование (FP), модули и даже отчасти классово-ориентированный дизайн.

@@ sec.ydkjs-scope.ch7.see-closure.heading
Увидеть замыкание

@@ sec.ydkjs-scope.ch7.see-closure.b0
Замыкание — поведение функций, и только функций. Если ты не имеешь дело с функцией, замыкание не применяется. У объекта не может быть замыкания, как и у класса (хотя у его функций/методов может). Чтобы замыкание можно было наблюдать, функция должна быть вызвана, причём в другой ветви цепочки scope, чем та, где она была определена.

@@ sec.ydkjs-scope.ch7.see-closure.b2
Кажется, что после завершения каждого вызова `lookupStudent(..)` все её внутренние переменные будут выброшены и собраны сборщиком мусора ([[gc]]). Но хотя `greetStudent(..)` принимает один аргумент в параметре `greeting`, она также ссылается на `students` и `studentID` — идентификаторы из охватывающего scope `lookupStudent(..)`. Каждая такая ссылка из внутренней функции на переменную внешнего scope называется [[closure]]. Академически говоря, каждый экземпляр `greetStudent(..)` **замыкается на** внешние переменные `students` и `studentID`.

@@ sec.ydkjs-scope.ch7.see-closure.b3
Замыкание позволяет `greetStudent(..)` продолжать обращаться к этим внешним переменным даже после завершения внешнего scope. Экземпляры `students` и `studentID` не собираются сборщиком мусора, а остаются в памяти. Если бы у функций JS не было замыканий, завершение каждого вызова `lookupStudent(..)` сразу разрушало бы её scope, и мы должны были бы получить `ReferenceError`. Но ошибки нет. Это прямое наблюдение замыкания!

@@ sec.ydkjs-scope.ch7.see-closure.b4
## Замыкание в стрелочной функции

@@ sec.ydkjs-scope.ch7.see-closure.b5
Из-за краткости синтаксиса стрелочных функций `=>` легко забыть, что они тоже создают scope. Стрелочная функция `student => student.id == studentID` создаёт ещё один пузырь scope внутри scope функции `greetStudent(..)` — назовём его ОРАНЖЕВЫМ(4). В результате замыкание на `studentID` держит не `greetStudent(..)`, а эта стрелочная функция, переданная колбэком в метод массива `find(..)`. Даже крошечные стрелочные функции могут участвовать в «вечеринке» замыканий.

@@ sec.ydkjs-scope.ch7.adding-up.heading
Складываем замыкания

@@ sec.ydkjs-scope.ch7.adding-up.b1
Каждый экземпляр внутренней функции `addTo(..)` замыкается на свою собственную переменную `num1` (со значениями `10` и `42` соответственно), поэтому эти `num1` не исчезают только потому, что `adder(..)` завершилась.

@@ sec.ydkjs-scope.ch7.adding-up.b2
Важная деталь: замыкание связано с **экземпляром** функции, а не с её единственным лексическим определением. При каждом запуске внешней функции `adder(..)` создаётся новый экземпляр внутренней `addTo(..)`, а для каждого нового экземпляра — новое замыкание. Хотя замыкание основано на лексическом scope, который обрабатывается при компиляции, наблюдается оно как свойство экземпляров функций во время выполнения.

@@ sec.ydkjs-scope.ch7.adding-up.note
Это ключевой механизм React: каждый рендер — новый вызов функции компонента, значит, каждый созданный внутри обработчик — **новый экземпляр**, замкнутый на переменные **этого рендера**.

```js
function Counter() {
  const [count, setCount] = useState(0);
  const log = () => console.log(count);   // count этого рендера
  return <button onClick={log}>{count}</button>;
}
```

Отсюда и «устаревшее замыкание» (stale closure): функция, созданная в старом рендере, видит старый `count`.

@@ sec.ydkjs-scope.ch7.live-link.heading
Живая связь, а не снимок

@@ sec.ydkjs-scope.ch7.live-link.b0
Замыкание — это на самом деле живая связь, сохраняющая доступ к самой переменной целиком. Мы не ограничены чтением значения: замкнутую переменную можно и обновлять (переприсваивать)! Замкнув переменную в функции, мы можем продолжать пользоваться ею (читать и писать), пока в программе существует ссылка на эту функцию, откуда бы мы её ни вызвали.

@@ sec.ydkjs-scope.ch7.live-link.b2
Поскольку замыкание часто ошибочно считают ориентированным на значение, а не на переменную, разработчики иногда спотыкаются, пытаясь с его помощью сохранить «снимок» значения в определённый момент. Классическая иллюстрация этой ошибки — определение функций внутри цикла:

@@ sec.ydkjs-scope.ch7.live-link.b4
Каждая сохранённая функция возвращает `3`, потому что к концу цикла единственной переменной `i` в программе присвоено `3`. У каждой из трёх функций в массиве `keeps` есть своё замыкание, но все они замкнуты на одну и ту же общую `i`. А объявление `let` в цикле `for` создаёт новую переменную на каждой итерации. Именно этот трюк/особенность нужен нашим замыканиям в цикле:

@@ sec.ydkjs-scope.ch7.live-link.note
**Замыкание хранит переменную, а не значение** — самая важная фраза главы.

В React ты видишь обратную сторону: `count` — это `const`, и каждый рендер создаёт новую переменную, поэтому старое замыкание видит старую переменную (старое значение). Решения:

```js
setCount((c) => c + 1);          // функциональное обновление — берёт последнее значение
const ref = useRef(count);       // ref — одна «переменная» на все рендеры
```

`useRef` работает ровно как `count` в `makeCounter`: одна переменная, много читателей.

@@ sec.ydkjs-scope.ch7.common-closures.heading
Обычные замыкания: Ajax и события

@@ sec.ydkjs-scope.ch7.common-closures.b0
Чаще всего замыкания встречаются в колбэках:

@@ sec.ydkjs-scope.ch7.common-closures.b2
Колбэк `onRecord(..)` будет вызван когда-то в будущем, после прихода ответа на Ajax-запрос. К тому моменту вызов `lookupStudentRecord(..)` давно завершится. Почему же `studentID` всё ещё существует и доступна колбэку? Замыкание.

@@ sec.ydkjs-scope.ch7.common-closures.cap3
Обработчик события замыкается на `label`

@@ sec.ydkjs-scope.ch7.common-closures.note
Почти весь асинхронный код, который ты пишешь на фронтенде, — это замыкания:

```js
async function loadUser(id) {
  const res = await fetch(`/api/users/${id}`);
  // `id` доступна и после await — замыкание
  return { id, ...(await res.json()) };
}
```

`fetch(...).then(...)`, `setTimeout`, `addEventListener`, `useEffect` — все они передают функцию «на потом», и эта функция уносит с собой окружение, в котором была создана.

@@ sec.ydkjs-scope.ch7.observable-definition.heading
А если я его не вижу? Наблюдаемое определение

@@ sec.ydkjs-scope.ch7.observable-definition.b0
Помни: в нашем определении замыкания акцент на наблюдаемости. Если замыкание существует (в техническом, реализационном или академическом смысле), но его нельзя наблюдать в программе, имеет ли это значение? Нет. Например, вызов функции, использующей лексический поиск, в том же scope — это просто лексический scope, а не замыкание:

@@ sec.ydkjs-scope.ch7.observable-definition.b2
На переменные глобального scope, по сути, нельзя (наблюдаемо) замкнуться, потому что они всегда доступны отовсюду. Переменные, которые просто существуют, но к которым никогда не обращаются, не создают замыкания. А если функция не вызывается, замыкание нельзя наблюдать.

@@ sec.ydkjs-scope.ch7.observable-definition.b3
> Замыкание наблюдается, когда функция использует переменную(ые) из внешнего scope, даже выполняясь в scope, где эти переменные были бы недоступны.

@@ sec.ydkjs-scope.ch7.observable-definition.b4
Ключевые части определения: должна участвовать функция; она должна ссылаться хотя бы на одну переменную из внешнего scope; она должна вызываться в другой ветви цепочки scope, чем переменная(ые).

@@ sec.ydkjs-scope.ch7.observable-definition.note
На собеседовании отвечай на вопрос «что такое замыкание?» этим определением с тремя условиями, а затем напиши пример `makeCounter`. Это гораздо сильнее, чем половинчатый ответ вроде «функция внутри функции».

Запомни: если функция вызывается внутри своего же scope — это **просто лексический scope**. Замыкание проявляется, когда функция «уходит в другое место».

@@ sec.ydkjs-scope.ch7.lifecycle-gc.heading
Жизненный цикл замыкания и сборка мусора (GC)

@@ sec.ydkjs-scope.ch7.lifecycle-gc.b0
Поскольку замыкание по своей природе связано с экземпляром функции, его захват переменной длится, пока существует ссылка на эту функцию. Если десять функций замкнуты на одну переменную и со временем девять ссылок на них выброшены, оставшаяся единственная ссылка всё ещё удерживает переменную. Когда выброшена и последняя ссылка, исчезает последнее замыкание на эту переменную, и сама переменная собирается сборщиком мусора.

@@ sec.ydkjs-scope.ch7.lifecycle-gc.b1
Замыкание может неожиданно помешать сборке мусора для переменной, которая тебе уже не нужна, что со временем ведёт к неконтролируемому росту памяти. Поэтому важно выбрасывать ссылки на функции (а значит, и их замыкания), когда они больше не нужны.

@@ sec.ydkjs-scope.ch7.lifecycle-gc.b3
Внутренняя функция `onClick(..)` удерживает замыкание на переданный `cb`. Значит, ссылки на функциональные выражения `checkout()` и `trackAction()` удерживаются через замыкание (и не могут быть собраны), пока эти обработчики подписаны. Отписка от обработчика, когда он больше не нужен, может быть даже важнее изначальной подписки!

@@ sec.ydkjs-scope.ch7.lifecycle-gc.note
Это объясняет, зачем в React существует функция очистки `useEffect`:

```js
useEffect(() => {
  const onResize = () => setWidth(window.innerWidth);
  window.addEventListener('resize', onResize);
  return () => window.removeEventListener('resize', onResize);
}, []);
```

Без очистки `onResize` (и его замыкание) продолжает жить даже после размонтирования компонента — классическая [[memory-leak]].

@@ sec.ydkjs-scope.ch7.per-variable.heading
По переменной или по scope?

@@ sec.ydkjs-scope.ch7.per-variable.b0
Считать ли, что замыкание распространяется только на упомянутые внешние переменные, или оно сохраняет всю цепочку scope со всеми переменными? Концептуально замыкание действует по переменной, а не по scope. Обычно предполагается, что Ajax-колбэки, обработчики событий и все прочие замыкания захватывают только то, на что явно ссылаются. Но реальность сложнее.

@@ sec.ydkjs-scope.ch7.per-variable.b2
Многие современные JS-движки применяют оптимизацию, удаляющую из scope замыкания переменные, на которые нет явных ссылок. Но, как видно на примере `eval(..)`, бывают ситуации, когда такую оптимизацию применить нельзя, и scope замыкания продолжает содержать все исходные переменные. Иными словами, с точки зрения реализации замыкание должно действовать по scope, а затем необязательная оптимизация урезает scope до того, что действительно захвачено.

@@ sec.ydkjs-scope.ch7.per-variable.b3
Если переменная хранит большое значение (например, объект или массив) и находится в scope замыкания, а значение тебе больше не нужно и держать эту память не хочется, безопаснее (с точки зрения памяти) вручную сбросить значение, чем полагаться на оптимизацию замыканий/GC:

@@ sec.ydkjs-scope.ch7.per-variable.note
Практический вывод: в долгоживущих замыканиях (обработчики событий, интервалы, подписки на глобальный store) следи за переменными с большими данными.

Проверить это можно в Chrome DevTools → Memory → Heap snapshot: объекты, удерживаемые замыканием, видны как `context` в разделе «Retainers».

@@ sec.ydkjs-scope.ch7.alternative.heading
Альтернативный взгляд

@@ sec.ydkjs-scope.ch7.alternative.b0
Наш текущий взгляд предполагает, что куда бы функцию ни передали и где бы ни вызвали, замыкание сохраняет скрытую связь с исходным scope, обеспечивая доступ к захваченным переменным. Но о замыканиях можно думать и иначе. Эта альтернативная модель уводит на второй план идею «функций как значений первого класса» и вместо этого опирается на то, что функции (как и все непримитивные значения) хранятся в JS по ссылке и присваиваются/передаются копией ссылки.

@@ sec.ydkjs-scope.ch7.alternative.b1
Вместо того чтобы считать, что внутренний экземпляр `addTo(..)` перемещается во внешний КРАСНЫЙ(1) scope через `return` и присваивание, можно представить, что экземпляры функций на самом деле остаются на месте в своём окружении scope — разумеется, с нетронутой цепочкой scope. В КРАСНЫЙ(1) scope отправляется лишь ссылка на оставшийся на месте экземпляр функции, а не сам экземпляр.

@@ sec.ydkjs-scope.ch7.alternative.b2
В этой альтернативной модели функции остаются на месте и продолжают обращаться к своей исходной цепочке scope, как и всегда. А замыкание описывает магию **сохранения экземпляра функции живым** вместе со всем его окружением и цепочкой scope, пока где-либо в программе существует хотя бы одна ссылка на этот экземпляр.

@@ sec.ydkjs-scope.ch7.alternative.note
Обе модели дают одинаковый результат, просто смотрят с разных сторон:

- **Модель наблюдения:** функция «путешествует» и уносит своё окружение с собой.
- **Модель реализации:** функция остаётся на месте, наружу уходит только **ссылка** на неё; пока ссылка жива, живёт и всё окружение.

Вторая модель полезнее для понимания GC и утечек памяти: она учит спрашивать «кто всё ещё удерживает это окружение?»

@@ sec.ydkjs-scope.ch7.why-closure.heading
Зачем нужны замыкания?

@@ sec.ydkjs-scope.ch7.why-closure.b0
Представь, что на странице есть кнопка, по клику на которую нужно получить и отправить данные Ajax-запросом. Без замыкания обработчик должен читать атрибут DOM при каждом срабатывании. Почему бы обработчику не запомнить это значение? Попробуем улучшить код с помощью замыкания:

@@ sec.ydkjs-scope.ch7.why-closure.b2
Две похожие техники из парадигмы функционального программирования (FP), опирающиеся на замыкания, — [[partial-application]] и каррирование. С их помощью мы меняем форму функций с несколькими входами так, что часть входов передаётся заранее, а остальные — позже; начальные входы запоминаются через замыкание. Когда переданы все входы, выполняется основное действие.

@@ sec.ydkjs-scope.ch7.why-closure.cap3
Частичное применение: URL и данные передаются заранее, `evt` — позже

@@ sec.ydkjs-scope.ch7.why-closure.note
Частичное применение нужно в React каждый день:

```js
const handleChange = (field) => (e) =>
  setForm((f) => ({ ...f, [field]: e.target.value }));
<input onChange={handleChange('email')} />
<input onChange={handleChange('password')} />
```

`handleChange('email')` возвращает новую функцию, которая хранит `field` в замыкании, — не нужно писать отдельный обработчик для каждого поля ввода.

@@ sec.ydkjs-scope.ch7.closer.heading
Ближе к замыканию

@@ sec.ydkjs-scope.ch7.closer.b0
Мы рассмотрели две модели для понимания замыканий:

**Наблюдательная:** замыкание — это экземпляр функции, который помнит свои внешние переменные, даже когда функцию передают в другие области и вызывают там.

**Реализационная:** замыкание — это экземпляр функции и его окружение scope, сохранённые на месте, пока ссылки на них передаются и вызываются из других областей.

@@ sec.ydkjs-scope.ch7.closer.b1
Итог пользы для наших программ: замыкание может повысить эффективность, позволяя экземпляру функции помнить ранее вычисленную информацию вместо того, чтобы вычислять её каждый раз. Замыкание может улучшить читаемость кода, ограничивая открытость scope за счёт инкапсуляции переменных внутри экземпляров функций и при этом сохраняя доступ к этой информации для будущего использования.
