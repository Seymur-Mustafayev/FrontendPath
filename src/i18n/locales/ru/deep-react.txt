@@ deep.react.0
Главная идея React проста: UI — это функция от состояния. Ты не меняешь DOM шаг за шагом, а просто говоришь «для этих данных экран должен выглядеть так», а React вычисляет разницу и применяет её.

## Компонент и props

[[component]] — обычная функция, которая принимает props и возвращает [[jsx]]. [[props]] только для чтения — потомок их не меняет. Если нужно изменение, наверх передаётся колбэк (поток данных вверх возможен только в виде событий).

```tsx
type Props = { order: Order; onSelect: (id: number) => void; };

function OrderRow({ order, onSelect }: Props){
  return (
    <tr onClick={() => onSelect(order.id)}>
      <td>{order.id}</td>
      <td>{order.total.toFixed(2)} ₼</td>
    </tr>
  );
}
```

## Истинная природа JSX

JSX — синтаксический сахар; при сборке он превращается в вызовы функций. Поэтому JSX-выражение — обычное значение: его можно записать в переменную, хранить в массиве, передать как prop.

```tsx
const header = <h2>Заказы</h2>;
<Panel title={header} footer={<Actions />} />
```

Для условного рендера есть три способа, и выбирают их по читаемости:

```tsx
{isEmpty && <Empty />}
{isLoading ? <Skeleton /> : <Table rows={rows} />}
{(() => { switch (status) { /* ... */ } })()}
```

Внимание: если написать `{count && <Badge />}`, а `count` равен нулю, на экране появится `0` — правильная форма `{count > 0 && ...}`.

## Композиция

[[composition]] — главный механизм переиспользования в React. Если список props компонента растёт (`showHeader`, `headerTitle`, `headerIcon`, `showFooter`…), это сигнал, что его нужно разделить:

```tsx
// вместо разбухшей конфигурации
<Card>
  <Card.Header title='Заказ #1042' action={<Button>Печать</Button>} />
  <Card.Body>{children}</Card.Body>
</Card>
```

Этот приём называется «слотом» и основан на передаче JSX через props.

## Атрибут key

В списке `key` сообщает React, какой элемент какой. Использовать индекс как key при сортировке и удалении — значит получить неверный результат: React неправильно сопоставляет элементы, и значения input «перескакивают» из одной строки в другую.

```tsx
{rows.map(r => <OrderRow key={r.id} order={r} />)}   // стабильный уникальный key
```

## Практическое правило

Если компонент превышает один экран (примерно 150 строк) или ему трудно дать имя, он делает слишком много. Критерий разделения не технический, а смысловой: каждый компонент должен представлять одно понятие.

@@ deep.react.1
[[state]] — память компонента, которая меняется со временем. Ключ к пониманию React: когда состояние меняется, React ЗАНОВО вызывает функцию компонента и сравнивает результат с предыдущим.

## Что значит ре-рендер и чего он не значит

[[re-render]] — повторное выполнение функции компонента. Это НЕ означает обновления DOM. React сравнивает новый результат с предыдущим (reconciliation) и применяет к DOM только разницу. Поэтому «много рендеров» само по себе не проблема; проблема — дорогая работа во время рендера.

## Правильная форма обновления

```tsx
const [count, setCount] = useState(0);

setCount(count + 1);       // опирается на значение текущего рендера
setCount(c => c + 1);       // опирается на последнее значение в очереди — безопаснее
```

Два подряд вызова `setCount(count + 1)` продвигают на один шаг, а функциональная форма — на два. В асинхронном коде и колбэках всегда выбирай функциональную форму (смотри тему [[closure]]).

## Состояние-объект и состояние-массив

Состояние нужно обновлять иммутабельно, потому что React сравнивает ссылки:

```tsx
setFilters(f => ({ ...f, status: 'paid', page: 1 }));
setRows(rs => rs.map(r => r.id === id ? { ...r, qty: r.qty + 1 } : r));
```

## Где живёт состояние

Важнейшее архитектурное решение — где хранится состояние. Правило: в ближайшем общем родителе компонентов, которые его используют, — не выше и не ниже. Без нужды поднятое наверх состояние заставляет перерендериваться всё дерево.

А хранить производное значение в состоянии — классическая ошибка:

```tsx
// НЕПРАВИЛЬНО — придётся держать их синхронными
const [rows, setRows] = useState([]);
const [filtered, setFiltered] = useState([]);

// ПРАВИЛЬНО — вычисляй во время рендера
const filtered = rows.filter(r => r.status === status);
```

## Батчинг

Начиная с React 18 все обновления применяются пакетно — нет разницы между обработчиком события, Promise и setTimeout ([[batching]]). То есть три подряд `setState` дают один рендер.

```tsx
function onSave(){
  setSaving(true);
  setError(null);
  setDirty(false);   // все три вместе → один рендер
}
```

## Сброс состояния через key

Малоизвестный, но очень полезный приём: новый `key` у компонента полностью сбрасывает его состояние.

```tsx
<OrderForm key={orderId} orderId={orderId} />   // при смене заказа форма начинается с чистого листа
```

Это и короче, и надёжнее, чем писать ручной сброс через `useEffect`.

## Когда useReducer

Если несколько полей меняются взаимосвязанно (шаги формы, фильтр + страница + сортировка), `useReducer` упорядоченнее: все переходы видны в одном месте, а тестировать проще.

@@ deep.react.2
[[useeffect]] — самый неправильно используемый хук React. Его цель — не «выполнить код при загрузке компонента», а СИНХРОНИЗИРОВАТЬСЯ с системами вне дерева React.

## Случаи, когда эффект НЕ НУЖЕН

Это самое важное, и официальная документация тоже это подчёркивает:

```tsx
// 1) Производное значение — эффект НЕ НУЖЕН
useEffect(() => { setFullName(first + ' ' + last); }, [first, last]);  // неправильно
const fullName = first + ' ' + last;                                   // правильно

// 2) Реакция на событие — эффект НЕ НУЖЕН
useEffect(() => { if (submitted) postForm(); }, [submitted]);          // неправильно
function onSubmit(){ postForm(); }                                     // правильно

// 3) Сброс состояния при смене props — используй key
<Form key={userId} />
```

Случаи, когда эффект действительно нужен: подписки (WebSocket, слушатели событий), таймеры, синхронизация с API браузера (title, localStorage, фокус), аналитика, жизненный цикл сторонней библиотеки.

## Массив зависимостей

[[dependency-array]] определяет, когда эффект запустится снова. Правило линтера React `exhaustive-deps` здесь друг, а не враг: удалить зависимость — значит спрятать проблему, а не решить её.

```tsx
useEffect(() => {
  const ac = new AbortController();
  fetchOrders(filters, ac.signal).then(setRows);
  return () => ac.abort();          // [[cleanup]]
}, [filters]);                       // если filters — новый объект на каждом рендере → бесконечный цикл
```

Это самая частая причина бесконечного цикла: в зависимостях объект или функция, создаваемые заново на каждом рендере ([[referential-equality]]). Решение — либо стабилизировать значение (`useMemo`, `useCallback`), либо разбить зависимость на примитивы (`filters.status`, `filters.page`).

## Функция очистки

Cleanup срабатывает ПЕРЕД каждым повторным запуском и при размонтировании. Без неё подписки и таймеры накапливаются — это первая причина [[memory-leak]].

```tsx
useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id);
}, []);
```

## Поведение StrictMode

В режиме разработки React 18 намеренно запускает эффекты дважды (mount → unmount → mount). Это не баг: так выявляются эффекты, для которых ты не написал правильную очистку. В продакшене такого поведения нет.

## Не первый выбор для загрузки данных

Загружать данные через useEffect можно, но тогда всё придётся писать самому: состояние гонки, отмену, кэш, повторные попытки, фоновое обновление, объединение одинаковых параллельных запросов. Всё это готово в [[tanstack-query]]. А в Next.js данные загружаются в серверном компоненте, и эффект вообще не нужен.

## Отличие useLayoutEffect

`useLayoutEffect` работает синхронно, ДО того, как браузер отрисует кадр. Его используют только для случаев вроде измерения размеров и немедленной корректировки позиции (позиционирование tooltip); злоупотребление им блокирует рендер.

@@ deep.react.3
Формы — область, где в React пишется больше всего кода, и выбранный подход напрямую влияет и на производительность, и на объём кода.

## Контролируемый подход

[[controlled-component]] хранит значение в состоянии: единый источник истины находится в React.

```tsx
const [email, setEmail] = useState('');
<input value={email} onChange={e => setEmail(e.target.value)} />
```

Преимущество: значение всегда доступно, мгновенная валидация и условный UI делаются легко. Слабость: каждый символ означает рендер. В маленькой форме проблемы нет, а в форме заказа из 30 полей это ощутимо.

## Неконтролируемый подход

В [[uncontrolled]] форме значение остаётся в DOM и читается, когда нужно:

```tsx
const formRef = useRef<HTMLFormElement>(null);
function onSubmit(e){
  e.preventDefault();
  const data = Object.fromEntries(new FormData(formRef.current!));
  save(data);
}
```

## React Hook Form

[[react-hook-form]] построен на неконтролируемой модели и сочетает преимущества обоих миров: минимум рендеров, сильная валидация, обработка ошибок на уровне полей.

```tsx
const schema = z.object({
  customerId: z.number({ message: 'Нужно выбрать клиента' }),
  total: z.number().positive('Сумма должна быть положительной'),
  note: z.string().max(500).optional()
});

const { register, handleSubmit, control, formState: { errors, isSubmitting } } =
  useForm<z.infer<typeof schema>>({ resolver: zodResolver(schema) });

<form onSubmit={handleSubmit(onSubmit)}>
  <input {...register('total', { valueAsNumber: true })} aria-invalid={!!errors.total} />
  {errors.total && <p role='alert'>{errors.total.message}</p>}
  <button disabled={isSubmitting}>Сохранить</button>
</form>
```

Для особых UI-компонентов (DevExtreme SelectBox, DatePicker) используется `Controller` — компонент библиотеки работает как контролируемый, а остальные поля остаются неконтролируемыми.

## Возврат серверных ошибок в форму

Валидация бывает не только на клиенте. Ошибки полей, пришедшие с сервера, нужно передать в форму:

```tsx
catch (e) {
  if (isApiError(e) && e.fields) {
    Object.entries(e.fields).forEach(([name, msg]) => setError(name, { message: msg }));
  }
}
```

[[custom-hook]] — стандартный механизм повторного использования логики в React. Именно поэтому паттерны HOC и render-props из эпохи классов ушли на второй план.

## Когда выносить хук

Когда внутри компонента логика состояния и эффектов смешана с UI или когда та же логика понадобилась во втором месте. Имя хука должно начинаться с `use` — это не просто соглашение, а условие работы правил линтера.

```tsx
function useDebouncedValue<T>(value: T, delay = 300){
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);
  }, [value, delay]);
  return debounced;
}

// использование
const [q, setQ] = useState('');
const debouncedQ = useDebouncedValue(q, 400);
const { data } = useQuery({ queryKey: ['search', debouncedQ], queryFn: ... });
```

## Признаки хорошего хука

У него одна ответственность, он возвращает понятный результат, и по имени ясно, что получит вызывающая сторона. Хук, который делает больше двух вещей, обычно нужно разделить.

```tsx
// доменный хук: данные + операции в одном месте
function useOrder(id: number){
  const query = useQuery({ queryKey: ['order', id], queryFn: () => getOrder(id) });
  const pay = useMutation({ mutationFn: payOrder, onSuccess: () => qc.invalidateQueries({ queryKey: ['order', id] }) });
  return { order: query.data, isLoading: query.isLoading, pay: pay.mutate, isPaying: pay.isPending };
}
```

Этот приём очищает компонент: он занимается «что», а не «как» ([[separation-of-concerns]]).

## Правила хуков и их причина

[[rules-of-hooks]]: хуки вызываются только на верхнем уровне компонента или другого хука и без условий. Причина во внутреннем устройстве React — хуки сопоставляются не по имени, а по ПОРЯДКУ ВЫЗОВА. Вызов внутри условия ломает порядок, и состояния перемешиваются.

```tsx
if (isAdmin) { const [x] = useState(0); }   // ЗАПРЕЩЕНО
const [x] = useState(0);
if (isAdmin) { /* используй x */ }           // правильно
```

## Частые ловушки

Объект, возвращаемый из хука, новый на каждом рендере. Если передаёшь его в зависимости другого хука, может понадобиться стабилизировать его через `useMemo`. Условный `return` внутри хука тоже запрещён.

## Хуки из библиотек

Не всё нужно писать самому: в наборах вроде `usehooks-ts` и `react-use` есть проверенные хуки — `useLocalStorage`, `useMediaQuery`, `useOnClickOutside`. Главное — прежде чем добавить в проект целый пакет, оценить, не ради ли одного-единственного хука это делается ([[bundle-size]]).

@@ deep.react.5
[[context]] — встроенный ответ React на проблему передачи props вниз через несколько уровней — [[prop-drilling]]. Но это не глобальный менеджер состояния, и неправильное использование — скрытый источник проблем с производительностью.

## Prop drilling — действительно проблема?

Передача через два-три уровня нормальна и читаема. Проблема начинается, когда уровней пять-шесть, а промежуточные компоненты просто передают props дальше, не используя их. Иногда лучшее решение — не Context, а композиция:

```tsx
// вместо проброса собери потомка выше и передай его
<Layout sidebar={<UserPanel user={user} />} />
```

## Настройка контекста

```tsx
const ThemeContext = createContext<Theme | null>(null);

export function useTheme(){
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error('useTheme работает только внутри ThemeProvider');
  return ctx;
}
```

Этот хук-обёртка даёт две пользы: тип не бывает `null`, а неправильное использование останавливается понятным сообщением.

## Ловушка производительности

Когда меняется значение [[provider]], перерендериваются ВСЕ компоненты, читающие этот контекст, — даже `React.memo` этого не предотвращает. А самая частая ошибка — создавать объект value заново на каждом рендере:

```tsx
// НЕПРАВИЛЬНО — новый объект на каждом рендере → рендерятся все потребители
<AuthContext.Provider value={{ user, login, logout }}>

// ПРАВИЛЬНО
const value = useMemo(() => ({ user, login, logout }), [user, login, logout]);
<AuthContext.Provider value={value}>
```

## Разделение контекста

Хранить в одном контексте часто и редко меняющиеся данные вредно. Классическое решение — разделить на два:

```tsx
<AuthStateContext.Provider value={user}>          {/* меняется редко */}
  <AuthActionsContext.Provider value={actions}>   {/* не меняется никогда */}
```

Так перерендериваются только компоненты, читающие `user`, а те, кто использует функцию `login`, не затрагиваются.

## Для чего его ИСПОЛЬЗОВАТЬ НЕ НУЖНО

Использовать Context для серверных данных — одна из самых дорогих ошибок: кэширование, устаревание, повторные попытки, объединение параллельных запросов — всё это придётся писать вручную. Для этой работы есть [[tanstack-query]] (смотри тему [[server-state]]).

А для часто меняющегося глобального клиентского состояния (например, позиции на canvas, состояния редактора) лучше подходит store с поддержкой селекторов вроде Zustand — там можно подписаться только на используемую часть.

Оптимизация производительности — самая неправильно применяемая тема в React: разработчики либо не делают её вовсе, либо рассыпают `useMemo` повсюду. Правильный порядок всегда один: сначала измерь, потом найди причину, потом исправь.

## Ссылочное равенство — корень проблемы

В JavaScript объект и функция каждый раз — новая ссылка:

```js
{} === {}            // false
(() => {}) === (() => {})   // false
```

Это и есть [[referential-equality]], и на нём построен весь механизм мемоизации React: `React.memo` поверхностно сравнивает props, `useEffect` проверяет зависимости через `Object.is`.

## Роль трёх инструментов

```tsx
const Row = React.memo(function Row({ order, onSelect }){ ... });   // [[react-memo]]

const total = useMemo(() => rows.reduce((s, r) => s + r.total, 0), [rows]);  // [[usememo]]
const onSelect = useCallback((id: number) => setSelected(id), []);            // [[usecallback]]
```

Внимание: `useCallback` имеет смысл только тогда, когда функция уходит как prop в мемоизированный компонент или является зависимостью эффекта. Мемоизировать функцию, передаваемую обычной DOM-кнопке, бесполезно — наоборот, это расход памяти и кода.

## Когда memo ломается

Самый частый случай: компонент мемоизирован, но в props на каждом рендере уходит новый объект.

```tsx
<Row order={order} style={{ padding: 8 }} onSelect={(id) => open(id)} />
// style и onSelect новые на каждом рендере → memo бесполезен
```

## Не оптимизируй без измерений

[[profiler]] в React DevTools показывает, какой компонент, сколько и ПОЧЕМУ рендерился (включи параметр «Record why each component rendered»). Решение об оптимизации принимается после этого отчёта. Иначе ты пытаешься решить неизмеренную проблему и усложняешь код.

## Решения получше мемоизации

1. Опустить состояние ниже — пусть меняющееся состояние живёт только в маленьком поддереве.
2. Композиция — если тяжёлый потомок передаётся как `children`, рендер родителя не перерендеривает его.
3. Виртуализировать список ([[virtualization]]) — для 10 000 строк нужен windowing, а не memo.
4. Перенести дорогое вычисление на сервер или в worker.

Новый компилятор React автоматизирует мемоизацию и делает ненужной большую часть написанных вручную `useMemo`/`useCallback`. Но знать механизм всё равно необходимо: компилятор анализирует существующий код и не работает с кодом, написанным не по правилам (мутации, побочные эффекты).

> Тема «Тест хуков и мемоизации» в пути Testing — продолжение этого раздела: не утверждать, что мемоизация работает, а доказывать это счётчиком рендеров и проверкой ссылок.

## Error boundary

Если ошибку, выброшенную во время рендера, не обработать, React разбирает всё дерево и показывает белый экран. [[error-boundary]] этого не допускает:

```tsx
import { ErrorBoundary } from 'react-error-boundary';

<ErrorBoundary
  FallbackComponent={({ error, resetErrorBoundary }) => (
    <div role='alert'>
      <p>Этот раздел не загрузился: {error.message}</p>
      <button onClick={resetErrorBoundary}>Попробовать снова</button>
    </div>
  )}
  onError={(e, info) => report(e, info)}   // отправить в Sentry
>
  <ReportPanel />
</ErrorBoundary>
```

Важное ограничение: error boundary ловит только ошибки рендера, методов жизненного цикла и конструктора. Ошибки в обработчиках событий и асинхронном коде до него не доходят — их нужно обрабатывать через `try/catch` или колбэк `onError` у мутации.

Стратегия размещения: одна глобальная граница в корне (против полного падения), по одной на каждом маршруте и отдельные — для независимых тяжёлых разделов (графики, таблицы).

## Suspense

[[suspense]] — граница, показывающая fallback для ещё не готового содержимого:

```tsx
<Suspense fallback={<TableSkeleton rows={8} />}>
  <OrdersTable />
</Suspense>
```

Самое частое применение — разделение кода через `React.lazy`; также работает с хуком `useSuspenseQuery` из TanStack Query и серверными компонентами Next.js.

Дизайн fallback важен: skeleton, повторяющий реальную структуру, вместо спиннера предотвращает скачок [[cls]] и уменьшает ощущение ожидания.

## Ленивая загрузка

```tsx
const ReportChart = lazy(() => import('./ReportChart'));

<Suspense fallback={<ChartSkeleton />}>
  {showChart && <ReportChart data={data} />}
</Suspense>
```

Лучшие кандидаты для [[code-splitting]]: маршруты, тяжёлое содержимое внутри модальных окон, библиотеки графиков/PDF/редакторов, разделы администрирования. Делить каждый маленький компонент — обратный эффект: появляется множество мелких запросов.

Чтобы улучшить пользовательский опыт, чанк можно подгрузить заранее:

```tsx
<button onMouseEnter={() => import('./ReportChart')} onClick={open}>Отчёт</button>
```

## Объединение всех трёх

Стандартная структура такова: ErrorBoundary на уровне маршрута → внутри Suspense → внутри lazy-компонент. Так состояния загрузки, ошибки и содержимого управляются в одном месте декларативно, а сам компонент занимается только успешным сценарием.
