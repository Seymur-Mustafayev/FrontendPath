@@ deep.next.0
Самое важное в изучении Next.js — не API, а знание того, ГДЕ выполняется код. Один и тот же React-компонент может работать в браузере, на сервере или во время сборки, и этот выбор определяет скорость продукта, его SEO и требования к инфраструктуре.

## Четыре модели

```
CSR : пустой HTML + JS → браузер загружает данные
      + простой хостинг   − медленный первый экран, слабое SEO
      подходит для внутренних панелей и админок

SSR : сервер строит HTML на каждый запрос
      + свежие данные, хорошее SEO   − нагрузка на сервер, растёт TTFB
      личный и быстро меняющийся контент

SSG : HTML строится во время сборки
      + самый быстрый, отдаётся с CDN   − данные на момент сборки
      маркетинговые страницы, документация, блог

ISR : статическая страница обновляется в фоне с интервалом
      + баланс статической скорости и свежести
      каталог, страницы товаров
```

## Hydration

[[hydration]] — подключение JS к HTML, пришедшему с сервера, чтобы сделать его интерактивным. Если результат рендера на сервере и на клиенте различается, React предупреждает и перестраивает эту часть.

```tsx
// классические причины ошибки гидратации
new Date().toLocaleString()      // на сервере другой часовой пояс
Math.random()
localStorage.getItem('theme')     // на сервере нет localStorage
window.innerWidth
```

Правильное решение: читать такие значения в эффекте (чтобы первый рендер был одинаковым с обеих сторон) или загружать компонент только на клиенте через `dynamic(..., { ssr: false })`.

## Как делается выбор

Последовательность вопросов: (1) Страница публичная и должна быть видна в поиске? (2) Данные одинаковы для всех пользователей? (3) Насколько старыми они могут быть? По ответам спускаешься в порядке статика → ISR → SSR. А для внутренних экранов, требующих аутентификации, простой CSR + [[tanstack-query]] — вполне законный выбор.

## Связь с измерениями

SSR улучшает метрику [[lcp]], потому что пользователь видит содержимое, не дожидаясь JS. Но большой бандл JS всё равно создаёт проблему [[inp]] — серверный рендер не ускоряет интерактивность. Поэтому модель рендеринга и оптимизация [[bundle-size]] друг друга не заменяют.

App Router — современная модель Next.js, и в её центре стоит [[rsc]] — React Server Components. Это не просто новая структура папок, а новый способ думать о том, где выполняются компоненты.

## По умолчанию сервер, клиент — исключение

В App Router каждый компонент по умолчанию серверный: он работает на сервере, его результат отправляется потоком HTML/RSC, а код НЕ попадает в браузер. То есть если тяжёлая библиотека используется в серверном компоненте, она не добавляется в бандл пользователя.

```tsx
// app/orders/page.tsx — серверный компонент (никакой директивы нет)
export default async function OrdersPage({ searchParams }){
  const orders = await db.order.findMany({ where: { status: searchParams.status } });
  return <OrdersTable rows={orders} />;   // прямое обращение к БД, API-маршрут не нужен
}
```

## Граница 'use client'

`'use client'` пишется там, где нужна интерактивность (хуки, события, API браузера). Важное правило: эта директива создаёт ГРАНИЦУ — всё, что импортирует этот компонент, тоже попадает в клиентский бандл. Поэтому границу нужно опускать как можно ниже, к листовым компонентам.

```tsx
'use client';
export function StatusFilter({ value }){ /* useState, onChange */ }
```

Серверный компонент можно передать внутрь клиентского как `children` — это главный приём, позволяющий держать границу низко:

```tsx
<ClientTabs>
  <ServerReport />    {/* серверный компонент работает как потомок клиентского */}
</ClientTabs>
```

## Server Actions

[[server-action]] — функция, выполняемая на сервере и вызываемая с клиента, — мутация без отдельного API-эндпоинта:

```tsx
// app/orders/actions.ts
'use server';
export async function createOrder(formData: FormData){
  const parsed = OrderSchema.parse(Object.fromEntries(formData));
  const order = await db.order.create({ data: parsed });
  revalidatePath('/orders');           // обновить кэш
  return order;
}
```

Замечание о безопасности: server action ведёт себя как публичный эндпоинт — аутентификацию и проверку прав нужно выполнять ВНУТРИ него, доверять вызывающей стороне нельзя.

## Streaming и Suspense

[[streaming]] позволяет отправлять страницу частями: быстрая часть появляется сразу, медленная добавляется, когда будет готова.

```tsx
<Suspense fallback={<StatsSkeleton />}>
  <SlowStats />      {/* пока этот компонент ждёт, остальная страница уже видна */}
</Suspense>
```

## Практические замечания

В серверном компоненте нет `useState`, `useEffect`, `onClick`. Импортировать серверную функцию прямо в клиентский компонент нельзя. Провайдеры контекста размещаются на клиентской границе. Сначала эти правила кажутся непривычными, но в итоге объём JS, который приложение отправляет в браузер, заметно уменьшается.

Маршрутизация в App Router определяется файловой системой, и структура папок — это прямо структура URL. Это упрощает поиск того, где находится код.

## Соглашения о файлах

```
app/
  layout.tsx          → каркас, охватывающий все страницы (корневой layout обязателен)
  page.tsx            → /
  loading.tsx         → Suspense fallback (автоматически)
  error.tsx           → error boundary (должен быть 'use client')
  not-found.tsx       → 404
  orders/
    page.tsx          → /orders
    [id]/page.tsx     → /orders/12   (динамический сегмент)
    layout.tsx        → каркас только для раздела /orders
  (marketing)/        → группировка — на URL не влияет
  api/health/route.ts → HTTP-эндпоинт
```

## Поведение layout

[[layout]] НЕ перерендеривается при переходе между маршрутами и сохраняет своё состояние. То есть позиция прокрутки сайдбара и состояние открытого меню при переходе не теряются. Это главный механизм, дающий ощущение SPA.

`template.tsx`, наоборот, пересоздаётся при каждом переходе; его используют, когда нужна анимация появления.

## loading и error

Достаточно создать файл `loading.tsx` — Next.js автоматически обернёт страницу в Suspense. `error.tsx` играет роль [[error-boundary]] для этого сегмента и даёт возможность повторить попытку через функцию `reset()`.

```tsx
'use client';
export default function Error({ error, reset }){
  useEffect(() => report(error), [error]);
  return <><p>Что-то пошло не так</p><button onClick={reset}>Попробовать снова</button></>;
}
```

## Route handler

[[route-handler]] создаёт HTTP-эндпоинт для webhook, загрузки файлов, интеграций со сторонними сервисами:

```ts
export async function GET(req: Request){
  const { searchParams } = new URL(req.url);
  const rows = await getOrders(searchParams.get('status'));
  return Response.json(rows, { headers: { 'Cache-Control': 'no-store' } });
}
```

## Навигация

Компонент `<Link>` заранее загружает видимые ссылки (prefetch), поэтому переходы ощущаются мгновенными. Для программной навигации используют `useRouter().push()`. А `redirect()` вызывается в серверном компоненте или action.

## Middleware

`middleware.ts` работает до того, как запрос дойдёт до сервера: проверка аутентификации, перенаправление по языку, A/B-тесты. Поскольку выполняется в среде Edge, API Node.js там ограничены, и выполнять тяжёлую работу там неправильно.

@@ deep.next.3
Система кэширования Next.js мощная, но при использовании без понимания возникают проблемы «данные не обновляются» или «при каждом запросе идёт на сервер». Этот раздел объясняет слои и способы управления ими.

## Слои кэша

```
1. Request memoization  → один и тот же fetch в пределах одного рендера выполняется один раз
2. Data Cache           → результаты fetch могут храниться между деплоями
3. Full Route Cache     → полный результат HTML/RSC статического маршрута
4. Router Cache         → кэш навигации на стороне браузера
```

## Управление на уровне fetch

```ts
await fetch(url, { cache: 'force-cache' });                 // вести себя как статика
await fetch(url, { cache: 'no-store' });                    // каждый раз свежие данные
await fetch(url, { next: { revalidate: 60 } });             // обновить в фоне через 60 секунд
await fetch(url, { next: { tags: ['orders'] } });           // управление через тег
```

Значение [[revalidate]] можно задать и на уровне страницы: `export const revalidate = 300;`. А `export const dynamic = 'force-dynamic'` делает всю страницу динамической.

## Инвалидация по тегам

Самый точный способ: при изменении данных удаляется только связанный с ними кэш.

```ts
'use server';
export async function updateOrder(id: number, input: OrderPatch){
  await api(`/orders/${id}`, { method: 'PATCH', body: JSON.stringify(input) });
  revalidateTag('orders');       // все fetch с этим тегом считаются устаревшими
  revalidatePath(`/orders/${id}`);
}
```

## Критическое правило безопасности

Главный вопрос при выборе [[cache-strategy]]: одинаково ли это содержимое для всех пользователей? Если пустить персональные данные в статический кэш, данные одного пользователя могут показаться другому. Для личных страниц нужно выбирать `no-store` или динамический рендер, привязанный к cookie.

## Объединение с клиентской стороной

Распространённый приём — загрузить начальные данные в серверном компоненте, а интерактивную часть продолжить через [[tanstack-query]]: первый экран приходит быстро, а последующие фильтры и обновления управляются на клиенте. Для этого серверные данные передаются через `initialData` или гидратацию.

## Диагностика

Если данные не обновляются, порядок такой: (1) посмотри параметр cache у fetch, (2) посмотри, помечена ли страница как статическая или динамическая (в выводе сборки рядом с каждым маршрутом есть отметка), (3) проверь, что вызов revalidate действительно выполняется, (4) проверь, нет ли кэша на уровне CDN.

Деплой часто подают как «нажатие одной кнопки», но в реальном проекте управление окружениями, результат сборки и выбор инфраструктуры — серьёзные решения.

## Переменные окружения

```
.env.local          → локальная разработка (в репозиторий НЕ попадает)
.env.example        → файл-образец без значений (попадает в репозиторий)
platform secrets    → значения для продакшена (в панели Vercel/Azure)
```

Критическое правило для [[env-variable]] в Next.js: переменная с префиксом `NEXT_PUBLIC_` включается в БАНДЛ, и её может увидеть любой пользователь. Ключи API, строки подключения, секретные токены никогда не пишут с этим префиксом.

```ts
const apiUrl = process.env.NEXT_PUBLIC_API_URL;   // видна в браузере — OK
const dbPass = process.env.DB_PASSWORD;            // только на сервере — OK
```

Типизируй переменные и проверяй их при старте (например, через Zod) — чтобы неправильная конфигурация всплыла при сборке, а не после деплоя.

## Результат сборки

[[build-artifact]] должен собираться один раз и одинаково распространяться во все окружения. Пересборка под каждое окружение — источник проблем вида «в тесте работало». Исключение — переменные, встраиваемые при сборке (NEXT_PUBLIC_): они фиксируются в момент сборки, поэтому значения, специфичные для окружения, нужно читать из конфигурации во время выполнения.

Смотреть на вывод сборки — полезная привычка: Next.js показывает, статический или динамический каждый маршрут, и объём JS при первой загрузке.

## Платформы

[[vercel]] требует для Next.js минимум настройки: preview-деплои, edge-сеть и поддержка ISR уже готовы. На стороне Azure два основных варианта: Static Web Apps (статика или гибрид) и App Service (полноценный Node.js-сервер, с правилами корпоративной сети). Выбор Azure часто не технический, а организационный — требования к данным и сети.

Возможен и деплой через Docker: параметр `output: 'standalone'` создаёт минимальный серверный пакет.

## Минимум после деплоя

У каждого продакшен-приложения должны быть три вещи: мониторинг ошибок ([[sentry]]) с source map, измерение ключевых метрик (Core Web Vitals по данным реальных пользователей) и план отката. На Vercel вернуться к предыдущему деплою — один клик; в Azure эту роль играют deployment slots.

## Связь с конвейером

Деплой нужно выполнять не вручную, а через [[pipeline]]: lint → typecheck → test → build → deploy. Эта последовательность подробно раскрывается в теме CI/CD пути Git.
