@@ deep.perf.0
Разговор о производительности без цифр невозможен. Core Web Vitals сводят пользовательский опыт к трём измерениям, и они влияют и на ранжирование в Google, и на реальную конверсию.

## Три метрики

```
LCP (Largest Contentful Paint)  → когда отрисован самый крупный видимый элемент
    хорошо < 2.5s   |  плохо > 4s
INP (Interaction to Next Paint) → задержка реакции на действие пользователя (заменила FID)
    хорошо < 200ms  |  плохо > 500ms
CLS (Cumulative Layout Shift)   → неожиданный сдвиг раскладки
    хорошо < 0.1    |  плохо > 0.25
```

## Что замедляет LCP

Обычно одно из четырёх: медленный ответ сервера (TTFB), ресурсы, блокирующие рендер (CSS, синхронный JS), позднее обнаружение изображения или ожидание рендера на стороне клиента.

Практические решения: объяви элемент LCP заранее (`fetchpriority='high'`, `preload`), НЕ ставь ему `loading='lazy'`, отдавай изображение в современном формате, встрой критический CSS inline и пересмотри выбор рендеринга на сервере ([[ssr]]).

## INP и длинные задачи

[[inp]] напрямую зависит от того, как долго JavaScript занимает главный поток. Причины: тяжёлый рендер, фильтрация больших списков, сторонние скрипты, синхронные вычисления на каждое нажатие клавиши.

Решения: разбивать работу на части, переносить тяжёлые вычисления в Web Worker, откладывать несрочные обновления через `useDeferredValue`/`startTransition`, debounce в полях ввода, виртуализация списков.

## Главные причины CLS

Изображения без заявленных размеров, шрифт, загружающийся позже (FOUT), баннеры/уведомления, динамически добавляемые сверху, и рекламные/iframe-блоки без зарезервированного размера. Решение: резервирование размеров для всех медиа, `font-display: swap` + `size-adjust`, skeleton той же высоты, что и реальное содержимое.

## Лабораторные и реальные данные

[[lighthouse]] — лабораторное измерение: одно устройство, одни сетевые условия. Данные реальных пользователей (RUM) могут отличаться. Для реальных измерений используют библиотеку `web-vitals`:

```js
import { onLCP, onINP, onCLS } from 'web-vitals';
onLCP(m => sendToAnalytics(m));
onINP(m => sendToAnalytics(m));
onCLS(m => sendToAnalytics(m));
```

## Установка бюджета

Производительность — не разовая работа, она склонна к регрессу. Поэтому команды задают бюджет: например, JS первой загрузки не больше 200 KB, LCP не больше 2.5 секунды. Проверка этого бюджета в CI (Lighthouse CI, bundlesize) обеспечивает его реальное соблюдение.

## Разделение кода

Лучшие кандидаты для [[code-splitting]] — маршруты и редко используемые тяжёлые компоненты:

```tsx
const ReportsPage = lazy(() => import('./pages/Reports'));
const PdfExport = lazy(() => import('./features/PdfExport'));
```

У разделения есть предел: десятки мелких чанков — это множество сетевых запросов. Практическое правило — уровень маршрутов и независимые блоки больше 30 KB.

## Условия tree shaking

Чтобы работал [[tree-shaking]]: пакет должен быть в формате ESM, нужно использовать именованные импорты, а объявление побочных эффектов в пакете должно быть настроено правильно (поле `sideEffects`). Пакеты CommonJS остаются за рамками этой оптимизации.

## Связь с кэшированием

Правильное разделение бандла повышает эффективность кэша: когда редко меняющийся vendor-код лежит в отдельном чанке, каждое изменение твоего кода не заставляет пользователя заново загружать все библиотеки.

## Когда остановиться

Оптимизация [[bundle-size]] подчиняется закону убывающей отдачи. Спуститься с 800 KB до 300 KB — большой выигрыш; делать код нечитаемым ради спуска с 300 до 280 — неправильное решение. Определи целевой размер, достигни его и защищай бюджет в CI.

## Четыре шага оптимизации изображений

1. Правильный формат: [[webp]]/AVIF для фото, SVG для логотипов и иконок.
2. Правильный размер: отправлять изображение 2000px в блок 400px — самое частое расточительство.
3. Варианты через [[srcset]] и ширина в раскладке через `sizes`.
4. Резервирование размеров (`width`/`height` или `aspect-ratio`) — для [[cls]].

```html
<img src='p-800.avif' srcset='p-400.avif 400w, p-800.avif 800w'
     sizes='(max-width:640px) 100vw, 640px'
     width='800' height='600' alt='Товар' loading='lazy' decoding='async'>
```

## Шрифты

Файл шрифта большой и может блокировать появление текста. Стандартный набор:

```css
@font-face{
  font-family: 'Source Sans 3';
  src: url('/fonts/source-sans.woff2') format('woff2');
  font-display: swap;      /* текст виден сразу, шрифт меняется, когда придёт */
  unicode-range: U+0000-00FF, U+0400-04FF;  /* латиница + кириллица */
}
```

[[font-display]] `swap` решает проблему FOIT (невидимый текст), но при смене шрифта может дать скачок — приблизив запасной шрифт к оригиналу через `size-adjust` и `ascent-override`, этот скачок убирают.

Дополнительное внимание для русского языка: нужно подключить подмножество шрифта `cyrillic`, иначе кириллические буквы отобразятся запасным шрифтом, и текст будет выглядеть смешанным.

```html
<link rel='preconnect' href='https://fonts.gstatic.com' crossorigin>
<link rel='preload' as='font' type='font/woff2' href='/fonts/main.woff2' crossorigin>
```

## Подсказки для ресурсов

```
preconnect  → заранее установить соединение с другим доменом (шрифты, API)
preload     → рано загрузить ресурс, который ТОЧНО нужен на этой странице
prefetch    → в свободное время загрузить ресурс вероятной следующей страницы
```

Если объявить через [[preload]] слишком много ресурсов, эффект будет обратным — сетевая очередь забьётся, и действительно критический ресурс задержится.

## Сторонние скрипты

Скрипты аналитики, чат-виджетов, рекламы и карт часто тяжелее твоего собственного кода. Решения: `async`/`defer`, загрузка после действия пользователя (facade), стратегии `next/script` в Next.js (`lazyOnload`, `worker`). Самый быстрый способ измерить их влияние — заблокировать скрипт в DevTools и сравнить метрики.

## Принцип виртуализации

[[virtualization]] (или [[windowing]]) рендерит только видимые строки, а вместо остальных ставит пустую область, сохраняющую общую высоту. При прокрутке видимое окно обновляется.

```tsx
import { useVirtualizer } from '@tanstack/react-virtual';

const parentRef = useRef<HTMLDivElement>(null);
const rowVirtualizer = useVirtualizer({
  count: rows.length,
  getScrollElement: () => parentRef.current,
  estimateSize: () => 44,
  overscan: 8               // буфер за пределами видимой области
});

<div ref={parentRef} style={{ height: 600, overflow: 'auto' }}>
  <div style={{ height: rowVirtualizer.getTotalSize(), position: 'relative' }}>
    {rowVirtualizer.getVirtualItems().map(v => (
      <div key={rows[v.index].id}
           style={{ position: 'absolute', top: 0, transform: `translateY(${v.start}px)`, height: v.size, width: '100%' }}>
        <Row order={rows[v.index]} />
      </div>
    ))}
  </div>
</div>
```

## В контексте DevExtreme

В DataGrid та же проблема решается готовыми режимами: virtual scrolling, paging и remoteOperations. А при больших данных самое правильное решение — отдать фильтрацию, сортировку и пагинацию СЕРВЕРУ: отправлять в браузер 50 000 строк и фильтровать их там — архитектурная ошибка.

## Цена виртуализации

Поиск по странице (Ctrl+F) не работает, печать и экспорт требуют отдельного решения, строки переменной высоты требуют дополнительных вычислений, а для доступности атрибуты вроде `aria-rowcount` приходится задавать вручную. Поэтому спискам на 200–300 строк виртуализация не нужна.

## Частота ввода

Разница между [[debounce]] и throttle на практике:

```js
// debounce: один раз через 300ms после того, как пользователь перестал печатать
const debouncedQ = useDebouncedValue(q, 300);

// throttle: при прокрутке не чаще одного раза в 100ms
window.addEventListener('scroll', throttle(onScroll, 100), { passive: true });
```

В React 18 есть альтернатива — `useDeferredValue`: во время ввода UI остаётся отзывчивым, а тяжёлый список рендерится с отложенным значением.

```tsx
const deferredQ = useDeferredValue(q);
const filtered = useMemo(() => rows.filter(r => r.name.includes(deferredQ)), [rows, deferredQ]);
```

## Другие тяжёлые места

В таблицах с большим числом элементов дорогими могут быть и sticky-заголовки, и тени. Ограничение анимаций свойствами `transform`/`opacity` и откладывание рендера невидимых блоков через `content-visibility: auto` дают дополнительный выигрыш.

## React Profiler

[[profiler]] — отдельная вкладка React DevTools. Нажимаешь запись, повторяешь проблемное действие, затем смотришь на результат: какие компоненты рендерились, сколько времени это заняло и почему.

В настройках включи параметр «Record why each component rendered» — он показывает причину вроде «изменились props», «изменился state», «отрендерился родитель», «изменился context» и уточняет цель оптимизации.

На графике широкие полосы — обычно компоненты, которые занимают больше всего времени. Если на один клик рендерятся 40 компонентов, а большинство из них не изменились, значит, либо состояние слишком высоко, либо композиция неправильная.

## Панель Performance

Собственная панель браузера показывает всю картину: сеть, выполнение JS, layout, paint. [[flame-chart]] показывает иерархию и длительность вызовов функций; длинные непрерывные блоки — места, где главный поток занят.

Привычка при проверке: поставь CPU throttling на замедление в 4 раза, а сеть — на «Fast 3G». Проблемы, невидимые на твоём мощном компьютере, там сразу всплывают — а большая часть пользователей находится именно в таких условиях.

## Утечки памяти

[[memory-leak]] в SPA ощущается как утяжеление по мере перехода по страницам. Способ диагностики: сними heap snapshot в панели Memory → несколько раз зайди на проблемную страницу и выйди → сними новый snapshot → сравни. Причину укажут отсоединённые (detached) DOM-узлы и объекты, число которых растёт.

Самые частые причины: неочищенный `setInterval`, не удалённый слушатель событий, не закрытый WebSocket/EventSource, колбэк, обновляющий состояние после размонтирования компонента. Решение всегда одно — возвращать из эффекта функцию [[cleanup]].

## Измерение в продакшене

Локальное измерение не заменяет реального пользователя. Реальная картина складывается, когда объединяются метрики из `web-vitals`, трассировка производительности [[sentry]] и данные о TTFB со стороны сервера. Только после этого на вопрос «какая страница медленная» можно ответить фактами.

## Порядок работы

```
1. Преврати жалобу в цифру         (какая страница, какое действие, насколько)
2. Воспроизведи и измерь           (Profiler / Performance)
3. Найди самую большую долю        (бандл? рендер? сеть?)
4. Сделай одно изменение           (не меняй пять вещей сразу)
5. Измерь снова и сравни
6. Зафиксируй результат как бюджет
```
