Эти три понятия — scope, hoisting и замыкание — составляют основу модели памяти JavaScript. Большая часть проблем в React вроде «приходит старое значение», «эффект работает бесконечно», «счётчик застыл» решается именно здесь.

## Лексическая область видимости

[[scope]] — область видимости переменной, и в JavaScript она лексическая: какие переменные увидит функция, определяется тем, где она НАПИСАНА, а не тем, где вызвана.

```js
const a = 'модуль';
function outer(){
  const b = 'outer';
  function inner(){
    const c = 'inner';
    console.log(a, b, c);  // видит все три уровня
  }
  return inner;
}
```

`var` имеет функциональную область видимости, а `let` и `const` — блочную: `let`, объявленный внутри блока `if` или `for`, снаружи не существует.

## Hoisting и TDZ

[[hoisting]] — это «поднятие» объявлений в начало области видимости. Объявление функции поднимается целиком (её можно вызвать до объявления), `var` поднимается, но его значение `undefined`, а `let`/`const`, хоть и поднимаются, остаются в зоне, которая называется [[tdz]]:

```js
console.log(x);  // undefined  (var)
console.log(y);  // ReferenceError: Cannot access 'y' before initialization
var x = 1;
let y = 2;
```

Поэтому современный стандарт — делать `const` выбором по умолчанию, а `let` писать только тогда, когда нужно переприсваивание.

## Замыкание

[[closure]] — это когда функция несёт с собой лексическое окружение, в котором была создана. Функция может обращаться к переменным этого окружения и позже:

```js
function createCounter(){
  let count = 0;                 // недоступно снаружи
  return {
    inc: () => ++count,
    get: () => count
  };
}
const c = createCounter();
c.inc(); c.inc();
c.get();  // 2
```

На этом основан паттерн «модуль»: переменная остаётся скрытой, и добраться до неё могут только возвращённые функции.

## Stale closure — настоящая проблема в React

На каждом рендере функция компонента выполняется заново, и для этого рендера создаются НОВЫЕ переменные и новые функции. Колбэк, сохранённый внутри эффекта, «замораживает» значения того рендера:

```js
useEffect(() => {
  const id = setInterval(() => {
    setCount(count + 1);   // count ВСЕГДА значение из первого рендера → застревает на 1
  }, 1000);
  return () => clearInterval(id);
}, []);                     // пустой массив зависимостей
```

Есть три правильных решения:

```js
// 1) функциональное обновление — старое значение не нужно
setCount(c => c + 1);

// 2) правильно указать зависимость (интервал каждый раз пересоздаётся)
useEffect(() => { ... }, [count]);

// 3) хранить последнее значение в ref
const latest = useRef(count);
latest.current = count;
```

## Замыкание внутри цикла

Классический пример: `for (var i = 0; i < 3; i++) setTimeout(() => console.log(i))` три раза выводит 3, потому что `var` — одна переменная. А с `let` каждая итерация создаёт собственную привязку, и выводится 0, 1, 2.

> Самый быстрый способ понять замыкание — DevTools: поставь breakpoint внутри функции и посмотри раздел Closure в панели Scope — там прямо видно, какие переменные «замкнуты».

`this` — самое неправильно понимаемое ключевое слово JavaScript, потому что работает иначе, чем `this` в других языках: его значение зависит не от того, где функция написана, а от того, КАК она вызвана.

## Четыре правила привязки

```js
function show(){ console.log(this); }

show();                 // обычный вызов → undefined (strict) / globalThis
const o = { show };
o.show();               // вызов метода → o
new show();             // конструктор → новый объект
show.call({ id: 1 });   // явная привязка → { id: 1 }
```

Значение [[this]] определяется в таком порядке: `new` → явная привязка (семейство [[bind]]) → вызов метода → значение по умолчанию.

## Исключение для стрелочных функций

У стрелочной функции нет собственного `this` — она берёт его из лексического окружения, в котором была создана, и изменить его никаким способом нельзя. В колбэках это незаменимо:

```js
class OrderService {
  constructor(){ this.items = []; }
  loadAll(ids){
    return ids.map(id => this.load(id));   // стрелка → this сохраняется
  }
}
```

И наоборот, писать метод объекта стрелкой — ошибка, потому что `this` будет указывать не на объект, а на окружение модуля.

## Потеря метода

Если отделить метод от объекта и передать его дальше, привязка теряется:

```js
const btn = document.querySelector('button');
btn.addEventListener('click', service.save);        // this теряется
btn.addEventListener('click', () => service.save()); // правильно
btn.addEventListener('click', service.save.bind(service)); // правильно
```

Именно в этом причина знаменитой строки `this.handleClick = this.handleClick.bind(this)` в классовых компонентах React. В функциональных компонентах эта проблема исчезает — одно из практических преимуществ функционального подхода.

## Цепочка прототипов

Наследование в JavaScript работает через [[prototype]]. Если свойство не найдено в объекте, поиск продолжается вверх по цепочке `Object.getPrototypeOf()` и заканчивается на `null`.

```js
const arr = [1, 2];
arr.map        // берётся из Array.prototype.map
arr.toString   // берётся из Object.prototype
```

Синтаксис [[class]] — читаемая оболочка над этим: `class` и `extends` всё так же строят цепочку прототипов. В современном синтаксисе классов есть также поля `#private` и статические методы.

## Где это нужно

В функциональном React `this` в повседневной работе почти не встречается, но нужен в трёх местах: при чтении старых классовых компонентов, при изучении внутренностей библиотек и на собеседованиях. А вот создание классов ошибок полезно в реальной практике:

```js
class ApiError extends Error {
  constructor(status, message){ super(message); this.name = 'ApiError'; this.status = status; }
}
```

Большая часть работы фронтенда — преобразование данных: отфильтровать пришедший с сервера массив, сгруппировать, отсортировать, превратить в модель UI. Для этого вместо циклов используют декларативные методы массивов — код становится короче, а намерение читается.

## Три основных метода

Тройка [[map-filter-reduce]]: `map` преобразует (возвращает столько же элементов), `filter` отбирает, а `reduce` сворачивает всё в одно значение.

```js
const paid = orders.filter(o => o.status === 'PAID');
const rows = paid.map(o => ({ id: o.id, total: o.total }));
const sum  = paid.reduce((acc, o) => acc + o.total, 0);

// группировка — самое полезное применение reduce
const byCustomer = orders.reduce((acc, o) => {
  (acc[o.customerId] ??= []).push(o);
  return acc;
}, {});
```

Другие часто нужные: `find`, `some`, `every`, `flatMap`, `Object.entries/fromEntries`. В современных средах есть и методы `toSorted`, `toReversed` и `with` — они возвращают новый массив, не меняя исходный, что идеально для React.

## Ссылочная семантика

Объекты и массивы передаются по ссылке. Это объясняет, зачем в React существует правило [[immutability]]: React проверяет изменение состояния через `Object.is`, то есть если ссылка та же, считается, что ничего не произошло.

```js
// НЕПРАВИЛЬНО — та же ссылка, ре-рендера не будет
items.push(newItem);
setItems(items);

// ПРАВИЛЬНО — новая ссылка
setItems([...items, newItem]);
setItems(items.filter(i => i.id !== id));
setItems(items.map(i => i.id === id ? { ...i, qty: i.qty + 1 } : i));
```

## Spread и глубина

[[spread]] делает поверхностную (shallow) копию: копируется первый уровень, а вложенные объекты по-прежнему общие.

```js
const next = { ...order, customer: { ...order.customer, name: 'Новый' } };
```

Для глубоких структур используют `structuredClone()` или Immer. Функция `produce` из Immer позволяет писать код, похожий на мутацию, но в результате возвращает новый объект — Redux Toolkit использует это внутри.

## Деструктуризация и значения по умолчанию

```js
const { id, customer: { name = 'Неизвестно' } = {}, items = [] } = order;
function createOrder({ customerId, note = '', ...rest }){ /* ... */ }
```

[[destructuring]] в React используется ежедневно, чтобы распаковывать props и результаты хуков. Злоупотребление глубокой деструктуризацией снижает читаемость — после двух уровней обычное обращение понятнее.

## Современные операторы

Optional chaining `?.` останавливается, встретив в цепочке `null/undefined`; nullish coalescing `??` подставляет значение по умолчанию только для `null` и `undefined` (в отличие от `||`, пропускает `0` и `''`). Эта разница вызывает реальные баги в полях с суммами и количеством:

```js
const qty = input.qty || 1;   // при 0 станет 1 — НЕПРАВИЛЬНО
const qty = input.qty ?? 1;   // останется 0 — ПРАВИЛЬНО
```

JavaScript однопоточен: в каждый момент выполняется только один фрагмент кода. Несмотря на это, одновременно можно обрабатывать десятки запросов, таймеров и событий. Механизм, который делает это возможным, — [[event-loop]], и его понимание позволяет предсказывать поведение асинхронного кода.

## Составные части

[[call-stack]] — стек выполняемых функций. API браузера (таймеры, fetch, DOM-события) работают вне JS и, когда готовы, ставят колбэк в очередь. Event loop делает одну-единственную работу: если стек пуст, берёт из очереди следующую задачу и кладёт её в стек.

Есть две основные очереди: очередь макрозадач ([[task-queue]] — setTimeout, setInterval, I/O, события) и очередь [[microtask]] (колбэки Promise, queueMicrotask, MutationObserver).

## Правило приоритета

После каждой макрозадачи очередь микрозадач опустошается полностью, и только потом идут рендер и следующая макрозадача.

```js
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');

// Вывод: 1, 4, 3, 2
```

Этот порядок — классический вопрос на собеседовании, но у него есть и практическая ценность: бесконечно удлиняя цепочку микрозадач, можно полностью заблокировать рендер, потому что браузер не переходит к отрисовке, пока микрозадачи не закончатся.

## Блокировка и INP

Долгое синхронное вычисление занимает стек, и в это время не обрабатываются ни клики, ни прокрутка, ни анимация. Задачи дольше 50 ms считаются «long task» и напрямую ухудшают метрику [[inp]].

Варианты решения:

```js
// 1) разбить работу на части
async function processAll(items){
  for (let i = 0; i < items.length; i++){
    process(items[i]);
    if (i % 200 === 0) await new Promise(r => setTimeout(r));  // дать передышку
  }
}

// 2) перенести тяжёлое вычисление в Web Worker
const worker = new Worker('/calc.js');
worker.postMessage(rows);
worker.onmessage = e => setResult(e.data);

// 3) отложить несрочную работу на время простоя
requestIdleCallback(() => sendAnalytics());
```

## Связь с React

Конкурентный режим React 18 построен поверх этой модели: обновления, помеченные через `startTransition`, не считаются срочными, и при необходимости браузер прерывает их, чтобы обработать ввод пользователя. То есть знание event loop прямо объясняет, зачем существуют хуки `useTransition` и `useDeferredValue`.

## Почему важна статическая структура

Объявления `import` пишутся в начале файла и без условий. Это значит, что бандлер, не выполняя код, а просто читая его, знает, кто что использует. В результате становится возможным [[tree-shaking]] — неиспользуемые экспорты удаляются из сборки.

```js
import { formatDate } from './utils/date';    // остаётся только эта функция
import * as utils from './utils/date';        // tree-shaking ослабевает
```

CommonJS (`require`) динамичен и затрудняет такой анализ; это одна из причин, почему старые пакеты раздувают бандл.

## Именованный и default-экспорт

[[named-export]] безопаснее при рефакторинге: при переименовании места использования выдают ошибку, а редактор может предложить автоимпорт. Default-экспорт можно импортировать под разными именами в каждом файле, что затрудняет поиск. Команде нужно выбрать одно правило; для компонентов React именованный экспорт распространяется всё шире.

## Динамический импорт

```js
const { default: Chart } = await import('./ReportChart');
// В React:
const ReportChart = lazy(() => import('./ReportChart'));
```

[[dynamic-import]] возвращает Promise и создаёт отдельный чанк. Это стандартный способ вынести тяжёлые библиотеки (графики, PDF, текстовый редактор, карты) из основного бандла.

## Barrel-файлы

Собирать экспорты через `index.ts` удобно, но если класть их в каждую папку, возникают две проблемы: растёт время сборки и повышается риск циклических импортов. В больших проектах barrel-файл оставляют только на границе пакета (например, общей UI-библиотеки).

## Вопрос побочных эффектов

Модуль выполняется один раз при первом импорте, и его результат кэшируется. То есть код, написанный на уровне модуля (например, подключение аналитики), срабатывает сразу при загрузке этого модуля. Бандлеру это поведение сообщают флагом `sideEffects: false` в `package.json` — неправильная пометка может привести к удалению реальной функциональности.

## Три фазы события

Событие сначала спускается от корня к цели (capture), срабатывает на цели (target), затем поднимается вверх ([[bubbling]]). Третий параметр `addEventListener` выбирает фазу:

```js
el.addEventListener('click', fn);                 // фаза всплытия (по умолчанию)
el.addEventListener('click', fn, { capture: true });
el.addEventListener('click', fn, { once: true });  // срабатывает один раз и удаляется
el.addEventListener('scroll', fn, { passive: true }); // не будет вызывать preventDefault — прокрутка ускоряется
```

## Делегирование событий

[[event-delegation]] — это один слушатель на родителе вместо слушателя на каждой строке списка из тысяч строк:

```js
table.addEventListener('click', (e) => {
  const row = e.target.closest('tr[data-id]');
  if (!row) return;
  openOrder(row.dataset.id);
});
```

Преимущества: экономия памяти и автоматическая работа динамически добавляемых элементов. React внутри работает по похожему принципу — собирает события на корневом контейнере.

## stopPropagation и preventDefault

Это разные вещи: `preventDefault()` отменяет поведение браузера по умолчанию (переход по ссылке, отправку формы), а `stopPropagation()` останавливает всплытие события. `stopPropagation` нужно использовать осторожно — он молча ломает работу внешнего кода (аналитики, закрытия по клику снаружи).

## Очистка

Каждый добавленный [[event-listener]] нужно удалять, иначе возникает [[memory-leak]]:

```js
useEffect(() => {
  const onKey = (e) => { if (e.key === 'Escape') close(); };
  document.addEventListener('keydown', onKey);
  return () => document.removeEventListener('keydown', onKey);  // [[cleanup]]
}, [close]);
```

Самое простое решение — `AbortController`: одним сигналом удаляются сразу несколько слушателей.

```js
const ac = new AbortController();
window.addEventListener('resize', onResize, { signal: ac.signal });
window.addEventListener('scroll', onScroll, { signal: ac.signal });
return () => ac.abort();
```

## API наблюдателей

В современном коде вместо проверки видимости элемента через событие прокрутки используют `IntersectionObserver` (бесконечная прокрутка, ленивая загрузка), для отслеживания размеров — `ResizeObserver` (подстройка графиков), а для изменений DOM — `MutationObserver`. Они оптимизированы браузером и быстрее и точнее, чем написанные вручную расчёты прокрутки.
