@@ deep.sec.0
[[xss]] — самая классическая проблема безопасности фронтенда: вредоносный скрипт выполняется на твоей странице, в твоём домене, с сессией пользователя. Итог — кража токенов, поддельные операции и утечка данных.

## Три вида

```
Stored XSS   → вредоносный код хранится в базе (комментарий, имя профиля) и выполняется при каждом просмотре
Reflected XSS→ попадает на страницу прямо из параметра URL
DOM XSS      → целиком на стороне клиента, например через innerHTML
```

## Что делает React и чего не делает

React автоматически экранирует значения внутри JSX — то есть `{userInput}` всегда показывается как текст. Это по умолчанию закрывает большую часть XSS.

Но три двери остаются открытыми:

```tsx
<div dangerouslySetInnerHTML={{ __html: comment }} />   // 1
<a href={userUrl}>Ссылка</a>                             // 2 — схема javascript:
el.innerHTML = value;                                     // 3 — прямой DOM
```

## Очистка

Если нужно показать форматированный текст, [[sanitization]] обязательна:

```ts
import DOMPurify from 'dompurify';
const safe = DOMPurify.sanitize(comment, { ALLOWED_TAGS: ['b','i','em','strong','a','p','ul','li'], ALLOWED_ATTR: ['href'] });
```

Белый список (что разрешено) всегда безопаснее чёрного (что запрещено).

## Проверка URL

```ts
function safeHref(url: string){
  try {
    const u = new URL(url, window.location.origin);
    return ['http:', 'https:', 'mailto:'].includes(u.protocol) ? u.href : '#';
  } catch { return '#'; }
}
```

Для внешних ссылок важно писать и `rel='noopener noreferrer'` — иначе открытая страница может манипулировать твоей через `window.opener`.

## CSP — вторая линия защиты

Заголовок [[csp]] ограничивает, из каких источников можно выполнять скрипты. Правильно настроенная CSP отсекает последствия XSS, даже если она произошла:

```
Content-Security-Policy: default-src 'self';
  script-src 'self' 'nonce-{random}';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none'
```

`frame-ancestors 'none'` предотвращает clickjacking. Безопасный способ внедрения — сначала применить CSP в режиме `Content-Security-Policy-Report-Only` и посмотреть на отчёты.

## Как работает CSRF

При атаке [[csrf]] вредоносный сайт заставляет браузер пользователя отправить запрос на твой сайт. Поскольку браузер автоматически добавляет cookie, запрос выглядит аутентифицированным.

```html
<!-- на вредоносном сайте -->
<form action='https://bank.example.com/transfer' method='POST'>
  <input type='hidden' name='to' value='attacker'>
</form>
<script>document.forms[0].submit()</script>
```

## Защита

```
SameSite=Lax     → в POST-запросах с другого сайта cookie не отправляются (современное значение по умолчанию)
SameSite=Strict  → самое строгое; не отправляются даже при переходе по внешней ссылке (влияет на UX)
CSRF-токен       → выданное сервером одноразовое значение отправляется вместе с запросом
Проверка Origin  → сервер проверяет источник запроса
```

Параметр [[same-site-cookie]] — главная защита в современных браузерах, но при поддержке старых браузеров или особых сценариях нужен и токен. Внимание: Bearer-токен, отправляемый в заголовке Authorization, не подвержен CSRF, потому что браузер не добавляет его автоматически, — это одна из сторон выбора между cookie и токеном.

## Параметры cookie

```
Set-Cookie: session=...; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600
```

`HttpOnly` закрывает чтение из JS (защита от XSS), `Secure` гарантирует отправку только по HTTPS.

## Заголовки безопасности

```
Strict-Transport-Security: max-age=63072000; includeSubDomains
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
Content-Security-Policy: ...
```

Они задаются в конфигурации сервера или хостинга (в Next.js — функцией `headers()`). Для проверки есть инструменты вроде securityheaders.com, и это простой шаг проверки после деплоя.

## Роль фронтенда

Ни один из этих механизмов не решается в коде фронтенда, но фронтенд-разработчик должен замечать их отсутствие: если у cookie нет HttpOnly, если CSP вообще не настроена, если сайт работает по HTTP — это вопросы, которые стоит поднять на ревью кода.

@@ deep.sec.2
Управление токенами и сессией — самый заметный компромисс между безопасностью и удобством. Важно знать причины решений, потому что аргумент «все так делают» здесь не работает.

## Варианты хранения и их риски

```
localStorage    : удобно, общий для всех вкладок   | при XSS токен крадут сразу
sessionStorage  : удаляется при закрытии вкладки   | тот же риск XSS
память (state)  : устойчивее к XSS                 | теряется при обновлении, нужен процесс обновления
HttpOnly cookie : JS не может прочитать — надёжнее всего | требует защиты от CSRF
```

Самый сбалансированный современный подход: access token в памяти (или в HttpOnly cookie), а refresh token — обязательно внутри [[http-only-cookie]].

## Что не кладут в токен

Payload [[jwt]] — это base64, он не зашифрован. Там не должно быть паролей, персональных данных, деталей внутренней системы. Срок жизни токена (`exp`) держат коротким.

## Проверка прав на фронтенде

```tsx
{can('orders.delete') && <DeleteButton />}
```

Это ТОЛЬКО удобство интерфейса. Даже если пользователь не видит кнопку, он может отправить запрос напрямую. Значит, каждая операция должна заново проверяться на сервере. Правильно объяснить это разделение на собеседовании — один из показателей уровня middle.

## Очистка при выходе

```ts
await api('/auth/logout', { method: 'POST' });  // аннулировать сессию на сервере
queryClient.clear();                             // удалить закэшированные данные
localStorage.removeItem('ui-prefs');
navigate('/login', { replace: true });
```

Не очистить кэш — реальная утечка данных на общих компьютерах.

## Синхронизация между вкладками

Если пользователь выходит в одной вкладке, остальные тоже должны об этом узнать:

```ts
window.addEventListener('storage', (e) => {
  if (e.key === 'auth-event' && e.newValue === 'logout') hardReset();
});
```

## Истечение сессии

Если при истечении токена сразу выкинуть пользователя на страницу входа, он может потерять свою работу. Лучшая практика: сохранить заполненную форму, предложить войти заново в модальном окне и после успеха вернуть пользователя туда, где он был.

@@ deep.sec.3
В современном фронтенд-проекте большая часть кода написана не тобой — она приходит из зависимостей. Это делает риск [[supply-chain]] реальным: вредоносная версия пакета напрямую попадает к твоим пользователям.

## Источники риска

Захват пакета (угоняют аккаунт владельца), вредоносный новый владелец, typosquatting (похожие имена вроде `react-domm`), post-install скрипты и транзитивные зависимости — пакеты, которые ты не выбирал, но которые приходят косвенно.

## Практическая защита

```bash
npm audit --production      # показать известные уязвимости
npm audit fix               # применить безопасные обновления
npm ls <пакет>              # какой пакет его тянет
```

Результаты [[npm-audit]] нужно читать без фанатизма: уязвимость в devDependencies часто не превращается в риск для продакшена. Важны уязвимости в коде, который уходит к пользователю.

## Автоматизация

[[dependabot]] или Renovate автоматически открывают PR с обновлениями. Правильная настройка: patch-обновления группируются еженедельно, а major-обновления приходят отдельными PR. Если тесты слабые, эта автоматизация становится рискованной — то есть и здесь основа — тестирование.

## Критерии выбора пакета

При добавлении новой зависимости: дата последнего обновления, число открытых issue, число мейнтейнеров, размер, транзитивные зависимости, лицензия и альтернативы. Подход «пакет ради одной функции» (например, `is-odd`) наполняет кодовую базу ненужным риском.

## Lock-файл и воспроизводимость

[[lock-file]] — не только стабильность версий, но и инструмент безопасности: хранятся точная версия и integrity-хэш, то есть если содержимое пакета изменится, установка упадёт. Использование `npm ci` в CI включает эту защиту.

## Другие меры

Блокировать post-install скрипты в CI через `npm ci --ignore-scripts` (с исключениями для пакетов, которым они нужны), приватный registry для внутренних пакетов и установка только `dependencies` в production-сборке. В крупных организациях может требоваться и SBOM (перечень состава ПО).

> Запомни: команда `npm install <пакет>` означает выполнение кода. Этот простой факт придаёт выбору зависимостей необходимую серьёзность.
